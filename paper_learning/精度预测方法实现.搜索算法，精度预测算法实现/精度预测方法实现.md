## 0. 文档定位

### 0.1 为什么单独写这份计划

v1.5 §6.2 已列出 Phase 2 的任务表,但每条任务只到"输出物"层级,没有具体到"用什么算法、什么数据、什么接口、什么验收标准"。本文档把搜索算法和精度预测器这两个**核心创新模块**展开为可执行的 SOP。

### 0.2 为什么把这两块放在一起

精度预测器和搜索算法**不是独立模块**,它们通过评估器接口紧耦合:
```
搜索器 → 提出候选配置 → 精度预测器评估 → 返回精度差
                    ↘ latency LUT 评估 → 返回延迟
                    ↘ 硬约束 DSL 验证 → 返回是否合法
        ← Pareto 前沿筛选 ← 综合评估结果 ←
```
分开实现 → 联调时接口反复变,工程返工大;一起规划 → 接口先定死,模块并行开发。

### 0.3 与上下游模块的关系

| 上游(已有) | 本计划 | 下游(后续) |
|-----------|--------|----------|
| 1.1 量化 baseline 数据 | **训练数据** | Phase 3 完整 NuScenes 评估 |
| 1.2 剪枝 baseline 数据 | **训练数据** | Phase 3 Orin Top-K 实测 |
| 1.3 latency LUT | **评估器组件** | Phase 3 跨硬件迁移 |
| Phase 1A 硬约束 DSL | **过滤器** | Phase 3 论文实验 |

### 1.2 模块接口契约(先定死)

```python
# 配置对象 — 跨模块统一表示
@dataclass
class Config:
    prune_rate: dict[str, float]       # {module_name: rate}
    prune_object: str                  # 'channel' | 'head' | '2:4'
    prune_criterion: dict[str, str]    # {module_name: 'L1'|'Taylor'|'FPGM'|'Wanda'}
    q_bits: dict[str, str]             # {module_name: 'INT8'|'FP16'|'FP32'}
    q_granularity: dict[str, str]      # {module_name: 'per-tensor'|'per-channel'}
    q_object: dict[str, str]           # {module_name: 'W-only'|'W+A'|'none'}
    d_routing: dict[str, str]          # {module_name: 'GPU'|'DLA0'|'DLA1'}

# 精度预测器接口
class AccuracyPredictor(Protocol):
    def predict(self, config: Config) -> float:
        """返回精度差(0 ~ 1, 越小越好,vs FP32 baseline)"""
    def predict_with_uncertainty(self, config: Config) -> tuple[float, float]:
        """返回 (mean, std), 用于 Bayesian 搜索"""

# latency 评估器接口(LUT 已有,这里只列接口)
class LatencyEstimator(Protocol):
    def estimate(self, config: Config, hardware: str) -> float:
        """返回 latency (ms)"""

# 搜索器接口
class Searcher(Protocol):
    def search(self,
               legal_space: SearchSpace,
               accuracy_predictor: AccuracyPredictor,
               latency_estimator: LatencyEstimator,
               n_evaluations: int) -> list[Config]:
        """返回 Pareto 前沿候选"""
```

**契约一旦冻结,Stage B / C 可并行开发。**

**A.6 主动采样策略**:
- 现有 1.1 数据是"只剪枝率为 0 的纯量化",1.2 数据是"只量化为 FP32 的纯剪枝"
- 联合空间 (剪枝率 × 量化位宽) 完全没覆盖 → **必须补**
- 采样策略:Latin Hypercube 在 (剪枝率 × 量化位宽 × 量化粒度) 三维上采 30-50 个点
- 每个点跑 1.1+1.2 已有的 PTQ 流程,记录 cosine 与 AMOTA(子集即可,Phase 3 才跑全集)

**A.7 划分策略**:
- 不要纯随机划分 — 容易让训练集和测试集出现"同模型不同模块的配置"导致泄漏
- 推荐 **按 source 分层**: 60% train / 20% val / 20% test,每个 source 都按 60/20/20 分
- 留一个 holdout: 5-10 个"未来 Phase 3 在 Orin 上实测"的配置作为最终 holdout,Stage B 训练时绝对不碰

## 3. Stage B: 精度预测器实现(Week 2 后半 — Week 3)

### 3.1 阶段目标

训练一个能在毫秒级返回精度差预测的模型,**Spearman ρ > 0.85** 即可用于搜索器。

### 3.2 模型选型决策

| 选型 | 优势 | 劣势 | 推荐场景 |
|------|------|------|---------|
| **LightGBM**(推荐 baseline) | 数据 < 1000 样本时表现稳定 / 训练秒级 / feature importance 可解释 | 不擅长高维稀疏特征 / 外推能力弱 | **首选**,Stage B 第一周 |
| MLP(2-3 层) | 表达能力强 / 可加 dropout 抗过拟合 | 数据少时易过拟合 / 调参敏感 | 数据 > 500 时升级用 |
| MLP + Transfer(APQ 风格) | 可从 FP32 模型迁移,样本省 5-10× | 工程复杂 / 需要预训精度预测器 | 数据始终不够时用 |
| Gaussian Process | 自带不确定性 / 适合贝叶斯搜索 | 样本数 > 500 时计算爆炸 | 仅作搜索器 BoTorch 内部使用 |

**推荐路径**: Week 2 后半实现 LightGBM,如果验收不达标,Week 3 升级到 MLP。

### 3.4 关键设计

**B.1 特征工程要点**:

```python
# 类别特征(LightGBM 原生支持,不要 one-hot)
categorical = [
    "prune_object",            # 4 类
    "prune_criterion__*",      # 每个 module 一个
    "q_granularity__*",        # 每个 module 一个
    "q_object__*",             # 每个 module 一个
    "d_routing__*"             # 每个 module 一个
]

# 数值特征
numerical = [
    "prune_rate__*",           # 每个 module 一个
    "q_bits__*_numeric",       # INT8=8, FP16=16, FP32=32
]

# 派生特征(关键!纯数据驱动可能学不出来,要手工注入)
derived = [
    "prune_rate__avg",         # 跨模块平均
    "prune_rate__std",         # 跨模块标准差(对应 §0.3 跨层梯度约束)
    "q_bits__weighted_avg",    # 按 FLOPs 加权
    "q_bits__min",             # 最低位宽(瓶颈)
    "criterion_diversity",     # 不同 module 用了多少种准则
    "is_dla_routed",           # 是否有任何 module 走 DLA
]
```

**B.3 评估指标的优先级**:

| 指标 | 权重 | 解释 | 通过线 |
|------|------|------|--------|
| **Spearman ρ** | **最高** | Pareto 用相对排名,排名对就够 | **> 0.85** |
| Pareto rank correlation | 高 | 直接评估在 Pareto 前沿上的排名一致性 | > 0.75 |
| MAE | 中 | 绝对误差,辅助 | < 0.005 (0.5%) |
| R² | 低 | 容易被异常点带偏 | > 0.7 |

**为什么 Spearman 比 MAE 重要**: 搜索器只看哪个配置精度更高,不看精度具体差多少。预测精度差 0.01 vs 0.012 不重要,但排序对了至关重要。

**B.6 不确定性估计的两条路**:
- **LightGBM quantile regression**: 训三个模型(0.1 / 0.5 / 0.9 分位数),区间宽度 = 不确定性
- **Bootstrap ensemble**: 训 5-10 个 LightGBM(不同子样本),std = 不确定性

推荐 quantile regression,工程量小一半。

### 3.5 验收标准

- [ ] **Spearman ρ > 0.85** on val 集
- [ ] Pareto rank correlation > 0.75 on val 集
- [ ] MAE < 0.5% on val 集
- [ ] 单次预测 < 10 ms(否则搜索器吞不下)
- [ ] holdout 测试集上不退化超过 10%(防止过拟合到 val)
- [ ] 不确定性估计:90% 区间覆盖率 ∈ [85%, 95%](校准良好)

### 3.6 调试与诊断

预测器训不出来时按以下顺序排查:

1. **数据问题**: target 分布跨度太小(<0.02) → 数据没覆盖足够极端配置
2. **泄漏**: train / val 同 source 的 config 几乎一样 → 改 stratified split
3. **特征不足**: 缺少派生特征(如 `prune_rate__std`)→ 加手工特征
4. **过拟合**: train ρ > 0.95 但 val ρ < 0.7 → `num_leaves` 调小、加 L2
5. **欠拟合**: train ρ < 0.7 → 数据真的不够,回 Stage A.6 主动采样

## 4. Stage C: 搜索算法实现(Week 3 后半 — Week 4)

### 4.1 阶段目标

实现一个多目标 Pareto 搜索器,**给定预测器和 LUT,在 1000 次评估内找到 Pareto 前沿**。

### 4.2 算法选型决策

| 算法 | 工程量 | 样本效率 | 适合场景 | 推荐 |
|------|-------|---------|---------|------|
| 简单穷举 | 0.5 d | — | 搜索空间 < 1000 | 仅做 sanity baseline |
| 随机采样 + Pareto 过滤 | 0.5 d | 低 | 任何场景的 baseline | sanity baseline |
| **NSGA-II**(推荐) | 1-2 d | 中 | 评估快(预测器 ms 级) | **首选** |
| 贝叶斯多目标(qNEHVI) | 5 d | 高 | 评估慢(实测 min 级) | Phase 3 实测时用 |

**推荐路径**: 先做随机采样作为对照基线,再上 NSGA-II 作为主搜索器,贝叶斯留到 Phase 3。

**为什么 Phase 2 不用贝叶斯**: 预测器评估 ms 级,1000 次评估 ~10 秒,NSGA-II 完全够用。贝叶斯的样本效率优势在评估代价高时才体现(实测 min 级时,贝叶斯比 NSGA-II 省 5-10×)。

### 4.4 关键设计

**C.1 配置编码:混合空间处理**

NSGA-II 默认处理连续空间。本问题是混合空间(连续 + 类别),需要特殊编码:

```python
# 方案 A: 全部转为连续(简单)
# prune_rate ∈ [0, 0.7]            (天然连续)
# q_bits ∈ {INT8, FP16, FP32}     → 编码为 [0, 0.33, 0.67],用阈值离散化
# q_granularity ∈ {per-tensor, per-channel} → [0, 1] + 阈值 0.5

# 方案 B: pymoo MixedVariable(推荐)
import pymoo.core.variable as var
problem_vars = {
    "prune_rate__backbone": var.Real(bounds=(0, 0.7)),
    "q_bits__backbone": var.Choice(options=["INT8", "FP16"]),
    "q_granularity__backbone": var.Choice(options=["per-tensor", "per-channel"]),
    # ...
}
```

**C.4 硬约束三种处理方式对比**:

| 方式 | 实现 | 优劣 |
|------|------|------|
| **Repair**(推荐) | 把违法个体修正为最近的合法个体 | 不浪费评估预算,但 repair 函数要写 |
| Penalty | 违法个体 fitness 加大惩罚 | 简单,但浪费评估预算 |
| Death penalty | 违法直接弃用 | 最简单,但探索效率最低 |

**Repair 示例**:
```python
class HardConstraintRepair(Repair):
    def _do(self, problem, X, **kwargs):
        # 通道对齐 32: prune_rate 触发的剪后通道数对齐到 32
        for i in range(len(X)):
            for module in modules:
                rate = X[i, f"prune_rate__{module}"]
                orig_ch = original_channels[module]
                pruned_ch = round_to_multiple(orig_ch * (1 - rate), 32)
                X[i, f"prune_rate__{module}"] = 1 - pruned_ch / orig_ch
        # DLA 路由触发 B2 强制
        for i in range(len(X)):
            if X[i, f"d_routing__{m}"] == "DLA0":
                X[i, f"q_bits__{m}"] = "INT8"
                X[i, f"q_granularity__{m}"] = "per-tensor"
        return X
```

**C.5 评估器集成 — 多目标 fitness**:

```python
def evaluate(config: Config) -> tuple[float, float]:
    """返回 (-accuracy, latency), pymoo 默认最小化"""
    # 1. 调精度预测器
    accuracy_loss = accuracy_predictor.predict(config)  # 越小越好
    # 2. 调 latency LUT

```

**C.6 早停设计**:

| 早停条件 | 触发 | 含义 |
|---------|------|------|
| 评估次数 >= 1000 | 计数 | 资源上限 |
| 连续 50 代 hypervolume 增长 < 0.1% | hypervolume metric | 收敛 |
| 当前最优解被验证集判定为过拟合 | holdout check | 预测器不可信 |

**多样性维持**: 不要只挑当前 Pareto 前沿 Top-1,保留 Pareto 前沿上**等距 5-10 个点**作为 Phase 3 实测候选(覆盖精度-延迟全 trade-off)。

### 4.5 验收标准

- [ ] 1000 次评估完成 < 30 秒(预测器够快)
- [ ] NSGA-II 搜出的 Pareto 前沿 hypervolume **严格大于**随机采样基线
- [ ] Pareto 前沿上至少 5 个不同 trade-off 配置
- [ ] 0% 违法 — 硬约束 Repair 工作正常
- [ ] 与穷举对比(在小子空间内):NSGA-II 找到的 Pareto 与穷举的偏差 < 5%

### 4.6 风险与对策

| 风险 | 对策 |
|------|------|
| pymoo MixedVariable 在最新版本接口变动 | 锁定 pymoo == 0.6.x,提前 freeze requirements |
| Repair 函数写漏约束 → 仍有违法个体 | 评估前再走一次硬约束 DSL 验证 |
| Pareto 前沿"挤"在一个点附近 | 用 reference point 强制多样性 |
| 搜索器搜出的"最优"在 holdout 上不复现 | Stage D 必须做 holdout 验证 |

### 5.3 关键设计

**D.2 准则按子网分配(§0.5 落地)**:

```python
# 按 module 类型分配候选准则池
CRITERION_POOL = {
    "backbone":    ["L1", "FPGM"],          # CNN + BN, 偏几何
    "bev_encoder": ["L1", "Taylor"],        # 介于 CNN 和 Transformer
    "bev_decoder": ["Taylor", "Wanda"],     # Transformer, 偏激活感知
    "head":        ["L1"],                  # 简单分类头, L1 够用
}

# 在硬约束 Repair 中,把 prune_criterion 限制到对应池子
# 避免搜索器在 backbone 上选 Wanda(失效准则)
```

**D.4 与单维度搜索对比的实验设计**:

| 对照组 | 配置 | 期望结果 |
|--------|------|---------|
| Baseline 1: 1.1 单独量化最优 | 仅搜 B2,B1=0,D=GPU | 协同 Pareto **应该能 dominate**(同等精度下 latency 更低) |
| Baseline 2: 1.2 单独剪枝最优 | 仅搜 B1,B2=FP32,D=GPU | 协同 Pareto **应该能 dominate** |
| Baseline 3: 1.3 latency 优化 | 仅搜 D,B1/B2 给定 | 协同应在 Pareto 上多出几个点 |
| Baseline 4: 顺序搜索 (B2→B1→D) | 串行搜,不联合 | 协同应找到 Baseline 4 找不到的"局部次优规避点" |

**通过标准**:
- 协同 Pareto 前沿至少有 3 个点 dominate 任一 baseline
- 协同最优(精度优先)精度差 ≤ 任一 baseline 的精度差
- 协同最优(延迟优先)延迟 ≤ 任一 baseline 的延迟

**D.6 4090→Orin 复现率分析**:

```
拿 D.5 选出的 10 个 4090 Pareto 候选,在 Orin 上实测 latency 和精度
↓
计算 Spearman ρ
  - 精度排名: 4090 vs Orin(应几乎一致, ρ > 0.95)
  - latency 排名: 4090 vs Orin(compute-bound 应高, memory-bound 应低)
  - 综合 Pareto rank: ρ > 0.7 通过
↓
如果 ρ < 0.7 → 4090 阶段的 Pareto 在 Orin 上失效, Phase 3 必须重做
```

### 5.4 验收标准

- [ ] D.3 在 4090 上 6 小时内跑完 1000 次评估
- [ ] D.4 协同 Pareto 至少 dominate 1 个 baseline 的 3 个点
- [ ] D.5 候选清单覆盖精度-延迟 trade-off 至少 3 档(高精度 / 平衡 / 低延迟)
- [ ] D.6 Spearman ρ(精度) > 0.95 / Spearman ρ(综合) > 0.7
- [ ] D.7 报告包含: 实验配置 / Pareto 前沿图 / baseline 对比表 / Orin 复现分析
