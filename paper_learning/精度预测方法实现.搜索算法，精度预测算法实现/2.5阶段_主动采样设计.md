## 一、设计目标与依据

Sanity 报告 §四已经定位:46/48 特征因方差为 0 被 GBM 沉默。Stage 2.5 不是"多采点",而是**精确**针对沉默列采样:

| 沉默原因 | 列数 | 解决路径 |
|---------|------|---------|
| 1.1/1.2 实验没动这些模块 | 7 列 (backbone/heads/v2x_comm 剪枝相关) | **本采样针对前两个,v2x_comm 投入产出比低留待 Phase 3** |
| Phase 1A 锁 GPU only | 5 列 (d_routing__*) | 不在本采样范围,**留 Phase 3 Orin 实测** |
| 量化轴在 22 行里同步变化 | 4 列 (q_bits__* 高度相关) | **D 类 5 个配置专门打破此相关** |
| 剪枝 × 量化联合数据稀缺 | compound_pressure | **E 类 12 个配置就是为这个** |

## 三、合法性 + 探索性归类

| 类型 | 数量 | 含义 |
|------|------|------|
| **常规配置(经验约束也通过)** | 13 / 30 | "安全采样",肯定能跑出有用数据 |
| **探索性配置(触发经验约束)** | 17 / 30 | 故意触发"跨层梯度 < 30%",**用于 Phase 1B.6 拐点验证** |
| **物理违法(build 失败)** | 0 / 30 | 全部物理硬约束通过 ✅ |
| **软约束触发** | 0 / 30 | (FP32+INT8 极端混合等 negative 样本本批没采) |

**为什么 17 个探索性配置不该被丢弃?**

v1.5 §0.3 把约束分三类(物理/经验/软),并明确指出**经验硬约束本质是工程师手写的规则,Phase 1B.6 必须实测验证**。Stage 2.5 跑这 17 个"探索性"配置,会得到三种可能结果:

1. **它们的 latency 真的比常规的差很多** → 经验约束被实测确认 → 保留为硬过滤
2. **跟常规配置差不多** → 经验约束**过度保守** → 降级为软约束 / 废除
3. **介于两者之间** → 改写为按梯度大小给 penalty 的连续函数

无论哪种,**这 17 个配置都给框架提供了重要信号**。如果只采常规配置,我们永远不知道经验约束是真是假。

## 四、覆盖度分析(假设 30 个配置都拿到 AMOTA)

把 30 个 Config(无 target)合并到 22 行 baseline,**特征方差变化**:

### 4.1 解锁的特征(DEAD → OK/LOW)

| 特征 | before | after | 解锁路径 |
|------|--------|-------|---------|
| `prune_rate__backbone` | DEAD (全 0) | OK (4 个值) | A1-A6 + E9-E11 |
| `prune_rate__heads` | DEAD (全 0) | OK (2 个值) | B1-B3 + C3-C4 |
| `prune_criterion__backbone` | DEAD ('none' × 22) | OK | A 类带准则 'L1' |
| `prune_criterion__heads` | DEAD ('none' × 22) | LOW | B 类带准则 'L1' |

**4 个被沉默的特征被解锁** ← Stage 2.5 的核心战略目标达成。

### 4.2 关键派生特征方差变化

| 特征 | before var | after var | 倍数 | 含义 |
|------|-----------|-----------|------|------|
| **`compound_pressure`** | 0.0015 | **0.0027** | **1.8×** | **核心 motivation 特征,剪枝×量化联合压力** |
| `prune_rate__std` | 0.0161 | 0.0109 | 0.7× | 反而下降(单轴样本稀释了差异化分布) |
| `q_bits_num__std` | 6.0287 | 3.3933 | 0.6× | 反而下降(D/E 类多为全模块同位宽) |
| `criterion_diversity` | 0.2078 | 0.1701 | 0.8× | 微降(全程统一 L1) |

**`compound_pressure` 提升 1.8×** 是这个采样的**最关键收益**。它是 GBM 学习"剪枝压力 + 量化压力"的耦合形式 — Stage 4 NSGA-II 在 Pareto 前沿找最优 trade-off 时,这个特征直接决定预测器能否区分 "剪 30%+INT8" vs "剪 50%+FP16"。

### 4.3 仍 DEAD 的列(9 个)

| 仍 DEAD 的列 | 原因 | 何时打开 |
|------------|------|---------|
| 5 × `d_routing__*` | Phase 1A 决策 D1 锁 GPU | **Phase 3 Orin 实测** |
| `prune_rate__v2x_comm` | 没采(FLOPs 占比 5%,投入产出低) | Phase 3 视情况补 |
| `prune_criterion__v2x_comm` | 同上 | 同上 |
| `prune_rate__min` | 派生于 v2x_comm,只要 v2x_comm 不动就永远是 0 | 同上 |
| `is_dla_routed` | 派生于 d_routing,跟着 D1 解锁 | Phase 3 |

## 五、与 1.1/1.2 现有 schema 的兼容性

每个配置都生成了**两份 JSON**(直接放到现有 1.1/1.2 schema 里):

```
prune_configs/active_A1.json  …  active_E12.json    (30 份, 1.2 prune schema)
quant_configs/active_A1.json  …  active_E12.json    (30 份, 1.1 quant schema)
```

**兼容性核对**:
- ✅ `prune_configs/*.json` 字段对齐 1.2 现有的 `encoder/decoder/heads + locked + finetune + constraints`
- ⚠️ **多了一个 `backbone` 字段** — 1.2 实验代码里没实现 backbone 通道剪枝,A 类 6 个配置需要新代码或借助 Torch-Pruning(已在 prune JSON 里加了 `_note` 提醒)
- ✅ `quant_configs/*.json` 字段对齐 1.1 现有的 `global + layers + v2x_comm`,新增 `modules` 段细化每模块位宽

**这意味着**: 4090 上跑 PTQ 评估时,大部分配置直接复用 1.1/1.2 已有的实验脚本即可,**唯一新增工作量是给 backbone 加通道剪枝实现**(预计 0.5 天)。
