## 〇、方向纠偏

之前 `00_故事评估与实验路线_v1.md` 提的 framing 有误——把三档硬件按"4090 RSU / AGX 车端 / NX 量产"做应用分层，并自创"closed-loop HW-SW co-design"作为创新点。**这不符合 v1.5 工作流**。

v1.5 的真实结构：

```
┌─ 步骤 1: 硬件 capability YAML （三档硬件 = 三份 YAML 实例）
│   ↓
├─ 步骤 2: 注入硬约束 → 三份不同的合法搜索空间
│   ↓
├─ 步骤 3: B1 × B2 × D 联合搜索 → 三份不同的 Pareto 前沿
│   ↓
├─ 步骤 4: Top-K 实测验证
│   ↓
├─ 步骤 5: 制品化（engine + cache + 配置 YAML）
│   └ 配置 YAML 跨硬件流转，engine 不跨硬件
└─ 步骤 6: 在线监控 + 回归
```

**论文 contribution（按 v1.5）**：
1. **硬件 capability 描述文件 schema**（步骤 1）— 让一套框架适配 N 种硬件
2. **D ↔ B2 双向硬约束传播**（步骤 2 + §0.2）— 这是协同的核心耦合点
3. **B1 × B2 × D 联合搜索 + 评估反馈回路**（步骤 3 + §0.4）— 不是单维度顺序搜
4. **三硬件 Pareto 对比**揭示最优解的结构性差异（步骤 3-4 跨硬件结果）

UniV2X 上"加速天花板低"的事实仍可作为 motivation——它证明**单维度搜索 + 没有硬约束注入**会落入次优陷阱。

## 四、Orin NX 怎么办（这是论文叙事的薄弱点）

v1.5 §6.1 Phase 1A.2 要求 Orin Nano / Orin NX 也有 capability YAML 实例。当前**没有 Orin NX 设备**。

**两个候选方案**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| **(a) 仅写 capability YAML 推算式实例**（基于 NX 16GB 公开规格）+ 在 AGX 上用 cgroup/nvpmodel 模拟 NX 的算力上限 | 不需新设备；论文里诚实标注"模拟 NX"| 不能跑 NX 真实 latency，论文只能给"如果是 NX 会怎样"的推算 |
| **(b) 临时云端租用或借用 NX**（NVIDIA 开发者计划 / 高校实验室）| 真实数据 | 需协调，时间不可控 |

**建议**：先按 (a) 做，把 capability YAML 推算实例和 cgroup 模拟跑通；如果后期能拿到 (b) 真机，论文末期补一组 NX 真测做 ablation。
