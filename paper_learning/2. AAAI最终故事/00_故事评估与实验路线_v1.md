## 一、论文故事（按 v1.5 framing）

### 1.1 一句话核心

> **给定一个待加速网络与一档目标硬件，自动产出该硬件上的 Pareto 前沿（精度 × 延迟 × 能耗）；同一套框架适配多种硬件 (RTX 4090 / Jetson Orin AGX，未来扩展) × 多种网络（UniV2X / Pyramid Fusion / UniAD-tiny，未来扩展），通过硬件 capability 描述文件 + 硬约束自动注入实现"网络-硬件"双向可移植。**

**重要 framing 注意点（决策 D5 修正）**：
- **没有"主模型"一说**。UniV2X / Pyramid Fusion / UniAD-tiny 三个模型在论文中**地位平等**——都是"加速目标"
- 每个模型有各自的 Pareto 前沿、各自的最优配置、各自的"适配性结论"
- 论文叙事是"框架在 N 种网络 × M 种硬件上的自适应能力"，不是"主网络在三种硬件上的优化"
- 网络是**输入参数**（与硬件 capability YAML 对称），不是论文叙事的主角

### 1.2 论文 contribution（4 项，源自 v1.5 框架本身）

| # | Contribution | v1.5 对应 |
|---|---|---|
| **C1** | **硬件 capability 描述文件 schema** — 把硬件抽象为 (IP 列表, 精度集合, 对齐约束, 算子白名单, 工具链) 的 YAML 描述，让一套搜索流程适配 N 种硬件 | 步骤 1 + §0.2 分层旋钮的硬件依赖 |
| **C2** | **D ↔ B2 双向硬约束传播** — 把"模块路由到 DLA → B2 强制 per-tensor + INT8 + W+A"和反向"B2 选 per-channel → 该模块禁选 DLA"工程化为可复用的传播算子 | 步骤 2 + §0.2 重要区分表 |
| **C3** | **B1 × B2 × D 联合搜索 + 评估反馈回路** — 不是"先搜剪枝再搜量化再搜部署"的串行；评估器把实测/查表 latency 反馈回搜索器 | 步骤 3 + §0.4 |
| **C4** | **三硬件 Pareto 对比** — 同一网络在三档 capability YAML 上独立搜出的 Pareto 揭示最优解的结构性差异（例如 4090 上偏 per-channel + sparse TC，Orin AGX 上偏 DLA 子图 + per-tensor，Orin NX 上偏激进剪枝 + INT8） | 步骤 3-4 + §5 双平台分工 |

### 1.3 关键 motivation 数据（已在手）

| 反例 | 来源 | 论证什么 |
|---|---|---|
| UniV2X R101+DCN 22 维"声明搜索空间"实际可达 ≈ 9-10 维 | 1.1/1.2/1.3 + 整合报告 | **没有硬约束注入 + 单维度搜索 → 大量 config 物理上无法生效**（A 类 backbone 剪枝 prune_univ2x.py 不支持，D 类多模块量化 quick_eval_quant.py 只量化 BEV encoder 等）|
| V2X-ViT INT8 PTQ AP30 75.1 → 29.9 (-45pt) 崩溃 | QuantV2X 实测 | **没有 D ↔ B2 双向传播 + 缺乏精度预测器 → 量化决策"事后才知道崩"**；我们的精度预测器 + 硬约束传播能事前避免 |
| ResNet-50 FP16 在 Orin AGX 上 17,396 个 tactic 中 5,663 个 reformat layer (33%) | Orin 端 F1 verbose log（已采）| **量化/剪枝边界引入大量 reformat 反吞收益**——正是 v1.5 §0.2 要解决的"跨层精度边界"问题 |

### 1.4 与现有工作的差异

| 对比对象 | 我们多了什么 |
|---|---|
| **QuantV2X**（V2X 量化部署，2.2× 加速）| 量化 only → **B1 × B2 × D 联合**；事后报告崩溃 → **硬约束 + 反馈回路事前规避** |
| **APQ / HAQ**（HW-aware NAS L1 层）| 搜 A+B1+B2，硬件是 LUT 输入 → 我们搜 **B1+B2+D**，硬件是 capability YAML（不是黑盒数字）|
| **HALP / LightPrune**（HW-aware 剪枝）| 单维度（剪枝）+ latency LUT → 多维度联合 + **D ↔ B2 双向传播** |
| **CUDA-BEVFusion / DL4AGX uniad-trt**（NVIDIA 官方 BEV 部署）| 手工调参的最优部署 → **自动化 Pareto 搜索**（手工调参作为我们的 baseline 而非对手）|

#### 2.2.1 剪枝缺口的解决路径（直接回应"是不是要换模型"）

**核心判断**: **不是"承认 UniV2X 不能剪枝就换模型"的二元选择**。剪枝在 UniV2X 上的卡点是**模块级**的（backbone 卡死 / heads 卡级联 / FFN+decoder 可剪），论文应该**分模块对待 + 主力剪枝实验放到更友好模型**。

**三条候选路径**：

| 路径 | 内容 | 工程量 | 风险 | 推荐 |
|---|---|---|---|---|
| **A. 修剪枝代码** | 让 `prune_univ2x.py` 支持 backbone 分支 + heads 级联（DepGraph 或手写）| 6-10 天 | 高 | 拆分看 |
| └ **A1** R101+DCNv2 上做 backbone 剪枝 | DCN op weight 切片 + 重训 6 epoch | 5-7 天 | ❌ 历史 3 次 OOM | 不推荐 |
| └ **A2** DCNv2 → DCNv4 替换 + 微调（**DL4AGX dcnv4-trt 已有现成代码**）| 权重迁移 + 微调 + DL4AGX 验证 | 3-5 天 | 中 | ✅ **优先评估**（D4 决策）|
| └ **A3** heads 剪枝 DepGraph 集成 | mmcv 模型 DepGraph 兼容性 + LayerNorm 同步 | 2-3 天 | 中 | ⚠️ ROI 低（heads 占比小）|
| **B. 主力剪枝换更友好模型** | 把剪枝主力实验放到剪枝 100% 友好的模型上 | 0-5 天 | 低 | ✅ **主推** |
| └ **B1** UniAD-tiny (R50 无 DCN) | baseline 已训好；标准 conv 剪枝直接生效 | 0 天 | 低 | ✅ |
| └ **B2** Pyramid Fusion (HEAL) | 全 CNN，剪枝完全可用；DL4AGX 有 SparsityINT8 现成 | 3-5 天 移植 | 低 | ✅ |
| **C. UniV2X 接受局限** | 不剪枝，仅在 UniV2X 上做 B2 量化 + D 空间；剪枝维度作反例 | 0 天 | 0 | ✅ **必做兜底** |

**当前组合推荐（不是非此即彼）**：

```
C 必做（兜底）:
  UniV2X 在 B2/D 维度继续做实验 → 定位为论文 "重模型反例 + DCN 死锁的物理硬约束实证"
  这正是 v1.5 §0.3 物理硬约束 vs 经验硬约束区分的活案例

A2 优先评估（决策点 D4，2-3 天定方向）:
  评估 DL4AGX/dcnv4-trt 替换 DCNv2 是否可行（权重迁移 + 短期微调）
  ✅ 成 → UniV2X 升级为"能剪 backbone 的主线"，C 路径降级为兜底
  ❌ 败 → 维持 C 路径不变

B1 + B2 主推（剪枝主力实验在友好模型上）:
  UniAD-tiny: backbone 剪枝代码无需 DCN 适配，0 天工程量起步
  Pyramid Fusion: 全 CNN 剪枝 100% 友好，3-5 天移植到框架
  → 跨模型对照梯度: UniV2X(反例) vs UniAD-tiny(部分剪枝) vs Pyramid Fusion(完全剪枝)
  这本身就是论文 §0.5 "准则按子网分配"的天然实验素材
```

**正面回答"是不是承认 UniV2X 没法剪枝"**：

- ✅ 在 **R101+DCNv2 baseline** 下 backbone 剪枝是**物理硬约束** — DCN plugin 是 fused kernel，不响应通道剪枝。这**不是缺陷而是论文证据**（v1.5 §0.3 物理 vs 经验硬约束区分的活案例）
- ✅ heads 剪枝缺级联工具是**经验硬约束**（DepGraph 工程化能解，但 ROI 低）
- ❌ **不是"换掉 UniV2X"**，而是"**UniV2X 在剪枝维度上降级为反例 + 主力剪枝实验换 UniAD-tiny / Pyramid Fusion**"
- 🟡 **A2 (DCNv4 替换) 仍是 2-3 天能定方向的可选升级路径**，成则 UniV2X 自动升级为剪枝主线

**对论文 framing 的影响**：

正面影响 ≥ 负面影响。剪枝跨模型梯度（不可剪 / 部分可剪 / 完全可剪）反而是 **C2 双向硬约束传播 + C4 三硬件 Pareto 对比** 之外的第三个对照维度——证明框架能在不同剪枝可行性的模型上自动识别可达搜索空间。这比"硬上 UniV2X 剪枝"更有说服力。

### 5.1 决策 D5 的关键含义：无主模型论文叙事

**这是 v2.1 最重要的 framing 修正**。

```
旧叙事（v2.0 草稿）:
  UniV2X 是主线 → UniAD-tiny / Pyramid Fusion 是对照
  → 这种叙事会让 reviewer 问 "为什么主线就是 UniV2X"

新叙事（v2.1 决策 D5）:
  论文加速三个目标网络: UniV2X, Pyramid Fusion, UniAD-tiny
  各自有各自的:
    - capability frontier（在 4090 / AGX 各档下的 Pareto 前沿）
    - 适配性结论（哪些维度可剪/可量化，哪些是物理硬约束）
    - 最终最优配置（UniV2X DCN 限制下的最优 vs Pyramid 全 CNN 下的最优）
  → 论文 contribution 是"框架对多种网络的自适应能力"
  → 三个模型各自的 Pareto 对比本身就是论文 §4 实验主结果
```

### 5.2 决策 D4 的执行细节：DCN v4 闸门测试

**1-2 天内能定方向**：

```
Day 1 (Orin AGX):
  cd ~/DL4AGX_git/AV-Solutions/dcnv4-trt/
  跑 README 提供的 sample（最小 ONNX → TRT build/run）
  闸门 1: build 成功 + inference 输出正确?

Day 2 (取决于 Day 1 结果):
  IF Day 1 通过:
    在 dcnv4-trt sample 上启用 --int8 + calibration
    闸门 2: INT8 build 成功 + 精度差 < 5%?
    IF 通过 → DCNv4 解锁 INT8，UniV2X 可走"正常加速 case"路径
    IF 不通过 → INT8 在 Orin 上 DCN 仍受限 → UniV2X 进"不适合边缘"清单
  IF Day 1 不通过:
    UniV2X 直接进"不适合边缘"清单（连 FP16 部署都受限）
```

无论结果如何，UniV2X 的论文角色都明确：要么是"DCN-aware 加速 case"，要么是"边缘不适配的实证"。**不需要赌 DCNv4 替换全流程成功**。
