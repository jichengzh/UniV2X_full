## 问题 1 — 自训 ckpt 在 entropy INT8 校准下 AP 崩塌

**发现日期**: 2026-05-14
**已解决日期**: 2026-05-15 (采纳方案 1 = MinMax 校准为主路径)
**影响范围**: T3_p37 / T5_p62 / T7_wide_shallow / T8_narrow_deep 这 4 个我们自训的 Pyramid ckpt
**最终决议**: TRT INT8 build 主路径用 `trt.IInt8MinMaxCalibrator` 替代 `trt.IInt8EntropyCalibrator2`, 详见 §1.5 方案 1

### 1.1 一句话概括

自训模型在 FP16 下能检测，但它的中间激活分布比官方模型宽很多；TensorRT 的 entropy INT8 校准对这种"宽分布/长尾分布"很敏感，导致分类头量化后 score 边界失真，最终 AP 崩塌。

### 1.2 支持证据 (activation histogram 实测)

**测量**: 8 ckpt × 30 DAIR test sample, hook `shrink_conv` 输出 (= cls_head 输入, INT8 量化最关键位置).

| triplet | source | shrink_conv p99 | shrink_conv max | cls_head p99 | FP16 AP50 | INT8 entropy AP50 |
|---------|--------|----------------|-----------------|--------------|-----------|---------------------|
| T1_base | 官方 | **1.41** | 6.05 | 10.04 | 0.785 | 0.410 (部分崩) |
| T2_p25 | 官方 | **1.16** | 4.42 | 8.16 | 0.775 | 0.606 (部分崩) |
| T4_p50 | 官方 | **1.17** | 4.25 | 8.03 | 0.755 | 0.198 (部分崩) |
| T6_p75 | 官方 | **1.20** | 2.73 | 7.17 | 0.750 | **0.748 ✅** |
| **T3_p37** | **自训** | **2.48** | 6.91 | 10.07 | 0.761 | **0.021 ✗** |
| **T5_p62** | **自训** | **3.53** | 8.37 | 10.05 | 0.744 | **0.021 ✗** |
| **T7_wide_shallow** | **自训** | **2.79** | 7.25 | 10.27 | 0.761 | **0.021 ✗** |
| **T8_narrow_deep** | **自训** | **2.64** | 6.22 | 10.91 | 0.757 | **0.020 ✗** |

**核心数字**: 自训 ckpt 的 `shrink_conv` 输出 p99 = **2.48-3.53**, 官方 ckpt 为 **1.16-1.41** → **2-3× 偏宽**

### 1.3 失败链路

```
短期 fine-tune (25 epoch) + 无 weight decay
        ↓
BN running stats 没收敛 + conv 权重幅度未规整
        ↓
shrink_conv 输出激活整体偏宽 (p99 翻 2-3×)
        ↓
TRT entropy calibrator 选择更大的 clip 范围
        ↓
INT8 量化粒度 (step = clip/127) 变粗 ~3×
        ↓
cls_head INT8 matmul 输出在 logit≈-1.39 (= score 0.2) 附近精度不足
        ↓
sigmoid 后 fg/bg 判别失效, 所有候选框被同质化
        ↓
AP50 从 0.74-0.77 跌到 0.02 (全崩)
```

### 1.4 不是什么 (排除项)

| 候选根因 | 排除证据 |
|----------|---------|
| 剪枝率高 → 崩 | T6_p75 (75% prune) 完全不崩, T3_p37 (37%) 全崩 — **反向相关** |
| per-group width 非 pow2 → 崩 | T2 全非 pow2 没崩, T4 全 pow2 还是崩 — **不相关** |
| FP 权重坏了 | 所有 triplet FP16/INT8_minmax AP 都在 0.73-0.79 正常区间 — **ckpt 本身可用** |
| TRT engine / build pipeline bug | minmax 在同 engine 上完全 OK — **build 路径没问题** |
| 校准数据不够 (100 sample) | 100 sample 跑 minmax 稳得很 — **样本量不是瓶颈** |

### 1.5 解决方案

#### ✅ 方案 1 (主路径): INT8 校准换 MinMax

- **工程量**: 0 (只换 TRT calibrator 类)
- **核心修改**: `trt.IInt8EntropyCalibrator2` → `trt.IInt8MinMaxCalibrator`
- **效果** (e2e engine 实测, 8 triplet × 500 DAIR val):
  - 全部 build 成功, 全部稳定不崩
  - AP50 = **0.62-0.65** (官方/自训无差距, 见 §1.5.x)
  - 自训 ckpt 从 entropy 路径 0.02 → 0.62, 规避崩溃
- **代价**: 相比 FP16 (AP ~0.75) 损失 0.10-0.13 (e2e INT8 含 VFE+Scatter 固有损失, 与校准无关)
- **落地动作**:
  - framework 搜索空间剔除 `calibrator=entropy` (或保留作 LGB 负样本)
  - 主搜索 / Pareto / LGB 数据统一用 minmax
  - AP 数据源切到 `results/e2e_ap_minmax_v1/*.json` (e2e 实测), 不再用 `class_a_pyramid_full` (subnet)

#### ⏸ 方案 2 (备选): TRT percentile calibrator (p99.99 clip)
3-4h 工程, AP 0.58-0.65 跟方案 1 持平略低, 工程更脆弱 (PyTorch hook + 手工 `tensor.dynamic_range`). 不主用, 留作 calibrator 消融. 实现: `scripts/phase2/build_percentile_e2e_engine.py`.

#### ✗ 方案 3 (已验证无效): 延长 fine-tune 47→77 ep
shrink_conv p99 没收窄反而略升 (T3 2.48→2.98 等), 4 个 ckpt bestval 停 ep35. 宽分布是 schedule 结构性产物, 加 epoch 无效.

#### ⏸ 方案 4 (未尝试): QAT
1-2 day 工程, 仅当方案 1+2 都不够用时启动.

#### 1.5.x subnet AP vs e2e AP 差异 (重要修正, 2026-05-15)

旧 schema §八 假设 "AP 跟 TRT engine ONNX 范围无关" **被实测推翻**. e2e engine AP 比 subnet AP 系统性低 0.10-0.16 (VFE+Scatter INT8 量化噪声 subnet 测量看不到):

| triplet | subnet AP50 | e2e AP50 | 偏差 |
|---------|-------------|----------|------|
| T1_base | 0.785 | 0.625 | -0.160 |
| T3_p37 (自训) | 0.762 | 0.624 | -0.138 |
| T6_p75 | 0.748 | 0.645 | -0.103 |
| T8_narrow_deep (自训) | 0.747 | 0.652 | -0.095 |
| (其他 4 略) | | | |

**影响**: AP 列以 e2e 实测为准, Pareto 表 / LGB 训练全部切到 `results/e2e_ap_minmax_v1/`.

### 1.6 相关文件

## 问题 2 — lat 对比口径混淆: 用 e2e lat 比 Q 维度被 postproc 噪声污染

**发现日期**: 2026-05-15
**已解决日期**: 2026-05-15 (lat 对比口径切到 `lat_trt_mean_ms`)
**影响范围**: A.1 phase1 sanity 分析 (48 行 e2e_bench_v1) — 错误推断 "INT8 比 FP16 慢", 险些写进 paper §C

### 2.1 一句话概括

`lat_e2e_mean_ms` = `lat_trt + lat_postproc`. postproc (NMS+decode FP32) 工作量随检测候选框数波动, **与 Q 维度无关**但有 ~1-2ms 噪声. 用 e2e lat 比 INT8/FP16 时, NMS 噪声会盖过 TRT engine 真实加速 (0.3-0.5ms), 导致反向误判.

### 2.2 支持证据

T1_base 案例:

| Q | lat_trt_ms | lat_postproc_ms | lat_e2e_ms |
|---|------------|----------------|------------|
| Q_fp16 | 2.75 | **4.29** | **7.04** ← 反向最快 |
| Q_int8_mm | **2.21** ← 真实最快 | 5.90 | 8.12 |

- TRT engine: INT8 比 FP16 快 0.54ms (符合常理)
- postproc: INT8 比 FP16 多 1.61ms (NMS 噪声, 跟 Q 无关)
- e2e: INT8 e2e 反向慢 1.08ms

修正后 TRT lat 比较 (8/8 triplet INT8 ≤ FP16):

```
INT8_mm / FP16 ratio (TRT lat):
T1: 0.80, T2: 0.94, T3: 1.00, T4: 0.87, T5: 0.92, T6: 0.88, T7: 0.89, T8: 0.95
```

### 2.3 失败链路

```
做 sanity 分析 用 lat_e2e_mean_ms 对比 Q 维度
        ↓
T1_base/T7 处看到 INT8 e2e > FP16 e2e
        ↓
错误推断 "INT8 quantize/dequantize 开销超过 INT8 加速"
        ↓
错误反思 "FP16 已饱和 HMMA, INT8 不再加速"
        ↓
险些写进 dataset_analysis.md (用户质疑后查证 TRT lat 才修正)
```

### 2.4 排除项

| 候选根因 | 排除证据 |
|----------|---------|
| INT8 真的慢 | TRT engine lat 8/8 triplet INT8 ≤ FP16 (ratio 0.80-1.00) |
| postproc 跟 Q 有关 | postproc 是 NMS+decode FP32, 跟 engine 精度无关. Q_fp16 vs Q_int8 postproc 差 1.6ms 是检测候选数 / cls score 分布噪声 |
| measurement noise | n_measure=80, p50/p99 已稳; postproc 在 4-6ms 间波动是 NMS workload 本身 |

### 2.5 解决方案

#### ✅ 方案 1 (主路径): 数据表只留 `throughput_fps`, lat breakdown 进 bench JSON

- **工程量**: 0 (drop columns + 改 make_row)
- **e2e_bench_v1 schema 精简 (2026-05-15)**: 41 → 31 列, drop 10 个 lat-相关列
  - dropped: `lat_e2e_{mean,p50,p99}_ms`, `lat_trt_{mean,p50,p99}_ms`, `lat_postproc_{mean,p50}_ms`, `speedup_{e2e,trt}_vs_baseline`
  - kept: `throughput_fps` (Pareto target, = 1000 / lat_e2e_mean)
- **使用规则**:
  - **paper §C / Pareto / LGB target**: 只用 `throughput_fps` (单一指标, 无多重共线性)
  - **Q/B 维度内部诊断 (problem-investigation, 非 dataset)**: 按需读 `models/e2e_cache*/<tag>_<Q>_bench.json` 的 `lat_trt_ms.mean` (clean Q signal)
- **理由**: 11 个 lat 列强相关 → LGB 特征归因混乱; postproc lat 是 NMS 噪声, 进数据表会污染 LGB; paper 表表头臃肿无意义

### 2.6 相关文件

- 修正记录: `dataset_analysis.md` §A.0+A.1 检查 #3
- 数据表: `paper_learning/2. AAAI最终故事/data/e2e_bench_v1.csv` (31 列)
- lat breakdown (按 anchor): `models/e2e_cache*/<triplet>_<Q>_bench.json`

## 问题 3 — 孤儿子进程时序攻击导致 AP eval 用错语义 engine

**发现日期**: 2026-05-15
**已解决日期**: 2026-05-15 (kill 全进程树 + 删 AP 结果文件后重测)
**影响范围**: A.1 phase1 中 T1_base/Q_mix_s2 anchor — 报 AP50=0.153 (实际 0.549, 偏差 40pp)
**直接后果**: dataset_analysis.md 检查 #4 "B × Q 强耦合" 故事建立在错误数据上, 已撤回

### 3.1 一句话概括

`pkill -f <parent_pattern>` **只匹配父进程命令行, 不杀子进程**. 孤儿 `e2e_eval_ap.py` 子进程在被 unlink 的"错语义" engine 文件 (FD 仍打开) 上继续跑, 写入污染 JSON. 后续重启进程的 `eval_ap()` 检查发现 JSON 已存在, "[ap cached]" 直接读取孤儿结果, 没跑自己的 AP eval.

### 3.2 支持证据

**3 次 AP eval 在同一 byte-identical engine 上的结果**:

| Run | 时间 | engine path | AP30 | AP50 | AP70 | n_samples |
|-----|------|-------------|------|------|------|-----------|
| 1 (孤儿) | 16:17 | T1_base_Q_mix_s2.engine (52.2MB, 旧路径已 unlink 但 FD 还在) | 0.187 | **0.153** | 0.079 | 1618 |
| 2 (rebuild+eval) | 16:35 | T1_base_Q_mix_s2.engine (52.2MB, 重建 byte-identical) | 0.643 | **0.549** | 0.377 | 1618 |
| 3 (GPU 0 重测) | 18:06 | 同 run 2 engine | 0.643 | **0.549** | 0.377 | 1618 |
| 4 (GPU 1 跨卡) | 18:06 | 同 run 2 engine | 0.643 | **0.549** | 0.377 | 1618 |

→ run 2/3/4 跨 GPU 一致到 0.0001 → engine 输出**完全确定性**, 真值 AP50=0.549. Run 1 的 0.15 是孤儿在**错语义** engine (build_secs=161s, engine=67.87MB, layer0+layer1 FP16) 上跑的结果.

### 3.3 失败链路

```
16:09  phase1-attempt-1 build T1_base/Q_mix_s2 错语义 engine (67.87MB)
16:14  attempt-1 bench 完, 启动 AP eval 子进程 (on 错语义 engine)
16:15  我 pkill -f a1_q_expand_pathB_phase1 杀父进程
       ⚠ AP eval 子进程 (e2e_eval_ap.py) 没匹配, 继续运行
16:15  我 rm T1_base_Q_mix_s2.engine — 文件 unlink, 但孤儿子进程 FD 还在, 继续读
16:15  phase1-attempt-2 启动
16:16  attempt-2 build T1_base/Q_mix_s2 正语义 engine (52.2MB)
16:17  attempt-2 bench 完成
16:17  attempt-2 调 eval_ap()
       ⚠ 同时孤儿子进程完成 (180s), 把 AP=0.15 (基于错语义) 写入 JSON
16:17  attempt-2 的 eval_ap() 检查发现 JSON 存在
       → 打印 "[ap cached]" 直接读取
       → AP=0.15 (孤儿污染) 进入 staging CSV
```

### 3.4 排除项

| 候选根因 | 排除证据 |
|----------|---------|
| INT8 GPU 非确定性 | run 2/3/4 跨 GPU AP 差异 < 0.0001, 完全确定 |
| 真实 B × Q 耦合 | 其他 7 个 triplet × Q_mix_s2 全部 AP 0.53-0.57, T1_base 修正后 0.549 完全符合, 没有 baseline triplet 独特崩塌 |
| 校准缓存污染 | 重 build (run 2) 清空 cache 重 calib, engine byte-identical → calib data 输出一致 |
| AP eval 脚本 bug | 同脚本同 engine 后续 3 次跑出一致 0.549 |

### 3.5 解决方案

#### ✅ 方案 1 (主路径): kill 全进程树 + 删 AP 结果文件再重测

- **工程量**: 0 (操作规则)
- **新规则**:
  - kill 用 `pkill -f -P <parent_pid>` 或 `pkill -g <pgid>` 或显式 `kill <pid>; pkill -f <subprocess_pattern>` 杀全树
  - 清理重测时必须删: engine + build.json + bench.json + calib.cache + **AP json** (`results/a1_q_expand/{tag}_{q_tag}_ap.json` + `results/.../ap_eval_*` 目录)
  - eval_ap() 函数内 "[ap cached]" 短路需加 timestamp/hash 校验, 验证 cached JSON 跟当前 engine 哈希匹配
- **数据修正**: e2e_bench_v1.csv T1_base/Q_mix_s2 行 AP30/50/70 已更新为 run 3 值 (0.643/0.549/0.377)
- **反思撤回**: dataset_analysis.md 检查 #4 原 "B × Q 强耦合" 结论已撤回

#### ⏸ 方案 2 (备选): eval_ap 函数加 engine 哈希校验
让 cached JSON 跟当前 engine 哈希校验匹配再使用. 工程量 ~30 min, 暂不投入 (方案 1 操作纪律够用).

## 问题 4 — ONNX explicit Q/DQ 破坏 TRT 残差块融合, 系统性 -23pp AP

**发现日期**: 2026-05-15
**已解决日期**: 2026-05-15 (root cause 通过 TRT verbose log diff 验证)
**影响范围**: A.1 phase2 全部 pt/Q-DQ 路径变体 (Q_int8_pt_wa / pt_wo / pc_via_qdq / pc_wa_full 等)
**最终决议**: 接受 phase2 = 8 个 Q_int8_pc_wo anchor (走 `--w-only` flag, 不依赖 ONNX Q/DQ). pt 变体在 ONNX Q/DQ 路径**不可信测**, 必须用 TRT C++ API set weight ranges 才能真测.

### 4.1 一句话概括

通过 ONNX QuantizeLinear/DequantizeLinear 节点注入 explicit precision 会强制 TRT 在每个 Conv 边界插 reformat, **打断 Conv+BN+Add+ReLU 残差块融合** — TRT default INT8 path 把整个残差块融成 1 个 INT8 IMMA kernel, ONNX Q/DQ path 退化为 65 个独立 Conv + 大量 FP32 中间结果 → 累积 23pp AP 损失.

### 4.2 支持证据 (TRT verbose log diff)

| 指标 | A: Q_int8_mm (TRT calibrator path, AP 0.78) | B: ONNX Q/DQ path (AP 0.55) | 差异 |
|------|--------------------------------------------|----------------------------|------|
| Unique fused Conv+X patterns | **391** | 292 | -25% |
| Total Conv fusion mentions | 2173 | 771 | -65% |
| INT8 mentions in log | 6420 | 1884 | -3.4× |
| Tactic explorations | 31360 | 6461 | -5× |
| Build log size | 56842 行 (8.6 MB) | 26330 行 (3.0 MB) | -54% |

A 探索的融合 pattern 包括完整的残差块, 如:
```
/backbone_m1/resnet/layer0/layer0.0/conv1/Conv + /backbone_m1/resnet/layer0/layer0.0/Add + relu_1/Relu
```
TRT 选 cuDNN CaskConvolution INT8 tactic 把 Conv+Add+ReLU 跑成一个 IMMA kernel.

B 的 Q/DQ 节点在 weight + activation 边界插 reformat, 大部分 Conv 只能单独 INT8 计算, **65 个独立 Conv** 全部 reformat 进出, 跟 BN/Add/ReLU 没法融合 → FP32 中间结果 → 误差累积.

### 4.3 失败链路

```
preprocess ONNX 加 Q→DQ 包裹每个 Conv weight + activation
        ↓
TRT 解析时识别 Q/DQ 节点 → 进入 explicit precision mode
        ↓
explicit mode 要求 Q/DQ 严格 enforce, 不允许 fusion 跨越 Q/DQ boundary
        ↓
Conv+BN+Add+ReLU 残差块在 ONNX 里 Conv 前后各有 Q/DQ, 中间 BN/Add 没有 Q/DQ
        ↓
TRT 无法把这串 op 看作 1 个融合块, 退化为:
   DQ → Conv (INT8) → Q → reformat → BN (FP32) → Add (FP32) → ReLU (FP32) → Q → DQ → 下一 Conv
        ↓
每个残差块插入 6+ reformat ops, 65 个 Conv = 大量 FP32 中间状态
        ↓
累积 FP32 quantization noise → AP -23pp (0.78 → 0.55)
```

### 4.4 排除项 (5 个 hypothesis 全部排除)

| 候选根因 | 排除证据 |
|----------|---------|
| Calibrator + Q/DQ 冲突 | --precision fp16 + no calibrator + ONNX Q/DQ 仍 0.549 |
| Activation Q/DQ 缺失 | 加完整 W+A Q/DQ (65 个 act Q/DQ) 仍 0.549 |
| Per-tensor weight 真崩 | per-channel via Q/DQ (跟 TRT default 同 granularity) 也 0.549 |
| Head Conv (cls/reg/dir) 量化损 logit | 排除 head Conv Q/DQ 后仍 0.550 |
| GPU 非确定性 / measurement artifact | 跨 GPU rerun 一致 (差 < 0.001) |

剩余 hypothesis (5: residual block fusion 破坏) 经 verbose log diff **量化验证**.

### 4.5 解决方案

#### ✅ 方案 1 (主路径): 不走 ONNX Q/DQ, phase2 收 8 个 Q_int8_pc_wo

- **工程量**: 0 (已完成)
- **核心**: Q_int8_pc_wo 通过 `m4_8_trt_build_bench.py --w-only` flag 实现 (在 TRT network 解析后 `layer.set_output_type(0, FP16)`), **保留 TRT default calibrator + 自动 fusion**, 仅强制 Conv 输出 FP16. 不走 ONNX Q/DQ.
- **数据**: 8 anchor 已并入 e2e_bench_v1.csv (T1-T8 × Q_int8_pc_wo), AP50 一致 0.528-0.556
- **角色**: paper §C "W-only INT8 是 mediocre 中间路径" 证据

#### ⏸ 方案 2 (备选, 未投入): TRT C++ API 直接改 weight ranges

工程量: 4-6h. 在 TRT network parse 后, 用 `IConvolutionLayer.kernel = quantized_weights` 或 `layer.set_input_range(...)` 直接 override weight 量化, 跳过 ONNX Q/DQ 路径. TRT 10 Python 部分 API 缺, 可能要 fork C++ binding. 仅在 paper §C 需要 per-tensor weight 真测时启动.

## 问题 7 — Pyramid Fusion AP 不敏感是 finetune-equilibrium artifact, 真崩溃点存在

Pyramid Fusion DAIR-V2X 任务 AP 看似不敏感 (跨 21 triplet std=0.031, 跨 6 Q std=0.005) **是 finetune-equilibrium artifact**. 实测 raw pruned (0 epoch finetune) 即使 14% 温和剪枝也**完全崩溃 (AP50=0)**, 直到 finetune 后才能恢复.

### 7.4 修订后的真相 (推翻之前的 claim)

**之前错的 claim**: "Pyramid Fusion 协同任务对 backbone 加速 robust, 89% prune + INT8 仅损 1-3pp AP, 是 fusion 任务的 inherent property"

**真相**:
1. **AP 极度敏感** — 同 backbone weights 不做 finetune 就完全崩 (即使 14% 温和 prune)
2. **csv 中"AP 不变" 是 finetune-equilibrium artifact** — 每个 triplet 都被 25-47 epoch HEAL finetune 到稳定
3. **Fusion redundancy hypothesis 假设不成立** — Pyramid Fusion 多 agent 融合不能 compensate 未 finetune 的 broken backbone
4. **Finetune (per-config 25-47 epoch) 是 AP 稳定的真正 driver**, 不是 fusion 本身

### 7.5 对 paper §C 的含义

**修订 framing**:
- ❌ 不能 claim "fusion 任务 inherent robust to compression"
- ✅ 真实 claim: "structural prune + per-config finetune (≥25 epoch) 可恢复至 baseline-1pp 内"
- ✅ "Finetune budget 是加速 framework 的硬约束" — 实测 2 epoch 恢复 75%, 47 epoch 恢复 98%

**加速 framework 修正**:
- 之前: B/Q 维度搜索空间 = (T1-T22) × (Q_fp32 to Q_int8_pc_wo). 隐含假设: 每点都 finetune
- 修正: 应加 **finetune_epochs ∈ {0, 2, 5, 25, 47}** 作为新搜索子维度
- Trade-off: 0 epoch → AP 崩 (不可用); 2 epoch → AP -14pp (部分崩); 47 epoch → AP 几乎完美但 finetune cost ~3h/config

**论文核心 narrative 调整**:
- "为什么需要 LGB predictor?" — 因为评估每个 (B, Q, D) 组合需要 ~3h finetune + AP eval, 全 sweep 不可行
- Predictor 的实用价值: 跳过 finetune 直接预测 final AP (假设每点都 finetune 到 equilibrium)
- 这是 **真实可信** 的加速 framework motivation

### 7.6 补充实验 — T22_raw + Q_int8_mm (2026-05-20)

验证 "quantization 是否在 broken backbone 上引入额外退化":

| 配置 | AP50 |
|---|---|
| T22 raw (0 FT) + Q_fp32 | 5e-8 |
| T22 raw (0 FT) + **Q_int8_mm** | **6.8e-8** |

→ **Quant 与 broken model 完全 orthogonal**. 两者都已在零地板. Quantization 不会救 broken model, 也不会让它更差.

### 7.7 Phase 1 Pilot 实测 (AP 不敏感解决方案 plan, 2026-05-21)

3 个 prune 级 (14% / 57% / 89%) × 5 FT 档位 (4/6/8/10/15) = 15 个 fresh AP eval (n=1789).

**结果**: 任何 FT∈[4,15], AP[T11_p14]-AP[T22_p89] gap < 0.025, **无 sweet spot 让 B 维度 AP variance ≥ 0.05**.

| FT | AP[T11] | AP[T17] | AP[T22] | std | gap |
|---|---|---|---|---|---|
| 4 | 0.549 | 0.552 | 0.527 | 0.011 | +0.023 |
| 6 | 0.539 | 0.501 | 0.530 | 0.016 | +0.009 |
| 8 | 0.516 | 0.514 | 0.500 | 0.007 | +0.015 |
| 10 | 0.520 | 0.528 | 0.531 | 0.005 | -0.011 |

详见 `/tmp/a9_pilot/eval/phase1_finding.md` + `spread_table.csv`.

**核心发现 (反直觉但论文级)**:
- Pyramid Fusion + DAIR-V2X 在 backbone capacity 上**显著 over-parameterized** (T22 仅 1.9% backbone params 即可恢复)
- 89% prune + FT=4 → AP=0.527 (baseline-2.2pp), FT=10 反而 AP=0.531 ≥ T11
- **真崩溃点只存在于 FT=0** (raw pruned weights)

### 7.8 最终结论 (paper §C framing, plan v1 时期)

**真实搜索空间中, 唯一 AP-sensitive 维度是 finetune budget**:

```
AP50 vs (B, Q, D, finetune_epochs):
  - finetune = 0:        AP ~ 0  (任意 B, Q, D 都崩)
  - finetune ≥ 4 epoch:  AP ~ 0.54 ± 0.02 (任意 B, Q, D 都基本恢复 baseline)
```

**对加速 framework 含义**:
1. **B/Q/D 三个 dim 对 AP 的影响 < ±2pp** (在 finetune-equilibrium 下)
2. **finetune_epochs 是真正的崩溃 axis**: 0 → 0, 2 → 0.4, 4 → 0.52, 6+ → 0.54+
3. **预测器价值**: 跳过 finetune 直接预测 final AP (假设 finetune ≥ 4 epoch). 否则 AP 完全不可预测 (要么 0 要么 0.54)
4. **真实搜索目标** = maximize speedup subject to (finetune cost ≤ budget AND finetune ≥ 4 epoch)

### 7.11 FT 维度二难: FT=8 抹平 vs FT=4 噪声 ≈ 信号 (2026-05-26)

**§7.10 修订后 deployment-time AP 跨度仅 0.117 (std=0.037), B/Q 影响只 ~6pp**. 用户审查: "**是不是 FT=8 选太大了, AP 都被抹平了**?"

跨 FT 实证对比 (合并 plan v2 + v3 数据):

| FT | N (含所有 Q × triplet) | mean | **std** | range | 说明 |
|---|---|---|---|---|---|
| 0 | 9 (全 AP=0) | 0.000 | 0.000 | 0.000 | 没 finetune, 任何 (B,Q) 都崩 |
| **2** | 12 | 0.181 | **0.148** | 0.390 | 跨度大但全 collapse 区 (AP < 0.4) |
| **4** | 8 (含 5 seed × p97) | 0.388 | **0.091** | 0.292 | 中等跨度 |
| **8** | 15 (unique B×Q) | 0.534 | **0.037** | 0.117 | 已收敛, AP 抹平 (§7.10) |
| **15** | 3 (仅 FP32) | 0.543 | **0.012** | 0.026 | over-converge, 跨度极小 |

**关键约束 — FT=4 的噪声地板** (Phase 1.3 实证):
- 同一 anchor (T_g8_p97 + FT=4) 5 个 seed → AP = 0.45/0.41/0.36/0.33/0.20
- **σ_noise = 0.096** ≈ FT=4 总 std (0.091)
- **R²_ceiling = 1 - σ²_noise / σ²_total ≈ 1 - 0.096²/0.091² ≈ -0.1** (噪声大于信号!)
- 含义: 即使 perfect predictor, 在 FT=4 数据上 R² 也几乎不可能正

**FT 选择二难**:

| FT | spread (信号) | noise | R²_ceiling | 可用? |
|---|---|---|---|---|
| FT=4 | 大 (std=0.091) | 大 (σ=0.096) | **≈0** | ❌ predictor 不可学 |
| FT=8 | 小 (std=0.037) | 小 (σ <0.02 估) | 0.7+ | ⚠️ R² 看似可学, 但跨度本身小, 信号有限 |
| FT=15 | 极小 (std=0.012) | 极小 | 0.9+ | ❌ 信号几乎为 0, 学到的也无用 |
| **FT=6 待测** | ? | ? | ? | **未验证, 可能是 sweet spot** |

**对 framework 设计 implication**:
- 不存在 "选个 FT 就能让 (B,Q,D) → AP 强可学" 的简单解
- FT=4 信号被噪声淹没 → predictor 不能学
- FT=8 信号小 → predictor 能学但精度有限 (MAE 0.012 vs trivial 0.034 = 65% 改善, 绝对值小)
- 真要论"AP-sensitive 搜索", 物理上可能就这么弱
- **Paper §C 不应宣称 "AP-aware 搜索成功"**, 应诚实承认 "deployment 时 AP 弱信号 + capacity-edge 高噪声"

**已完成实验** (用户指示 Option A, 2026-05-26): 45 anchor eval (3 triplet × 5 Q × FT∈{4,6,8}) + FT=4/FT=6 各 5-seed 噪声实测.

**实测结果**:

| FT | N (B×Q) | mean | **std (信号)** | **σ_noise (5-seed)** | **R²_ceiling** | LGB 实跑 R² | 实跑/ceiling |
|---|---|---|---|---|---|---|---|
| **4** | 15 | 0.430 | **0.073** | **0.096 (实测)** | **-0.73** ❌ | 未跑 (无意义) | — |
| **6** | 15 | 0.521 | **0.042** | **0.0234 (实测)** | **0.69** ✅ | **0.25** | 36% (under-realized) |
| **8** | 15 | 0.536 | **0.035** | ~0.020 (估) | 0.67 | **0.56** | 84% (well-realized) |

**关键 5-seed noise 数据**:
- FT=4: AP = 0.20, 0.33, 0.36, 0.41, 0.45 (range 0.25, σ=0.096) — **FT=4 训练根本不收敛, 不同 seed 跑出完全不同模型**
- FT=6: AP = 0.52, 0.52, 0.55, 0.56, 0.57 (range 0.055, σ=0.023) — **训练已稳定, 4× 改善 vs FT=4**
- FT=8: 未测但推断 σ<0.02 (基于 FT=6 已稳定 + epoch 27 更收敛)

**新发现 — FT=6 R²_ceiling 略高于 FT=8**:
- FT=6 ceiling = 0.69, FT=8 ceiling = 0.67 (差不多, FT=6 微弱优势)
- 但 LGB 实跑: FT=6 R²=0.25 (35% of ceiling), FT=8 R²=0.56 (84% of ceiling)
- FT=6 数据有 fold variance 大 (per-fold R²: [-1.10, -0.58, 0.99, 0.99, 0.97])
- **解释**: FT=6 训练尚未完全收敛, (B, Q) 间的 AP 模式比 FT=8 更"乱", LGB 在小数据 (N=15) 上学不到稳定模式

**FT=4 + p97 + int8_ent = 0.259 真触发 strict path A** (deployment-feasible FT 区, 跌破 0.30 阈值, 不是 plan v3 §1.1 FT=0/2 的 trivial 崩溃).

**对 framework 设计 implication**:
- **FT=4 物理上不可学**: 噪声 > 信号, 无任何 predictor 可以学
- **FT=6 是 "best ceiling but worst realized"**: 理论 ceiling 略高于 FT=8, 但小数据上 LGB 实跑 R² 反而低 (高 fold variance) — N 增加可能改善
- **FT=8 是 "deployment 现实最优解"**: ceiling 略低但 LGB 真能达到 84%
- 推论: paper §C 应当 **deployment 推荐 FT=8**, FT=4 标 warning, FT=6 留作 "future work 如果 N 增加可能更好"

详见 [`stats_v3/16_ft_sweep_comparison.png`](./stats_v3/16_ft_sweep_comparison.png) (3-panel) + [`stats_v3_ft6/`](./stats_v3_ft6/) (FT=6 完整 14 张 PNG, FT=8 视图保留在 stats_v3/).

### 7.12 e2e_bench_v1.csv 4704 anchor 全空间 AP 诊断 (2026-05-27)

**起因**: 出 `stats_v3_bench/` 14 张图后, D1 5-fold R²=0.909 的 PASS 标记看起来碾压 plan v3 的 0.56. 用户追问"除 FT 不统一外最大问题是什么", 深查后发现 R²=0.909 是**数据泄露虚高**, 真实信号跟 plan v3 同级.

#### 7.12.1 dataset 真实结构 (跟 4704 size 的初印象不符)

```
4704 = 21 triplet × 7 Q × 32 D
 ├ 147 unique (B, Q) cells     ← 这是 AP 唯一信息单元
 └ 每 cell 在 32 D 上复制       ← 对 AP 物理上零信号 (schema §十一 已写)
```

**D 维度对 AP 零信号实测** (147 cells, 每 cell ~32 D 复制):

| 指标 | AP cell-内 std | lat cell-内 std |
|---|---|---|
| median | **0.000** | 1.97 ms |
| mean | 0.014 | 3.83 ms |
| cell std > 0 占比 | 32/147 (22%) | **147/147 (100%)** |

例: T1_base + fp32 在 32 D 上, lat 跨 9.94 → 19.40 ms (~2×), **AP 几乎全部恒等 0.549**.

→ AP 视角下 4704 anchor 的**有效样本量 = 147**, D 是 32× 复制.

#### 7.12.2 R²=0.909 是 D 复制 fold-leakage 产物

5-fold split 同 (B,Q) cell 被打散 → train 看 (T22, fp32, D5)、test 看 (T22, fp32, D6), AP 完全一致 → LGB 用 D one-hot **memorize**.

不同 split 重训对照:

| Split 策略 | R² mean | per-fold |
|---|---|---|
| **现 D1 random 5-fold** (D 复制随机打散) | **0.909** | [0.94, 0.89, 0.92, 0.91, 0.88] |
| **GroupKFold by (triplet, q)** (D 复制全进同 fold) | **0.375** | [0.61, **−0.62**, 0.83, 0.19, 0.86] |
| **dedup 到 147 unique cell, KFold** | **−1.18** | [0.83, 0.63, **−6.13**, **−1.78**, 0.55] |

GroupKFold 跌 R² 0.53; 147 dedup 后**比直接预测 mean 还差**, 完全不能泛化到新 (B,Q) cell.

#### 7.12.3 4584 有效 AP 信号 ≈ plan v3 15 anchor

去掉 collapse 取 plateau-only (AP ≥ 0.50, N=3998):

| Dataset | N | LGB 5-fold R² | std |
|---|---|---|---|
| plan v3 FT=8 deployment | 15 unique B×Q | 0.558 | 0.037 |
| **bench plateau-only** | 3998 anchor | **0.572** | 0.032 |

**数据量 200×, R² 几乎一样**. plateau 内每个 Q 的 std 都 ≤ 0.04 (FT-equilibrium 抹平), bench 多出的 anchor 是同分布重复, 不带新信息.

#### 7.12.4 int8_ent 崩塌不可学

```
int8_ent 在 21 triplet 的 AP (D-平均):
  10 triplet 严重崩 (AP 0.007–0.282): T14, T18, T10, T20, T15, T3, T16, T8, T1, T4
  10 triplet 中度劣化  (AP 0.40–0.50): T19, T21, T11, T7, T22, T2, T6, T17, T5, T12
   1 triplet 不崩       (AP 0.523):    T13
```

崩 vs 不崩跟 plane 大小**无单调关系**:
- T14_p36 = (16, 16, 256), AP_ent = **0.007** (严重崩)
- T13_p29 = (32, 32, 256), AP_ent = **0.523** (不崩) — planes 几乎相同, AP 差 0.52

这说明 entropy calibrator 选错 scale 是**校准曲线随机偶发性**, 不是结构性. LGB 从 (planes, Q, D) 学崩不崩 ≈ 抛硬币 → D3 hold-int8_ent MAE = **0.248** (predictor 直接 fallback 到 plateau mean 0.55).

#### 7.12.5 4704 anchor 的 rationale 错位 (lat ≠ AP 视角)

回顾 `数据集制作_plan.md` v1.4 §〇.5 + §五:

> Stage 1 实测: f_AP_full R²=0.989 ✅ (实际是 D 复制泄露), f_lat R²=0.729 ❌ 卡上限
> 问题 6 诊断: TRT 内核选择噪声 + D 网格稀疏
> Stage 2e: 扩 D 子维度 4 → 32 cell, 期望 f_lat R² 0.73 → 0.85+

**4704 是为 lat predictor 设计的, 不是为 AP**:
- f_lat: random R²=0.471, GroupKFold by (B,Q) R²=0.464 (几乎不掉, D 是真信号), D1-only N=147 R²=0.177 (跌 0.30)
- f_AP: random R²=0.909, GroupKFold R²=0.375 (跌 0.53, D 是 leakage)

`数据集制作_plan §〇` 表格 "🔴 致命缺口: AP × D 维度联测真值 = 0" 的设计假设错: D 物理上不影响 AP, 联测**不必要**.

#### 7.12.6 综合结论

**plan v3 §7.10 结论 "deployment R²=0.56" 仍是 AP predictor 真实天花板**. bench 4704 的 R²=0.909 是统计学幻觉, 用 GroupKFold 校验后回到 0.37; plateau-only 子集回到 0.57 ≈ plan v3 15 anchor.

**根本结构限制 (跟 FT 不统一无关)**:
1. **D 对 AP 物理零信号** → 任何含 D 维度的 dataset 在 AP 视角下都有 32× over-sample
2. **AP 分布双峰** → 信号空间被压缩为 binary (healthy vs entropy-collapse), 4584 个数据点其实是 2 个 mode + 噪声
3. **entropy 崩塌随机** → 跟特征无单调关系, predictor 不可学 (但可规则前置过滤)

**对 paper §C 的硬约束**: 想突破 R² 0.56-0.57 的 plateau 内信号上限, 不能靠扩 D 维度或多 triplet, 必须:
- 引入更敏感的 Q variant (per-channel × per-stage 组合, 比当前 7 个粒度更细), 或
- 在 fully-finetune-equilibrium 之外开放 FT 子收敛区 (但 FT=4 已证噪声 > 信号)

详见 [`stats_v3_bench/`](./stats_v3_bench/) (14 PNG + 中文说明) + `e2e_bench_v1_sanity_report.md` (5 anchor rerun |Δ AP50| ≤ 0.0004 → csv AP 列已 sanity 通过).

### 7.13 ⚠️ 设计纪律 — **FT 是固定常量, NOT 搜索维度** (2026-05-27)

> **来历**: 用户在 2026-05-25 修订 plan v3 §7.10 时已明确, 但写在 "修订原因 #1" 隐藏位置, 后续 plan v4 设计仍出现 "FT sweep" 违规. 本节升为**顶级纪律**, 任何后续 plan / experiment / predictor 设计都必须遵守.

#### 7.13.1 原则

> **FT (finetune epoch) 是 deployment 配置, 不是 framework 搜索决策变量.**
> 一旦确定 FT* (典型 = 8), **整个 dataset / Phase A 验证 / Phase B 解决 / Phase D 验收 全部用同一 FT***, 不允许在实验内变 FT.

具体含义:
1. **Dataset 制作**: 所有 anchor 用同一 FT epoch ckpt, csv 写 `finetune_epochs` 列值全相同
2. **LGB 特征**: `ft` **不进**特征向量 (会导致 trivial R² 虚高, 详 §7.10)
3. **Phase A 因素归因**: 只在 **B × Q × (D)** 上做 factorial, **不在 FT 上做 sweep**
4. **解决方案 (Phase B)**: 选用 B 扩 / Q 扩 / B×Q 网格, **不选 "改 FT epoch"** 作为解决路径
5. **σ_noise 控制**: FT* 选定后, 测一次该 FT 的 σ_noise (5-seed), 作为后续所有阈值基准

#### 7.13.2 为什么 plan v1/v3/v4 反复违规?

| 违规 | 当时理由 | 真实问题 |
|---|---|---|
| plan v1 §1.1: "FT sweep 找 FT* sweet spot" | 假设 FT 影响 AP plateau | 跑完发现 [4,15] 全 plateau → 早停 |
| plan v3 §1.1 FT=0/2 underfit anchor | 给 collapse boundary warning 数据 | 用户驳: FT=0/2 不是 deployment 区, 不该进 LGB |
| plan v3 §7.11 FT=4/6/8 sweep + LGB v7 ap | 找"sweet spot" | 用户驳: 数据需要 unique FT, FT=8 已经定了 |
| plan v4 (本) §1.2 A.1 FT main effect | "归因 FT 是否主导" | 同样违规: FT 不是搜索维度, 无需归因 |

**根因**: 把"FT 是 dataset 设计参数 (一次性确定)" 跟 "FT 是 search axis (持续探索)" 混淆.

#### 7.13.3 当前 FT* = 8 (建议锁定值)

来源:
- σ_noise 实测: FT=4 σ=0.096 (NOT learnable), FT=6 σ=0.023, FT=8 σ<0.02 (估)
- LGB ceiling 实测: FT=8 R²=0.56 (84% of ceiling 0.67), FT=6 R²=0.25 (high fold variance)
- plan v3 §7.10 deployment 标准: FT∈{8, 15}, 取 8 是 deployment-realistic 最小值

**绝对 epoch 数对照** (架构 baseline 不同, **修正 2026-05-27**):
- **g32 baseline epoch = 23** (HEAL stage1 默认 bestval_at23), FT=N → epoch 23+N
- **g8 baseline epoch = 19** (plan v2 自训 baseline_g8), FT=N → epoch 19+N
- **g32 baseline triplet** (T1_base, 无 prune): 直接用 `net_epoch_bestval_at23.pth` (无 FT 概念)
- **g32 Track A v2 pruned** (T3/T5/T7/T8/T10-T22, 17 个): `models/dataset_a_cache/ft_*/net_epoch31.pth` (= **epoch 31** = baseline 23 + FT 8)
- **g32 HEAL 官方 pruned** (T2/T4/T6): 官方只到 epoch 25 (= FT 2), **需补训** 25→31
- **g8 pruned triplet** (T_g8_p87/p93/p97): `models/dataset_a_cache_g8/ft_T_g8_p*/net_epoch27.pth` (= **epoch 27** = g8 baseline 19 + FT 8)

注意: g8 跟 g32 是不同 architecture (resnext_groups + width_per_group 不同), 所以 g8 triplets 的 baseline epoch 不是 19. 实际 plan v2 §0.3 用 g8 baseline 训了 30 epoch, 再 prune 后 finetune. **g8 的 "FT=8" = g8 baseline epoch 19 + 8 = epoch 27 of g8 ckpt**, 跟 g32 的 epoch 27 数值上相同, 但**起点 baseline 不一样**.

跨架构 FT 对齐前提: 都用 epoch 27 (各自 architecture 内的 baseline+8). 这是 FT 时间预算对齐, 不是绝对 wall-clock 对齐.

#### 7.13.4 选定 FT* = 8 之后的具体约束

| 实验 | 约束 |
|---|---|
| Pre-Phase 0 | 用 1-2 个代表 anchor (e.g., T_g8_p97 + FT=8) 跑 5-seed 实测 σ_noise. 不通过 (σ > 0.05) → 换 FT* 重测 |
| Phase A 归因 | 跨 24 triplet × 5-7 Q × FT=8 固定, 不变 FT |
| Phase B 解决 | 扩 B 或 Q 或 B×Q grid, 但都在 FT=8 下 |
| Phase C 采集 | csv 写入 `finetune_epochs=8` 给所有 anchor |
| Phase D LGB | 特征里**不包含** ft 字段 |
| Phase E lat | 同样 FT=8, 跟 AP 一致 (lat 跟 FT 没关系, 但 ckpt 必须一致) |

#### 7.13.5 该原则永久生效

任何新 plan / experiment 启动前自检:
- [ ] 是否所有 anchor 用同一 FT epoch?
- [ ] LGB 特征是否不含 `ft`?
- [ ] 解决方案路径是否避开 "变 FT" 选项?
- [ ] csv 是否记 `finetune_epochs` 列?

任一违规 → 设计错误, 重新设计.
