# 实验纪律 (每次实验前必读)

> 起因: 一个 session 内连续 3 次把"看似合理的物理解释"当结论, 三次都被用户怀疑后才查到真相. 详见 `问题.md` 问题 2/3/4.

## 数据采集前

1. **kill 全进程树**: `pkill -f <parent>` 只杀父. 用 `pkill -g <pgid>` 或显式杀子进程. 清理时必须删 engine + build.json + bench.json + calib.cache + **AP json + ap_eval/ 子目录**.
2. **cache 短路必带哈希校验**: `if cached.exists():` 短路前, 比 cached 结果跟当前 engine/输入的 hash, 否则可能读到孤儿进程污染的旧结果.

## 数据分析时

3. **观察 ≠ 机制**: 先报"X 比 Y 慢 1.7×"这种纯观察事实, 机制解释一律标 hypothesis, 经验证才升级为结论.
4. **每个机制声明必须有 1 个反例测试**: 想声明"INT8 比 FP16 快是因为 IMMA tensor core" → 先用 FP32 测一遍, FP32 也快/慢说明 tensor core 不是原因. 想声明"channel 32 对齐" → 找一个 16/8 对齐反例.
5. **指标多列时确认对比口径**: lat 有 e2e/trt/postproc, AP 有 30/50/70 + n_samples — 用哪一列比? 选错列会得反向结论 (问题 2).

## 数据落地时

6. **可疑数据点必须 rerun**: 单一极端值 (AP=0.15 在一片 0.55 中) 不直接信, 同条件 rerun 2 次确认确定性.
7. **机制声明在 paper 主张里**: 加 caveat "经 N 次 rerun 一致 + 经反例验证". 没验证的不写进 §C 主表.

## 自检短路 (开始每个分析前自问)

- [ ] 我用的对比口径是哪一列? 跟问题域真的匹配吗?
- [ ] 我的机制假设, 有没有 1 个该 fails 的反例? (找最接近的反例 triplet)
- [ ] 上一次 pkill/cleanup 后, 有没有孤儿子进程? 有没有过时 cache?
- [ ] 这个极端值, rerun 过吗?
