# Pyramid Fusion 模态总览

> **范围**：HEAL Pyramid Fusion 框架 (`opencood.models.heter_pyramid_collab` /
> `heter_pyramid_single`) 中所有可用 modality 的 encoder 类型、网络结构、配置、
> ckpt 位置和"voxel-pooling"语义对照。
>
> **来源**：`opencood/models/heter_encoders.py` (300 行, 4 个 encoder 类)，
> stage1/stage2 ckpt configs，及 OPV2V `opv2v_4modality.json` modality assignment。

## 一、四个 modality 的对照表

HEAL 在 OPV2V 上预训练了 4 个 modality（m1-m4），每个 modality 一个独立的 encoder：

| Modality | Sensor | Encoder 类型 (`core_method`) | 参数量 (encoder) | 主要计算 | 已训练 ckpt |
|---|---|---|---|---|---|
| **m1** | LiDAR | `point_pillar` → `PointPillar` | 0.13 M | PillarVFE + Scatter | `stage1/Pyramid_m1_base_2023_08_14_04_28_12` ✓ |
| **m2** | Camera (4×) | `lift_splat_shoot` → `LiftSplatShoot` | 4.5 M (含 EfficientNet-b0) | EfficientNet + LSS voxel_pooling | `stage2/m2_alignto_m1` ✓ |
| **m3** | LiDAR | `second` → `SECOND` | ~5 M | MeanVFE + 3D sparse conv + HeightCompression | `stage2/m3_alignto_m1` ✓ |
| **m4** | Camera (4×) | `lift_splat_shoot` → `LiftSplatShoot` | 4.5 M | 同 m2 (不同分辨率/depth bins) | `stage2/m4_alignto_m1` ✓ |

> 注：HEAL 的设计哲学是**多模态共享 pyramid_backbone + heads**，每个 modality 只有
> 独立的 encoder/backbone/aligner（前置感知通路），然后通过 aligner 把各模态特征对齐到统一 BEV。

## 二、四种 encoder 的网络结构

### 2.1 m1: `PointPillar` (LiDAR, 经典)

```
点云 (N, 4)
  ├─ Voxelization (SpVoxelPreprocessor, dataset 端)
  │    └─ voxel_features (M, 32, 4)  voxel_coords (M, 4)  voxel_num_points (M,)
  ├─ PillarVFE
  │    ├─ 计算 f_cluster (相对 pillar 中心), f_center (相对 voxel 中心)
  │    ├─ Linear (10 → 64), BatchNorm1d, ReLU
  │    └─ torch.max(x, dim=1)  ← pillar 内 max-pool (32 点 → 1 个 feature)
  │         输出 pillar_features (M, 64)
  └─ PointPillarScatter
       └─ spatial_feature[:, indices] = pillars  ← 把 M 个 pillar 放回 BEV
            输出 BEV pseudo-image (B, 64, 200, 704)
```

**关键算子**：max-pool over points (PFN) + scatter to BEV grid。

### 2.2 m2/m4: `LiftSplatShoot` (Camera, LSS)

```
图像 (B, N=4, 3, 384, 512)  ← 4 个相机
  ├─ CamEncode (EfficientNet-b0)
  │    ├─ get_eff_features → (B*N, 320, 48, 64)
  │    ├─ image_head → x_img (B*N, camC=128, fH=48, fW=64)
  │    ├─ depth_head → depth_logit (B*N, D=48, 48, 64)
  │    └─ outer-product: new_x = depth.unsqueeze(1) * x_img.unsqueeze(2)
  │         输出 (B, N, D=48, fH=48, fW=64, C=128)
  ├─ get_geometry (像素 → ego 坐标)
  │    └─ frustum × inverse(post_rots) × intrins^-1 × rots + trans
  │         输出 geom_feats (B, N, D, fH, fW, 3)
  └─ voxel_pooling (LSS 核心算子, "splat")          ◄────────── 此处即调研所说瓶颈
       ├─ flatten + quantize 到 BEV 网格
       ├─ 过滤范围外
       ├─ ranks.argsort()
       ├─ QuickCumsum.apply (同格子 feature 累加)
       └─ 散射到 final (B, C, Y, X) BEV grid
            输出 BEV feature (B, 128, 256, 256)
```

**关键算子**：`voxel_pooling` 中的 `QuickCumsum.apply` — 这是一个自定义 autograd
function，做 frustum 点 → BEV 网格的 splat+sum，**memory-bound, 无 conv**。

### 2.3 m3: `SECOND` (LiDAR, sparse 3D conv)

```
点云 (N, 4)
  ├─ Voxelization
  ├─ MeanVFE
  │    └─ 对每个 voxel 内的点做 mean (voxel-pooling, 算子级别)
  │         输出 voxel_features (M, 4)
  ├─ VoxelBackBone8x  (3D sparse convolution, spconv)
  │    └─ 5 个 spconv stage, 下采样到 1/8
  │         输出 sparse feature (M', C, D', H', W')
  └─ HeightCompression
       └─ 把 Z 维度 reshape 进 C 维度
            输出 BEV feature (B, C', H/8, W/8)
```

**关键算子**：3D sparse convolution (依赖 `spconv` 库)。

## 三、"voxel-pooling" 在四个 modality 里指什么

**这是常见混淆点**——同一个词在不同 encoder 里指完全不同的操作：

| Modality | 是否有"voxel-pooling" | 它在指什么 | 文件:行 |
|---|---|---|---|
| **m1 (PointPillar)** | 类似操作 (不叫这名) | `torch.max(x, dim=1)` 对 pillar 内 32 点取 max | `pillar_vfe.py:46` |
| **m1 (PointPillar)** | 类似操作 (不叫这名) | `PointPillarScatter` 把 pillar 散射到 BEV | `point_pillar_scatter.py:65` |
| **m2/m4 (LiftSplatShoot)** | **✓ 真正叫 `voxel_pooling`** | LSS lift-splat-pool, 把 frustum 点 splat 到 BEV 格子, 同格子 feature 累加 | `heter_encoders.py:161` |
| **m3 (SECOND)** | 类似操作 (MeanVFE 内部) | 对 voxel 内的点取 mean (而非 max) | `mean_vfe.py` |

**调研所说"大部分耗时在编码层的 voxel-pooling"专指 m2/m4 的 LSS `voxel_pooling`**。
LiDAR 路径 (m1/m3) 的"voxel pooling"是 pillar/voxel 内部的 max/mean 聚合，**算量小，不是瓶颈**。

> HEAL 的两阶段训练：
> - **stage1**: 用一个主模态 (m1 = PointPillars) 训出基础 pyramid_backbone + heads
> - **stage2**: 冻结 pyramid_backbone + heads，**只训新模态的 encoder + backbone + aligner**，
>   让新模态"对齐"到 m1 的 BEV 特征空间

## 五、m1 vs m2 e2e 耗时对比（实测）

详细分段实测见 `分段耗时实测_v1.md`，这里只给总结：

| 阶段 | m1 (LiDAR PointPillars) | m2 (Camera LSS) |
|---|---|---|
| encoder 总耗时 | **3.0 ms** | **128.6 ms** (含 LSS voxel_pooling 116ms) |
| backbone | 2.1 | 0.6 |
| aligner | 0.02 | 0.56 |
| pyramid_backbone | 14.5 (forward_collab) | 4.1 (forward_single) |
| shrink + heads | 3.4 | 0.75 |
| **forward 小计** | **23.0** | **134.8** |
| postproc (含 NMS Shapely) | 74.6 | ~70 (估算, 同 m1) |
| **e2e** | **~98** | **~205** (估算) |

**关键发现**：m2 camera 比 m1 LiDAR e2e 慢 **~2×**，慢的差异**几乎全在 LSS 的 `QuickCumsum.apply` 一行（116ms）**。

## 六、对加速方案的影响

| modality | 主要瓶颈 | 推荐加速方案 |
|---|---|---|
| **m1 (LiDAR PointPillars)** | NMS (72ms, Shapely) > pyramid_backbone (14ms) | P0: MMCV `nms_rotated_cuda` (CUDA NMS) |
| **m2/m4 (Camera LSS)** | **LSS `QuickCumsum.apply` (116ms)** > NMS > CamEncode | **必须替换 `QuickCumsum` 为 BEVPoolv2 CUDA kernel** (mmdet3d / NVIDIA-AI-IOT) |
| **m3 (LiDAR SECOND)** | (未测) 推测：spconv 3D backbone | TRT spconv plugin 或换稠密 BEV backbone |

调研所说"剪枝到 30% 加速不明显"的根本原因：**LSS 的瓶颈是 memory-bound 的 cumsum，不受卷积参数量影响**。剪 EfficientNet 到 30% 只能省 cam_encode 那 8 ms 的一部分，对 116ms 的 QuickCumsum 完全无影响。
