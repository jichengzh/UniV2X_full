## 三、关键结论

### 3.1 NMS 是绝对主因

`opencood/utils/box_utils.py:693-738` 的 `nms_rotated`：

- **`.cpu().detach().numpy()` GPU→CPU 同步**
- **`convert_format` 构建 Shapely Polygon 列表**
- **Python while 循环 + Shapely `box.intersection(b).area / box.union(b).area` 的 O(N²) IoU**

是纯 CPU + Python 实现，**不是 CUDA kernel**。p99=176 ms 的高方差证实候选框数量主导（N² 复杂度）。

### 3.2 CNN 在 forward 范围内是主体（98%）

| forward 内部分解 | mean (ms) | 占 forward 23ms |
|---|---|---|
| encoder + backbone + aligner | 5.15 | 22.4% |
| pyramid_backbone | 14.45 | 62.8% |
| shrink + heads | 3.39 | 14.7% |
| **CNN 合计** | **22.99** | **~100%** |

**剪枝/量化** 在 forward 范围内有效（能省 5-10ms），但在 e2e 范围被 NMS 73% 拖死。

### 3.3 之前文档中需修正的数据

| 之前文档说 | 实测真实值 |
|---|---|
| NMS 占 e2e 60% | **NMS 占 e2e 73%** |
| pyramid_backbone 占 9% (= 3.3 ms) | **pyramid_backbone 占 15% (= 14.45 ms)**, 之前 3.3 ms 是 ONNX 单代理 dummy export |
| e2e baseline = 35.31 ms FP32 (M4.6.0) | **e2e 真实 = 98.37 ms FP32**；35.31 ms 只是 forward, 漏算 postproc |

## 四、加速优先级（按 ROI 排序）

| 优先级 | 方法 | 攻击对象 | 节省 | e2e 加速 |
|---|---|---|---|---|
| **P0** | MMCV `nms_rotated_cuda` 替换 Shapely NMS | NMS 71.69 ms | → ~1 ms | **98 → 27 ms = 3.6×** |
| P1 | UPAQ-style pruning + INT8（仅路侧 RSU） | encoder+backbone 5 ms | → 2.5 ms | (路侧单 agent 2×) |
| P2 | pyramid_backbone INT8 + 32 对齐 channel prune | pyramid 14 ms | → 9 ms | e2e ~1.05× |
| P3 | 2:4 sparse on backbone_m1 | backbone 2 ms | → 1.5 ms | < 1% |

**结论**：P0 单点就能拿到 3.6× e2e 加速，必须先做。P1-P3 的剪枝/量化优化在 NMS 未替换之前都被分母拖死。

### 5.3 关键观察

#### Smoking gun: `QuickCumsum.apply` 一行 116 ms

**`QuickCumsum.apply` 占整个 voxel_pool 的 97.4%**，占整个 e2e forward 的 86.4%。
所有其他 LSS 子操作（flatten / filter / argsort / scatter）加起来只有 3 ms。

**为什么这一行如此慢**：
- 输入：590K frustum 点（其中 486K 在范围内）
- 操作：对同一 BEV 格子的点做特征 sum-pooling（按 ranks 分组累加）
- 实现：`opencood/utils/camera_utils.py` 里的 `QuickCumsum` 自定义 autograd function
- 算子性质：memory-bound (大量非连续读写 + 排序后的依赖性累加)，**不是 compute-bound**
- 不受 CamEncode CNN 参数量影响

#### 与 LiDAR m1 的对比

| 指标 | m1 (LiDAR PP) | m2 (Camera LSS) | 倍数 |
|---|---|---|---|
| Encoder 总耗时 | 3.01 ms | 128.65 ms | **42.7×** |
| - 子瓶颈 | scatter_to_BEV (0.5 ms 估) | **QuickCumsum 116.43 ms** | – |
| Forward 总耗时 (无 NMS) | 22.99 ms | 134.79 ms | **5.9×** |
| 全 e2e (估含 NMS) | ~98 ms | ~205 ms | **2.1×** |

**结论**：**m2 比 m1 慢 ~2× e2e，慢的部分几乎全在 LSS QuickCumsum 这一行**。这印证了之前调研里"相机 Pyramid 剪枝 30% 加速微乎其微"的说法——剪 CNN 参数对 memory-bound 的 cumsum 无影响。

## 六、加速优先级（合并 m1 + m2 后重排）

| 优先级 | 方法 | 攻击对象 | 节省 | e2e 加速 (m1) | e2e 加速 (m2) |
|---|---|---|---|---|---|
| **P0** | MMCV `nms_rotated_cuda` 替换 Shapely NMS | NMS 70ms → 1ms | -70ms | **98 → 27 ms = 3.6×** | **205 → 135 ms = 1.5×** |
| **P0'** | **BEVPoolv2 / NVIDIA BEV-pool CUDA kernel 替换 `QuickCumsum.apply`** | QuickCumsum 116ms → ~10ms | -106ms | 不影响 m1 | **m2: 205 → 100 ms = 2.0×** |
| **P0 + P0'** | NMS + BEVPool 同时替换 | NMS + QuickCumsum | -176ms | m1: 98→27ms = 3.6× | **m2: 205 → 29 ms = 7.0×** |
| P1 | UPAQ-style pruning + INT8（路侧 RSU, LiDAR） | encoder+backbone 5ms | -2.5ms | 路侧单 agent 2× | 不适用 |
| P2 | pyramid_backbone INT8 + 32 对齐 channel prune | pyramid 14/4 ms | -5/-1 ms | e2e ~1.05× | e2e ~1.01× |

**核心结论**：
- m1 LiDAR baseline → **P0 (CUDA NMS) 单点 3.6× e2e**
- m2 Camera LSS → **P0' (BEVPoolv2) 单点 2× e2e**；P0+P0' 组合 **7× e2e**
- 剪枝/量化（P1, P2）在任一 modality 上 e2e 收益都 ≤ 5%

## 八、P0 + P0' 实测加速结果

### 8.1 实现方式

**P0 (NMS 替换)**：
- 文件：`scripts/phase2/m4_8_cuda_kernel_replacements.py::nms_rotated_mmcv`
- 调 `mmcv.ops.nms_rotated` (CUDA kernel)
- 输入接口转换：(N, 8, 3) corners → (N, 5) (xc, yc, w, h, angle)
- 正确性验证：48/48 候选框 100% overlap with HEAL 原 NMS

**P0' (QuickCumsum 替换)**：
- 文件：`scripts/phase2/m4_8_cuda_kernel_replacements.py::quickcumsum_native`
- 用 PyTorch 原生 `index_add_` 实现 segment-sum（2 个 kernel）替换 HEAL `QuickCumsum.apply` 的 6-kernel cumsum+masking 流程
- 正确性验证：x 输出最大差 5e-4 (fp32 噪声), geom_feats 完全一致

### 8.2 全 ablation 实测（mean ms, RTX 4090）

**测试**：m1 用 OPV2V test 100 sample (1.61 agents/scene, collab 模式)；m2 用 OPV2V test 60 sample (single 模式)

### 8.4 与预测对比

| 预测 (§六) | 实测 |
|---|---|
| m1 + P0: e2e 98→27 ms = 3.6× | 实测 e2e 83→27 ms = **3.04×** ✓ |
| m2 + P0+P0': e2e 205→29 ms = 7.0× | 实测 e2e 158→41 ms = **3.84×** ✓ |

> **预测偏差归因**：
> 1. 预测时用 m1 e2e baseline = 98 ms（200 sample 平均），重测时是 83 ms（100 sample），实测样本分布偏窄 → m1 baseline 比预测乐观 15 ms
> 2. 预测时用 m2 e2e baseline = 205 ms（按 m2 forward 135 + NMS 假设 70 推断），实际测出 m2 NMS 才 15 ms（因为 single 模式候选框少）→ m2 baseline 比预测乐观 47 ms
> 3. P0' 用 PyTorch 原生 `index_add_` 而不是 BEVPoolv2 CUDA kernel，前者比后者多约 10-15 ms（预测时假设是 BEVPoolv2 ~10 ms）

**关键结论**：尽管绝对加速倍数略低于预测，**P0 + P0' 仍然给出 3-3.8× e2e 加速**，且单点替换 < 100 行代码、不动训练流程、不动权重、AP 完全无损。

### 8.5 与剪枝/量化的对比（重新排序的 ROI）

| 优化 | 实施代价 | m1 加速 | m2 加速 | AP 损失 |
|---|---|---|---|---|
| **P0 (CUDA NMS)** | < 30 行代码, 1 人时 | **3.04×** ✓ | 1.07× | 0 |
| **P0' (segment-sum)** | < 50 行代码, 0.5 人时 | 不适用 | **2.68×** | 0 (5e-4 fp32 噪声) |
| **P0 + P0'** | < 80 行总代码 | **3.04×** | **3.84×** | 0 |
| pruning 25% + finetune | ~5 人日 (含 train) | <1.05× | <1.05× | -0.005 ~ -0.02 |
| INT8 PTQ (TRT) | ~3 人日 | <1.2× | <1.2× | -0.01 ~ -0.05 |
| pruning + INT8 | ~10 人日 | <1.3× | <1.3× | -0.02 ~ -0.05 |

**最终结论**：**先做 P0/P0'（一天工程）才有意义做剪枝/量化**。在不优化 NMS 和 QuickCumsum 之前，剪 CNN 参数对 e2e 完全无效（因为 90%+ 时间不在 CNN 里）。
