# F-Cooper (HEAL OPV2V LiDAR baseline) 全网络分段耗时实测

> **本文档为 F-Cooper baseline 真权重 (HEAL HF 发布 `bestval_at23`) 在 RTX 4090 上的
> 完整分段耗时实测**，格式与 `pyramid_fusion/分段耗时实测_v1.md` 对齐。
>
> **架构同质性 caveat（必读）**：F-Cooper 与 AttFuse/V2VNet/V2X-ViT/Where2Comm 共享 HEAL
> `HeterModelBaseline` 框架，**encoder_m1 + backbone_m1 完全一致**，仅 `fusion_net` 和 `shrinker_m1.stride`
> 不同。F-Cooper 用 stride 1 (输出 BEV 100×352)。详见 `V2X_baselines_横向对比_v3.md` §架构同质性声明。
>
> 关键发现：F-Cooper 的 max-pool fusion 仅占 e2e **1.6%**，NMS (Shapely)
> 占 **77%** — 与 Pyramid m1 完全一致的瓶颈模式。本框架 P0 (CUDA NMS) 可拿到 **~4×** 加速。

## 三、关键结论

### 3.1 NMS 是绝对主因 (77% e2e)

与 Pyramid m1 (NMS 73% e2e) 一致——所有用 `VoxelPostprocessor + nms_rotated` 的 HEAL 模型都
共享这个瓶颈。`opencood/utils/box_utils.py:nms_rotated`：

- `.cpu().detach().numpy()` GPU→CPU 同步
- Shapely Polygon 列表构建 + Python while 循环 + `box.intersection(b).area / box.union(b).area` 的 O(N²) IoU
- p99 = 130 ms（vs p50 = 68 ms，方差 2×）反映 N² 复杂度对候选框数量极敏感

### 3.2 F-Cooper 的 fusion 几乎免费 (1.6% e2e)

`MaxFusion` 仅含 `warp_affine_simple`（grid_sample 双线性插值）+ `torch.max(stacked_features, dim=0)`，
**0 可学参数**。这是设计哲学：用算力换通信带宽（每个 cav 传 256×100×352 feature map ≈ 22MB/scene
@ FP16，每帧 4 GB 估算）但 fusion 算力贡献极小。

### 3.3 forward 内部分解

| forward 内部分解 | mean (ms) | 占 forward 15.58ms |
|---|---|---|
| encoder + backbone + shrinker | 14.05 | 90.2% |
| fusion_net (MaxFusion) | 1.41 | 9.1% |
| heads | 0.12 | 0.7% |
| **CNN 合计** | **15.58** | **100%** |

剪枝/量化在 forward 范围内有效（能省 4-6ms），但在 e2e 范围被 NMS 77% 拖死。**先做 P0 NMS 替换是数学硬约束。**

## 四、加速优先级（按 ROI 排序）

| 优先级 | 方法 | 攻击对象 | 节省 | e2e 加速 |
|---|---|---|---|---|
| **P0** | MMCV `nms_rotated_cuda` 替换 Shapely NMS | NMS 69.10 ms | → ~1 ms | **89.81 → 21.7 ms = 4.1×** |
| P1 | encoder/backbone 50% L1 prune + finetune | 8.6 ms (encoder+backbone) | → 5.2 ms | e2e ~1.05× (after P0) |
| P2 | TRT INT8 (RSU 子模型 + shrinker_m1) | 14.05 ms (RSU) | → 5.6 ms | e2e ~1.1× (after P0) |
| P3 | TRT INT8 (全部 dense conv on ego) | 15.58 ms (forward) | → 6.2 ms | e2e ~1.15× (after P0) |
| n/a | fusion_net 剪枝 | 1.41 ms (无参数, 已最优) | — | 不适用 |

**结论**：P0 单点拿 4.1× e2e 加速。P1-P3 在 NMS 替换之后才有意义，叠加可到 ~6×（e2e = 89 → 15 ms）。

## 五、与 Pyramid m1 对比

| 指标 | Pyramid m1 | F-Cooper | 差异 |
|---|---|---|---|
| encoder_m1 | 3.01 | 3.02 | 一致 (相同 PointPillar) |
| backbone_m1 | 2.12 (ResNet) | 5.58 (BaseBEV) | F-Cooper 重 2.6 ms |
| aligner / shrinker | 0.02 (AlignNet) | 5.45 (DownsampleConv stride 1) | F-Cooper 重 5.4 ms |
| fusion 模块 | 14.45 (pyramid_backbone) | 1.41 (MaxFusion) | **F-Cooper 轻 13.0 ms** |
| heads + 其他 forward | 3.39 (shrink+heads) | 0.12 (heads only) | Pyramid 重 3.3 ms |
| **forward 小计** | **22.99** | **15.58** | F-Cooper 轻 **7.4 ms** |
| NMS (Shapely) | 71.69 | 69.10 | 一致 (heads 维度相同) |
| **e2e** | **98.37** | **89.81** | F-Cooper 快 **8.6 ms** |

**洞察**：F-Cooper 用"重 backbone + 轻 fusion"换 Pyramid 的"轻 backbone + 重 fusion"。**总 forward F-Cooper 略快**，但精度 F-Cooper 远低于 Pyramid (论文 AP70=0.66 vs 0.93)。

按 pyramid_fusion 同款方案：用 `mmcv.ops.nms_rotated` (CUDA polygon IoU) 替换 `box_utils.nms_rotated` (Shapely Python loop)。具体实现：`scripts/phase2/m4_8_cuda_kernel_replacements.py:nms_rotated_mmcv`。

### 6.2 关键观察

- **P0 单点拿 3.7× e2e 加速** — 与预测的 4.1× 接近 (差异因 forward 0.5ms 不可忽略 noise)
- **NMS 27× 加速**: 69.1 → 2.53 ms — 与 Pyramid m1 的 P0 测试一致
- **e2e 24.5 ms = 40.8 FPS** — 接近实时 (典型 V2X 要求 10-20 FPS)
- **新瓶颈**: P0 后 NMS 不再是 dominant；decode + dir + corners + range_mask = 4.7 ms 占 19% 是下一波目标

## 七、Caveats

1. **score_threshold = 0.2**：与原 HEAL eval 一致，**未做任何人为干预**。NMS workload 完全真实。
2. **agents/scene = 1.39**：OPV2V test 中部分场景为 1 agent (无 fusion)，多数 2 agents。
3. **P0 前后 forward stages 微差 0.5 ms**：CUDA Event 测量噪声 + 不同 GPU 状态下的 jitter。
4. **未测精度**：本测仅 latency。F-Cooper 在 OPV2V test 的 AP 数字见 HEAL 论文 Table 2 (AP70 ≈ 0.66)。
5. **原始数据**：baseline 在 `data/v2x_baseline_timing/fcooper_real.json`，P0 在 `fcooper_p0.json`。
