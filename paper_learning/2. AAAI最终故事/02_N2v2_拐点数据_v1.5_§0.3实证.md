# N2v2 拐点数据：经验硬约束在 Orin 上的真实失效（v1.5 §0.3 实证）

> **采集**: 2026-05-06 06:32-06:49 UTC
> **平台**: Jetson AGX Orin 64GB / JP 5.1.4 / TRT 8.5.2.2 / MODE_30W + jetson_clocks 锁频
> **角色**: v1.5 §6.1 Phase 1B.5 拐点验证；v1.5 §0.3 "经验硬约束 vs 物理硬约束"区分的实证素材
> **原始数据**: `data/orin_phase1b/n2v2_summary.csv`（24 行）

---

## 一、动机

v1.5 §0.3 把硬约束分三类（**物理 / 经验 / 软**），并明确提出：

> 经验硬约束（如 `channels mod 32 == 0`）是工程师手工总结的规则。
> §3 第 9 条进一步指出："这些经验规则**长期应被学到的规则替代**"。

但**经验规则在不同硬件上是否真的生效，从没有真实数据点验证过**。本次 N2v2 在 Orin AGX (Ampere sm87) 上做了第一次实证。

---

## 二、实验设计

构造 8 个最小 Conv ONNX，对照 channel 对齐拐点：

| 类别 | 输入 shape | 输出 channel | 期望（按经验规则）|
|---|---|---|---|
| out_c 不对齐 | [1, 128, 28, 28] | **63** | 比 64 慢（pad 到 64）|
| out_c 对齐 | [1, 128, 28, 28] | **64** | baseline |
| out_c 不对齐 | [1, 128, 28, 28] | **90** | 比 96 慢 |
| out_c 对齐 | [1, 128, 28, 28] | **96** | baseline |
| in_c (K dim) 不对齐 | [1, **63**, 28, 28] | 64 | 比 in_c=64 慢 |
| in_c (K dim) 对齐 | [1, **64**, 28, 28] | 64 | baseline |
| in_c 不对齐 | [1, **90**, 28, 28] | 64 | 比 96 慢 |
| in_c 对齐 | [1, **96**, 28, 28] | 64 | baseline |

每个 ONNX 用 trtexec **FP16 + INT8** 各跑 100 iter / avgRuns=50 / `--useSpinWait` / `--noDataTransfers`，jetson_clocks 锁频。

## 三、实测结果

### 3.1 out_c 拐点（输出通道对齐 32）

| out_c | FP16 (ms) | INT8 (ms) | FP16 vs 对齐基线 | INT8 vs 对齐基线 |
|---|---|---|---|---|
| **63** | 0.06325 | 0.05039 | **+0.27%** | **+0.32%** |
| **64** (对齐) | 0.06308 | 0.05022 | baseline | baseline |
| **90** | 0.08051 | 0.06113 | **-0.93%** ❗ | **+0.28%** |
| **96** (对齐) | 0.08126 | 0.06096 | baseline | baseline |

### 3.2 in_c (K 维) 拐点

| in_c | FP16 (ms) | INT8 (ms) | FP16 vs 对齐基线 | INT8 vs 对齐基线 |
|---|---|---|---|---|
| **63** | 0.04720 | 0.04096 | **-0.50%** | **+0.81%** |
| **64** (对齐) | 0.04744 | 0.04063 | baseline | baseline |
| **90** | 0.06034 | 0.04452 | **+0.07%** | **-0.45%** |
| **96** (对齐) | 0.06030 | 0.04472 | baseline | baseline |

### 3.3 ResNet-50 锁频后稳定性（验证测量本身可信）

| 配置 | 5 reps mean (ms) | 5 reps std (ms) |
|---|---|---|
| FP16 | 2.530 | 0.015 |
| INT8 | 1.767 | 0.007 |

std < 0.7%，证明 jetson_clocks 锁频有效消除 DVFS 抖动，**对齐拐点的微小差异不是测量噪声**。

## 四、结论与论文意义

### 4.1 经验规则失效的具体表现

`channels mod 32 == 0` 这条经验硬约束在 Orin sm87 + TRT 8.5 上：

- out_c 不对齐 vs 对齐: 差异 **|±0.93%| 以内**
- in_c 不对齐 vs 对齐: 差异 **|±0.81%| 以内**
- **甚至有 out_c=90 比 96 快（-0.93%）的反例** — 完全反直觉

### 4.2 失效根因

**TRT 8.5 在 Orin sm87 上对非对齐通道做 implicit padding**：
- 输入到 conv 时按硬件对齐自动 pad（计算量略增 < 2%）
- 但因为 LPDDR5 带宽富余 + GPU compute capacity 充足，pad 的额外算力被吸收
- 最终 latency 变化 < 1%，对齐"经验约束"被硬件/编译器自动消化

### 4.3 对 v1.5 §0.3 三类约束分类的修正

| 约束 | v1.5 §0.3 原分类 | N2v2 实证后修正 |
|---|---|---|
| 通道对齐 32 | 经验硬约束 | **应降级为软约束**（甚至可能是过时规则）|
| `K_dim ≥ 64` 才有 2:4 收益 | 经验硬约束 | 待验证（本次未测）|
| 跨层剪枝率梯度 < 30% | 经验硬约束 | 待验证 |

### 4.4 论文叙事价值

**这是 v1.5 §3 开放问题第 9 条 "硬约束如何从人工规则演进为学到的规则" 的第一组实证**：

- 旧 HW-NAS 框架（HALP / LightPrune / APQ）大量使用经验规则缩小搜索空间
- 但**经验规则在不同硬件 + TRT 版本上的有效性从未被系统验证**
- 我们的框架通过 capability YAML 实测数据（本表）**用真实测量替代人工规则**
- 实现了 v1.5 §0.3 提到的"演进路径"

### 4.5 直接影响搜索空间设计

按 N2v2 数据，下一步 4090 端 `framework/constraints.py` (任务 A3) 写硬约束 DSL 时：

```python
# 旧规则 (按经验):
HARD_CONSTRAINT: channels % 32 == 0   # 强制过滤掉所有非 32 倍数

# 新规则 (按 N2v2 实测):
SOFT_CONSTRAINT: channels % 32 == 0   # 仅作排序偏好，不过滤
# 或更精确: 不加这条规则，让 LightGBM 预测器学
```

如果硬塞旧规则，会过滤掉大量实际可用的剪枝率（如 90% 通道剪枝率，对应 90 通道）。
