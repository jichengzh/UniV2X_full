## 0. 前置共识

在进入流程之前,先约定 4 个会反复用到的概念。

### 0.1 协同加速 = B1 + B2 + D 联合搜索

UniV2X 的协同框架不是只搜剪枝、也不是只搜量化,而是三者**同时纳入同一个搜索器**:

- **B1 剪枝**(可配置剪枝实现于 1.2): 改变网络的参数/通道数
- **B2 量化**(可配置量化实现于 1.1): 改变参数的数值表示
- **D 部署配置**(可配置硬件优化实现于 1.3): 改变模型在硬件上的执行方式

**单独搜剪枝,再单独搜量化,再单独搜部署**——会错过三者之间的耦合点。
例如剪到 90 通道再 INT8 量化时,90 → 96 padding 会**完全抵消剪枝收益 + 量化增益**。
联合搜索的核心意义就是规避这种"局部最优组装出整体次优"的陷阱。

### 0.2 可配置维度的真实搜索空间

经过 1.1 / 1.2 实验已完成的"理论可调 → 实际可搜"裁剪,真实搜索空间是:

**B1 剪枝(3 轴)**:
| 轴 | 取值 | 与其他维度的耦合 |
|----|------|----------------|
| 剪枝率 | {0%, 10%, 20%, 30%, 50%, ...} | 受硬件对齐约束(channels % 32 == 0)钝化 |
| 剪枝对象/粒度 | {channel, head, N:M(2:4), element} — 主流是 channel | 受硬件支持决定(N:M 仅 Sparse TC) |
| 剪枝准则 | {L1, Taylor, FPGM, Wanda(激活感知)} | **与模型/量化/硬件强耦合,不可一次确定**(详见 §0.5) |

**B2 量化(4 轴)**:
| 轴 | 取值 |
|----|------|
| 位宽 | {INT8, FP16}(模块级) |
| 粒度 | {per-tensor, per-channel} (per-group 因 TRT 不支持已剔除) |
| 量化对象 | {W-only, W+A, none} |
| 模块选择 | {backbone, BEV encoder, 检测头} |

**B2 已锁定不参与搜索的(由 1.1 实验得出)**:
- 对称性 = 对称(TRT GPU 硬约束)
- 校准方法 = minmax/mse(无耦合,一次确定)
- V2X 通信 = INT8(已验证)
- 下游头 = INT8(已验证)
- 累加精度 = FP32(默认)

**重要区分**: B2 第 4 轴"模块选择"与 D 维度的"DLA 子图分裂"长得很像但**不是同一轴**。

| | B2 模块选择(软件量化) | D 设备路由(硬件 IP) |
|----|---|---|
| 决策内容 | "这个模块**怎么量化**" | "这个模块**在哪里跑**" |
| 决策粒度 | 模块 | 模块 / 子图 |
| 决策依据 | 精度敏感度(校准集 cosine) | 算子白名单 + 性能/能耗 |
| 在哪个空间 | B2 量化空间 | D 部署空间 |

两者表面都按模块粒度做决策,所以容易混为一谈,但本质上一个是"如何处理数值",一个是"在哪个 IP 上跑"。

**两者通过硬约束双向耦合**:

```
IF 模块路由到 DLA  →  B2 强制 (INT8, per-tensor, W+A, 对称)
                     B2 的 4 轴可行集合从原来 ~36 种缩为 1 种

IF B2 选 per-channel(精度需要)→  该模块必须走 GPU(不能选 DLA)
                                D.L1 设备路由的可行集合被 B2 反向收窄
```

所以 DLA 子图分裂**不应纳入 B2 的 4 轴**(否则混淆搜索空间层次),应留在 D 维度,但搜索器需在每次评估候选时同时考虑 D → B2 / B2 → D 的硬约束传播。

**D 部署配置(分层旋钮)**:

"分层旋钮"是按"决策针对什么对象"对 D 维度做的归类。每层的旋钮调节代价、影响范围都不同:

| 层 | 针对对象 | 旋钮举例 | 决策代价 |
|----|--------|---------|---------|
| **L1 设备路由** | 子图 / 模块 | stream / MPS / MIG / DLA core / 多 IP 分配 | 高(改全图编译路径) |
| **L2 精度** | 张量 / 数值表示 | 主要由 B2 决定;但**必须按 L1 路由切子图独立设定**(子图分裂) | 中 |
| **L3 算子内部** | 单个算子 | TRT tactic source / workspace pool / cuDNN benchmark mode | 低(TRT 多自动挑) |
| **L4 调度** | 多算子 / 多模型 | CUDA Graph / 时序缓存 / batch 策略 / stream 编排 | 中 |

**关于"L2 精度需子图分裂"**: 同一份 ONNX 不能用统一 L2 策略,因为 L1 路由分配的不同 IP 对精度有不同硬约束(例: DLA 强制 per-tensor + HWC4,GPU 支持 per-channel + CHW16)。所以必须按 L1 路由把图切成子图,每段独立设定 L2,边界插入 reformat 节点。详见 §0.6。

**关于"分层旋钮的硬件依赖"**: 上表是 NVIDIA 栈(Orin/数据中心)语境;在国产 NPU(华为/Horizon/黑芝麻)、Apple/高通栈上,L1-L4 的具体旋钮名称和取值不同(例: Horizon BPU 没有 stream 概念,L4 调度只剩 batch 策略;华为 Ascend L3 含 tile 手写)。详见 `survey_raw_2/d_space_non_nvidia.md`。**工作流的骨架不变,旋钮按硬件 capability 描述文件展开**(详见步骤 1)。

### 0.3 硬约束 vs 软约束

硬件对软件的指导可以分**三类硬度**,**搜索器对它们的处理方式不同**,且"是否属于人工规则"也不一样:

| 类型 | 是什么 | 例子 | 处理方式 | 是否人工规则 |
|------|--------|------|---------|------------|
| **物理硬约束** | 硬件本身的事实,违反构建失败 | 2:4 必须精确 50% / DLA 算子白名单 / Hopper 无 INT4 TC / TRT GPU 不支持非对称 | 搜索前**硬过滤** | ❌ **不是规则,是事实** — 你不写它也存在 |
| **经验硬约束** | 实验拐点,违反能跑但性能差 | channels % 32 == 0 / K_dim ≥ 64 / 跨层剪枝率梯度 < 30% | 搜索前硬过滤 | ✅ **是人工规则** — 来自实测经验 |
| **软约束** | 偏好性引导,违反不致命 | 剪枝率梯度平滑 / 模块间精度一致性偏好 | 搜索时作为**惩罚项** | ✅ **是人工规则** |

**重要观察(v1.4 新增)**: 这一节本质上是把"硬约束塞入"区分为两件事:
1. **物理事实的反映**(物理硬约束)— 不可省略,违反就 build 失败
2. **人工经验规则的注入**(经验硬约束 + 软约束)— 是工程师手工总结的"已知坏点"

**为什么仍然这样做(尽管它是人工规则)**:
- 数据稀缺: 训预测器需要大量 (硬件 × 模型 × 配置) 标注数据
- 规则代价低: 写一条 `channels mod 32 == 0` 的成本远低于跑实测
- 覆盖 80% 明显坏点: 不让搜索器在已知死路上浪费预算

**这种做法的 4 类失效模式**:
- **规则不全**: 新算子组合可能漏过(自定义 attention 在 DLA 白名单更新前)
- **规则冲突**: 多硬件目标时不同硬件的约束打架
- **规则过时**: TRT/硬件升级后规则失效
- **规则粗糙**: 阈值是经验值不是连续函数(K=63 vs K=64 不应是 0/1 跳变)

**演进路径**: 经验硬约束和软约束**长期应被学到的规则替代**,但物理硬约束永远存在。
- 可微 latency 预测器(LightPrune ICCV'25)替代"对齐拐点"规则
- 量化精度预测器(APQ CVPR'20)替代"哪种量化敏感"规则
- 仿真+搜索分离(Vidur SOSP'24)的仿真器本身就是"学到的规则"

详见 §3 开放问题第 9 条。

混淆这三类是常见错误——把物理硬约束当成软约束会让搜索器跑出大量构建失败候选;把经验软约束当成物理硬约束会错过好解。

### 0.4 反馈回路:从 latency 实测/查表回到搜索器

完整的协同不是"软件指导硬件 + 硬件指导软件"的单向闭合,而是有第三步反馈:

```
   ┌──────────────────────┐
   │ B1+B2+D 候选配置      │
   └──────────┬───────────┘
              ▼
   ┌──────────────────────┐
   │ 评估器:精度 + 延迟    │  ← 这步必须存在
   │ (LUT / Vidur / 实测) │
   └──────────┬───────────┘
              ▼
   ┌──────────────────────┐
   │ Pareto 前沿筛选       │
   │ → 反馈回搜索器        │
   └──────────────────────┘
```

没有这个反馈,只能用 FLOPs 当 proxy,会出现"FLOPs 降 30% 但 latency 几乎不降"的奇怪结果。
HALP / MetaPruning / Vidur 等工作的核心贡献就是把这条回路工程化。

### 0.5 剪枝准则不是常量,而是 (模型 × 量化 × 硬件) 的联合函数

剪枝准则(L1 / Taylor / FPGM / Wanda 等)看起来像"挑一个用就好",但**它的有效性会因其他维度漂移**,不能一次确定。

**根因**: "权重重要性"不是权重的固有属性,而是 **(权重幅度 × 激活分布 × 损失曲面)三者的联合函数**。每个准则只看了其中 1-2 项:

| 准则 | 看了什么 | 假设成立时 | 假设失效时 |
|------|--------|----------|----------|
| L1 | 权重幅度 | 激活近似均匀(CNN+ReLU) | 激活分布悬殊(LLM)、有 BN |
| Taylor | 权重 × 损失一阶导 | 损失曲面平滑 | 残差/skip 让一阶失真 |
| FPGM | filter 间几何距离 | filter 有真实冗余 | filter 高度专门化 |
| Wanda | 权重 × 激活幅度 | 激活差异大(LLM) | CNN 激活均匀时反不如 L1 |

**三种主要耦合**:

1. **准则 × 模型**: CNN 偏 L1/FPGM; Transformer 偏 Taylor; LLM 偏 Wanda
2. **准则 × 量化**:
   - INT8 噪底直接吞掉 |w| < scale/127 的小权重 → L1 排序须在量化后做
   - per-channel scale 让"小权重"标准不一致 → 应用 effective magnitude = |w|/scale_w
   - 混合精度下不同层"什么算小"的标准不同 → 准则必须按层 normalize
   - APQ (CVPR'20) 的核心贡献就是把准则评估放到量化后,精度提升 2.3% / 搜索代价省 600×
3. **准则 × 硬件**:
   - 2:4 强制 50% → 全局准则被钝化为组内 L1 即可
   - 通道对齐 32 → 准则细分被 round 拉平,L1 够用
   - DLA 算子白名单 → 准则需先过滤可剪通道
   - Sparse TC → 非结构化 mask 必须事后转 2:4,准则的精细优势被吞

**对 UniV2X 的具体含义**:

- BEV backbone(CNN + BN): L1 + FPGM 候选,需消除 BN 重缩放干扰
- BEV decoder(Transformer): Taylor 或 Wanda 候选
- 量化加上后(INT8 + per-channel): 准则评估必须在量化后做
- 硬件加上后(2:4 / 通道对齐 32): 全局准则的精细度被吞,L1 在大多数场景够用

**结论**: 工作流不能在搜索之前选定准则。最稳的做法是:**让准则也作为搜索变量,但用经验先验缩小候选**(比如 BEV 主干给 L1+FPGM,decoder 给 Taylor+Wanda),然后再让评估器在 (model × quant × hw) 下选最终 winner。

## 1. 六步流程

### 步骤 1: 确定部署场景与硬件目标

**目的**: 把"一个待加速网络"转化为"在哪颗芯片上、什么场景、什么 SLA 约束"。

**输入**:
- 待加速网络(ONNX / PyTorch checkpoint)
- 部署场景描述(车端 / 路侧 / 数据中心 / 边缘)
- 业务 SLA(目标 FPS / 延迟上限 / 功耗预算 / 显存上限)

**输出**: 一份"硬件 capability 描述文件",至少包括:

```yaml
hardware:
  name: ...                  # 例: Jetson AGX Orin 64GB
  arch: ...                  # 例: Ampere sm87
  ips:                       # 可用 IP 列表(关键)
    gpu: { precisions, tensor_core, streams_max, ... }
    dla: { count, precisions, quant_constraints, op_whitelist, ... }
                             # ← 没有 DLA 就不写;有别的 NPU 写别的
  alignment:                 # 对齐要求
    int8_channel: 32
    fp16_channel: 16
  features:                  # 软件能力
    mig, mps, sparse_tc, cuda_graph, ...
  toolchain:
    trt_version: ...
    jetpack_version: ...
```

**为什么用 capability 描述文件**: 不同硬件可用的 IP 完全不同(数据中心卡只有 GPU、Orin Nano 只有 GPU、Orin AGX 有 GPU+2 DLA、Horizon J5 是 BPU、CPU-only 板没 NPU)。把硬件能力抽象成描述文件,后续步骤 2 的硬约束和步骤 3 的搜索空间可以**按描述文件自动展开**,不用为每种硬件写一份工作流。

**典型硬件场景**:

| 场景 | 例子 | 可用 IP | DLA 约束是否适用 |
|------|------|---------|----------------|
| 数据中心 NVIDIA | A100/H100/L40S/RTX4090 | GPU only(可能 + MIG) | ❌ 不适用 |
| Jetson Orin AGX | 车端高配 | GPU + 2 DLA | ✅ 适用 |
| Jetson Orin NX | 车端中配 | GPU + 1 DLA | ✅ 适用 |
| **Jetson Orin Nano** | **低成本边缘** | **GPU only(无 DLA)** | **❌ 不适用** |
| 国产车规芯片 | Horizon J5/J6, 华为 MDC, 黑芝麻 A1000 | CPU + 自研 NPU(BPU/Ascend/NeuralPro) | ❌ 但有自家 NPU 约束 |
| CPU-only 嵌入式 | 工控机 / Raspberry Pi | CPU only | ❌ 走 OpenVINO/ORT CPU EP |

**关键操作**:
- 查厂商文档确认可用精度集合(NVIDIA Tensor Core 表 / Horizon BPU 算子表 / Apple ANE 算子表)
- 列各 IP 的算子白名单(如果有 NPU)
- 标注完整工具链版本(TRT/JetPack/CANN/Open Explorer 等)
- 测原模型基线 baseline(在目标硬件上实测,不要用开发硬件代替)

**陷阱**:
- **误把"目标硬件"等同于"开发硬件"**: 开发用 RTX 4090(Ada)、部署目标 Orin Nano(无 DLA),开发时跑 DLA 测试在 Nano 上完全用不上
- **不区分 Orin 型号**: AGX 有 2 DLA、NX 有 1 DLA、Nano **完全没有 DLA**——同样写"Jetson Orin"得到的工作流可能完全不同
- **忽略国产芯片的 SDK 差异**: Horizon Open Explorer 与 NVIDIA TRT 工具链完全不同,搜索器和制品流程也得换
- **工具链版本未锁定**: TRT 升级后 tactic 选择会变,部署制品需绑定版本

**当目标硬件没有 DLA / 没有 NPU 时**:
- L1 设备路由轴**退化**为只剩 GPU 内部(stream / MPS / MIG)的选择
- DLA 相关硬约束(per-tensor / HWC4 / 算子白名单)**全部从清单中移除**
- B2 量化的可行集合**反而扩大**(无 DLA 路由 → per-channel 全图可用)
- 这种情况下工作流更简单,但搜索空间更大,搜索代价反而可能更高

**对应工具/文件**:
- `survey_raw_2/d_space_nvidia.md` — NVIDIA 栈 capability 参考
- `survey_raw_2/d_space_non_nvidia.md` — 非 NVIDIA 厂商 capability 参考
- `survey_raw_2/ad_v2x_deployment.md` — Jetson Orin 各型号差异

### 步骤 2: 根据硬件能力裁剪搜索空间(注入硬约束)

**目的**: 把"理论可配置维度"裁成"目标硬件上实际可搜的合法集合"。

**输入**: 步骤 1 的硬件画像 + B1/B2/D 的理论搜索空间(见 0.2)。

**输出**: 一份"硬约束清单",描述哪些组合被先过滤。

**关键操作 — 硬约束清单(示例,以 Orin 为目标)**:

```
B1 剪枝硬约束:
  - 通道数必须对齐到 32 的倍数(INT8 TC 要求)
  - K 维度 >= 64(2:4 有效门槛)
  - 跨层剪枝率梯度 < 30%(避免打断 fusion)

B2 量化硬约束:
  - 对称性 = 对称(TRT GPU 强制)
  - per-channel activation 禁止(GPU GEMM 不支持)
  - Hopper 上禁 INT4 + TC(Orin Ampere 不受此限)

D 部署硬约束:
  - Orin 不支持 MIG → 走 Stream + MPS
  - DLA 算子白名单(Conv/Pool/FC/Activation/...),其他算子必 fallback
  - FP8 / FP4 在 Orin 不可用(等 Thor)

D → B2 硬约束传播(DLA 路由触发):
  IF 模块路由到 DLA:
    - B2.位宽 强制 = INT8(FP16 在 DLA 上没有 15× 加速)
    - B2.粒度 强制 = per-tensor(DLA 不支持 per-channel)
    - B2.对象 强制 = W+A(DLA 全 INT8 才有收益)
    - 输入布局 强制 = HWC4(否则触发 reformat,失去 DLA 优势)
  → B2 的 4 轴可行集合从 ~36 种缩为 1 种

B2 → D 硬约束传播(精度需求触发):
  IF B2.粒度 = per-channel:
    - D.设备路由 该模块禁止选 DLA
  IF B2.位宽 = FP16:
    - D.设备路由 该模块**可以**走 DLA 但价值低(无 15× 加速)
```

**陷阱**:
- 把硬约束当软约束: 搜索器会跑出大量 "构建失败" 候选,浪费预算
- 漏过滤: DLA 子图忘了 per-tensor 约束,搜出 per-channel 配置后才发现 fallback 到 GPU,前期评估全部失效

**对应工具/文件**:
- `survey_raw_2/README.md` §6.2 硬过滤清单 — 直接复用
- `survey_raw_2/quantization_x_hardware.md` §4 — DLA 量化约束细节

### 步骤 3: 联合搜索 B1 × B2 × D

**目的**: 在合法搜索空间内,通过评估器找出 Pareto 前沿。

**输入**: 步骤 2 裁剪后的合法搜索空间。

**输出**: 一组 Pareto 最优配置(精度 × 延迟 × 能耗 三轴前沿)。

**关键操作**:

1. **采样策略**:
   - 模块级而非逐层(逐层 2^54 不可行,模块级 32-96 种可穷举)
   - 优先级: B2 量化 > D 部署 > B1 剪枝(B2 收益最大,先搜)

2. **评估机制**:
   - **精度**: 校准集 cosine 相似度 / 小规模评估集 AMOTA
   - **延迟**: latency LUT 查表(预先建)/ Vidur 类仿真 / Top-K 候选用 trtexec 实测
   - **能耗**(可选): nvidia-smi / dcgm

3. **可借鉴机制**(来自 survey_raw_2):
   - APQ 的精度预测器迁移(FP32 → 量化)
   - HAWQ-V3 的 ILP formulation(混合精度搜索的启动点)
   - HALP 的 LUT-driven knapsack
   - DANCE 的可微评估器

4. **早停**:
   - 明显劣势点(精度 + 延迟双输)直接淘汰
   - 同 Pareto 等级中保留多样性(不只挑当前最优)

**陷阱**:
- "硬件配置随之变" 的方向反了: 不是搜完剪枝率再调硬件,而是**硬件约束先于搜索作为边界**,搜索器在合法集合内同时考虑剪枝率 + 量化位宽 + 部署 flag
- 用 FLOPs 代理 latency: 64→63 通道会 FLOPs 降 1.5% 但 latency 几乎不变(被 pad 回 64)
- 评估器与最终部署不一致: PyTorch 端搜出的最优在 TRT 端不复现(对称性 / per-channel act 等差异)
- **准则耦合被忽略**(详见 §0.5): 用单一准则跑全网络会在不同子网失效;必须按子网类型(CNN/Transformer)分配候选准则,且评估必须在量化后做
- **准则评估顺序错误**: 先剪后量化时,L1 看的是 FP32 magnitude,量化后排序可能颠倒 → 应在 (剪枝候选 × 量化候选) 的笛卡儿积上联合评估,而非串行

**对应工具/文件**:
- 1.3 已经在做 latency LUT 建表
- `survey_raw_2/hw_aware_nas_and_joint_search.md` — 现有联合搜索工作的范式参考

---

### 步骤 4: Top-K 候选实测验证

**目的**: 用真实硬件 + 完整评估集纠正搜索时的代理误差。

**输入**: 步骤 3 的 Pareto 前沿(典型 Top-5 到 Top-10)。

**输出**: 验证后的最终候选集(通常 1-3 个)。

**关键操作**:
- **延迟实测**: trtexec 在目标硬件实测,而非 LUT 估计
  - 多次 warmup + 取 P50/P95/P99
  - 记录完整 tactic 分布(`--verbose --profilingVerbosity=detailed`)
- **精度实测**: 完整数据集评估(NuScenes 全集而不是子集)
  - 不只看 cosine,看任务级指标(AMOTA, mAP, IoU)
- **能耗实测**(如果纳入目标): tegrastats 持续监控
- **稳定性**: 跑 5-10 次 engine build,检查 tactic 是否稳定

**陷阱**:
- TRT 版本差异: 升级 TRT 后同一份 ONNX 选的 tactic 可能完全不同,需重新验证
- 冷启动 vs 热启动: timing cache 缺失时第一次 build 选 tactic 可能不稳
- DLA fallback: 步骤 3 的搜索可能没真正走 DLA(用了 LUT 估计),实测才发现某层悄悄 fallback 到 GPU

**对应工具/文件**:
- 1.3 的 trtexec 实测脚本
- `survey_raw_2/d_space_nvidia.md` §2.5 — Verbose 输出解读

---

### 步骤 5: 选定最终方案 + 制品化

**目的**: 把验证过的方案固化为可部署的制品。

**输入**: 步骤 4 验证后的候选(1-3 个,根据场景选)。

**输出**: 完整的部署制品包,包括:
- engine 序列化文件(.engine / .plan)
- timing cache(显著加速重新 build)
- DLA loadable(如果使用 DLA)
- 部署配置文件(stream 数 / priority / MPS % / nvpmodel)
- 校准缓存(INT8 calibration cache)

**关键操作**:
- engine 与版本绑定: TRT 版本 + 驱动 + 硬件型号要写进文件名/元数据
- timing cache 持久化到对象存储(下次 build 从 10min → 30s)
- 部署脚本固定 nvpmodel / jetson_clocks(避免运行时调频干扰)

**陷阱**:
- engine 跨硬件不兼容: A100 build 的 engine 不能直接给 H100 用
- 校准缓存丢失: PTQ scale 重算导致精度漂移
- 配置不版本化: 团队成员各自调 stream 数,不可复现

**对应工具/文件**:
- 部署 manifest(待补充模板)

---

### 步骤 6: 在线监控与回归

**目的**: 部署后持续监控,确保性能不漂移。

**输入**: 部署后的运行时日志。

**输出**: 监控报告 + 触发回归的事件。

**关键操作**:
- **监控指标**:
  - 延迟分布(P50/P95/P99)
  - 显存占用峰值
  - SM / Tensor Core 利用率
  - 功耗(车端尤其重要)
  - 任务级指标(检测召回 / 跟踪 ID 切换数)
- **回归触发**:
  - TRT 版本升级 → 重新 build,对比 tactic 分布
  - 数据分布漂移 → 重新校准 INT8 scale
  - 硬件升级(Orin → Thor) → 整个流程重跑步骤 1-5

**陷阱**:
- 监控延迟而不监控 tactic: 延迟稳定不代表 tactic 稳定,某天 cuDNN/TRT 升级后 tactic 变了,可能精度悄悄下降
- 忽略尾延迟: P99 延迟在车端比平均延迟更重要,P99 失控会触发安全保护

**对应工具/文件**:
- tegrastats / nvidia-smi / dcgm 集成(待开发)

## 3. 待完善的开放问题

留给后续讨论:

1. **评估器的具体实现**:
   - 精度预测器要不要训(参考 APQ 的 transfer learning)?
   - latency LUT 的粒度?(模块级 vs 算子级)
   - 多目标 Pareto 用哪种算法?(NSGA-II / 贝叶斯多目标 / 简单穷举)

2. **B1 × B2 × D 的搜索顺序**:
   - 真正同时搜还是按层级展开?(B2 先粗筛、B1 再精修、D 最后)
   - 各空间大小对比: B1 (~20) × B2 (~96) × D (~30) ≈ 6 万,模块级是否需要分阶段?

3. **能耗维度是否纳入**:
   - 当前 1.3 已开始测能耗,但搜索是否真把它当目标?
   - 在车端 / 路侧 / 数据中心三种场景下能耗权重不同

4. **DLA 子图自动分裂**(与 B2 模块选择的耦合,详见 §0.2 重要区分):
   - 当前需要手动指定哪些层上 DLA
   - 是否可以让搜索器自动决定 DLA / GPU 分配?
   - 如何工程化"D → B2 / B2 → D 硬约束传播"——是预过滤还是动态约束?
   - 路由决策与量化决策能否真同时搜,还是按"先路由再量化"分阶段?

5. **跨硬件迁移**:
   - 在 Orin 上搜出的方案能否快速适配到 Thor?
   - 跨硬件迁移要重跑哪几步?

6. **协同框架与上层 NAS 的关系**:
   - 当前框架假定网络架构 A 已固定,只搜 B1/B2/D
   - 如果上层也要搜 A(网络架构),是嵌套搜还是联合搜?

7. **在线自适应**:
   - 当前是离线搜 + 固定部署
   - 是否有必要做运行时根据负载动态切配置?(如夜间低流量切低能耗模式)

8. **剪枝准则在 (模型 × 量化 × 硬件) 下的最优如何选**(由 §0.5 引出):
   - 是否需要为 BEV backbone / decoder / 检测头各自维护一个准则候选集?
   - 准则评估必须在量化后做,但成本是 (准则数 × 量化候选数) 的笛卡儿积——能否用代理预测器降本?
   - 硬件约束(2:4 / 通道对齐)钝化全局准则差异,是否在硬约束严的场景下直接锁 L1?
   - 是否引入 Wanda 这类激活感知准则进 BEV decoder 的搜索池?

9. **硬约束如何从人工规则演进为学到的规则**(由 §0.3 引出):
   - 当前经验硬约束(channels mod 32 / K≥64 / 跨层梯度 <30%)是工程师手写,长期看不可持续
   - 1.1/1.2/1.3 实验积累的 LUT 数据能否作为 latency / accuracy predictor 的训练集?
   - 如何判断"规则"已经覆盖足够多失效模式?(规则收敛性指标)
   - 跨硬件迁移时,经验规则是否需要全部重训?预测器能不能跨硬件迁移?
   - 物理硬约束 vs 经验硬约束 vs 软约束的边界何时模糊?(例: 某些硬件升级后,过去的经验拐点变为物理事实)
