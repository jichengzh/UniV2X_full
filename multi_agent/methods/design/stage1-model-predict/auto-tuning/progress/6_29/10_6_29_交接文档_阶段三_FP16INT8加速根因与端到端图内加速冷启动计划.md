## 1. 固定口径

1. latency 对外统一使用 `ms`。
2. 当前速度口径是 TVM compiled backbone/subnet module end-to-end, 输入为 `spatial_features`, 输出为 backbone/subnet 多尺度 feature。
3. 不能写成完整 perception pipeline latency, 也不能写成真实 RSU 边缘物理设备绝对速度。当前应使用 `full_network_claim=false`。
4. 每次实测必须记录 `nvidia-smi`、TVM target、command、stdout/stderr、raw artifact。
5. RTX4090/sm89 结果只能作为结构诊断。H800 总表/论文口径必须在 H800/sm90 环境重跑。
6. default FP16 engine 不能写成 TensorCore engine。只有 rewritten full-engine 自身出现 `wmma/tvm_mma_sync` 且完成 build/run/latency/output/AP gate, 才能写成 FP16 TensorCore measured。
7. INT8 只有 native full ONNX/topology route 且 lowering inventory 满足 `float32=0, quantize=0, dequantize=0`, 才能写成 native INT8 hot path。

## 2. 当前研究结论

### 2.1 FP16 推理加速不明显的原因

FP16 历史上没有明显快于 FP32, 主要不是因为 FP16 理论上不能加速, 而是:

```text
default FP16 full-engine 虽然 dtype 是 FP16, 但 TVM 默认 lowering 没有把主要耗时的 conv/group conv 自动降到 TensorCore fast path。
```

当前证据:

| 证据 | 结果 | 结论 |
|---|---:|---|
| default lhc_07 FP16 full engine | `wmma=0`, `tvm_mma_sync=0` | default FP16 engine 不是 TensorCore engine |
| 1x1 rewritten full engine | `wmma=468`, `tvm_mma_sync=13`, 但 rewritten 更慢 | TVM 能在 full engine 产生 TensorCore, 但 1x1 rewrite 不是加速解 |
| 3x3/group conv 单层 | 已观察到约 `7x-14x` 单层加速 | group conv 是主要加速空间 |
| lhc_07 group-conv真实 full-engine rewrite | `33.4367 ms -> 22.2563 ms`, speedup `1.5024x`, `wmma=72`, `tvm_mma_sync=2` | 图内真实加速已经在 sm89 结构验证中证明, 但不是 H800 final row |

准确表述:

```text
FP16 default route 不快, 是因为默认 lowering 没有自动进入 TensorCore fast path。
当前已经证明 lhc_07 的主要 group conv 做 same-signature TensorCore rewrite 后, 可以在 full-engine 图内产生真实 latency 加速。
剩余问题不是“FP16 能不能加速”, 而是 H800/sm90 复测和 rewritten full-engine AP-safe 正确性还没有收口。
```

### 2.2 FP16 当前正确性问题

当前 lhc_07 group-conv full-engine rewrite 的速度侧已经有结构证据, 但 correctness 仍未闭环。主要问题是 output2 drift。

最新诊断:

| 诊断 | 结果 | 解释 |
|---|---:|---|
| no-TVM im2col/group/padding/restore 映射自测 | direct group conv vs im2col restore `max_abs_err=1.86e-09` | 基础 index/group/padding/restore 不是明显错位 |
| 真实 lhc_07 candidate 采样映射 | 4 个 group-conv candidate 的 x/w/b mismatch 均为 0 | 权重/输入/bias 展开映射没有发现 gross bug |
| same-signature scale sweep | 不启用 TensorCore 时仍有 scale-dependent error | drift 不应简单归因于 TensorCore intrinsic |
| FP16 vs FP32 accumulation compare | FP32 accumulation 一致降低 mean_rel, 但不能消除差异 | 更像 reduction/order/rounding 组织差异 |

当前更可信根因:

```text
same-signature im2col/matmul replacement 与 default TOPI group_conv 的 reduction 组织不同。
FP16 非结合性和舍入顺序差异会导致 replacement 输出与 default TIR 有差异; full engine 中该差异会被 residual/conv 继续传播并放大到 output2。
FP32 accumulation 可以缓解, 但不能自动完全对齐 default TOPI 的 loop/reduction/rounding 组织。
```

因此下一步不能只看 kernel latency, 必须同时推进:

```text
1. H800/sm90 rewritten full-engine speed gate;
2. default-like reduction/order 或 partial AP-safe callsite rewrite;
3. lhc_07 rewritten AP smoke/full-val bridge。
```

### 2.3 INT8 之前推理加速不明显的原因

INT8 历史上慢的原因与 FP16 不同。INT8 之前的问题更偏 route/lowering:

```text
旧 INT8 route 实际更接近 QDQ-heavy / float32-heavy lowering, hot path 里仍残留 QuantizeLinear/DequantizeLinear 或 float32-heavy 运算。
```

native INT8 route 已经证明 TVM 可以 build/run INT8 backbone/subnet:

| route | label | latency_ms | energy_J | lowering gate |
|---|---|---:|---:|---|
| native INT8 smoke | `base` | 0.508514 | 0.144209023342 | `float32=0, quantize=0, dequantize=0` |
| native INT8 smoke | `s0_024` | 0.450200 | 0.128370079340 | `float32=0, quantize=0, dequantize=0` |
| native INT8 smoke | `s1_048` | 0.189394 | 0.046026392511 | `float32=0, quantize=0, dequantize=0` |
| native INT8 full ONNX topology | `base` | 11.095775 | 2.853151923181 | `float32=0, quantize=0, dequantize=0` |
| native INT8 full ONNX topology | `s0_024` | 9.235392 | 2.290300810919 | `float32=0, quantize=0, dequantize=0` |
| native INT8 full ONNX topology | `s1_048` | 8.109461 | 2.118255342182 | `float32=0, quantize=0, dequantize=0` |

准确表述:

```text
INT8 速度 route 问题已经从旧 QDQ/float32-heavy 推进到 native INT8/full ONNX topology。
INT8 当前主要缺口不是“TVM 能不能 build INT8 route”, 而是 scale-aware 数值、head/postprocess bridge、AP smoke/full-val 是否能稳定收口。
```

## 3. FP16 与 INT8 加速不明显的根因区别

| 维度 | FP16 | INT8 |
|---|---|---|
| 历史表象 | latency 与 FP32 接近 | latency 没有明显收益 |
| 根因类型 | dtype 是 FP16, 但默认 lowering 没有进 TensorCore | 旧 route 是 QDQ-heavy/float32-heavy, 不是真 native INT8 hot path |
| 关键 gate | full-engine TIR 中 `wmma/tvm_mma_sync > 0` | lowering inventory `float32=0, quantize=0, dequantize=0` |
| 已证明内容 | lhc_07 group-conv rewrite 在 sm89 full-engine 中 `33.4367 ms -> 22.2563 ms` | native INT8 smoke/full ONNX topology 已有 latency+energy route |
| 当前风险 | output2 drift, AP-safe 未收口, H800/sm90 未复测 | scale-aware 精度、prediction 非空、AP30/AP50/AP70 趋势 |
| 下一步重点 | H800 full-engine TensorCore rewrite + AP-safe | native INT8 AP/full-val + head/postprocess 分布解释 |

一句话区分:

```text
FP16 是“默认 FP16 没有自动走 TensorCore fast path”。
INT8 是“旧 INT8 route 不是 native INT8 hot path, 而是 QDQ/float32-heavy lowering”。
```

## 4. 如何实现端到端图里的真实加速

### 4.1 不能接受的伪加速

```text
只给单层 kernel 加速, 没有 full-engine rewritten binary。
只给 counterfactual latency, 写成真实 rewritten engine。
只看到 dtype=fp16/int8, 但 TIR/lowering 没有 fast path。
FP16 default engine 没有 wmma/tvm_mma_sync, 却写成 TensorCore engine。
INT8 旧 QDQ/static route 被写成 native INT8。
sm89/RTX4090 结构诊断被写成 H800/sm90 实测。
AP 或 output error 未解释, 直接扩展 original60。
```

### 4.2 FP16 图内加速路线

目标:

```text
在 full-engine backbone/subnet TVM module 的 main graph 中替换热点 group conv,
生成包含 TensorCore TIR 的 rewritten binary,
并在同脚本、同设备、同输入口径下证明 end-to-end latency_ms 降低。
```

执行路径:

1. 从 default full-engine 中定位热点 group conv PrimFunc 和 callsite。
2. 只对 shape/signature 完全匹配的热点 PrimFunc 做 replacement, 避免 fuse 名称漂移导致误替换。
3. replacement 必须保持 same-signature, main graph 不得引入额外 layout copy 或 host fallback。
4. 对 replacement 做 TensorCore schedule, build 后检查 `wmma/tvm_mma_sync`。
5. 直接运行 rewritten full-engine end-to-end latency, 不使用 counterfactual 替代真实结果。
6. 保存 default/rewrite TIR、lowered IRModule、compiled artifact、command/stdout/stderr、output error、AP smoke/full-val。

FP16 下一步判定:

```text
只有 rewritten full-engine 在 H800/sm90 上同时满足:
1. latency_ms 明显低于 default;
2. rewritten TIR 有 wmma/tvm_mma_sync;
3. output error/AP smoke 可接受;
才可以写成可扩展的 FP16 端到端图内加速路线。
```

### 4.3 INT8 图内加速路线

目标:

```text
构建 native INT8/full ONNX topology route, 让 hot path 中不再残留 QuantizeLinear/DequantizeLinear 和 float32-heavy lowering。
```

执行路径:

1. 保持 native full ONNX topology route, 不回退旧 static/QDQ route。
2. build 后先查 lowering inventory:
   - `float32=0`
   - `quantize=0`
   - `dequantize=0`
   - int8/int32 accumulation 符合预期
3. 在同设备同脚本下测 latency_ms 与 energy_J。
4. 再做 AP smoke/full-val, 重点检查:
   - prediction 非空
   - AP30/AP50/AP70 合理非零趋势
   - head/postprocess 分布与 FP16/FP32 baseline 可解释
5. 若 AP 崩溃, 优先查 scale-aware requant、Add/ReLU scale 对齐、output dequant、head/postprocess bridge。

INT8 下一步判定:

```text
只有 native INT8 route 同时满足:
1. lowering inventory 干净;
2. latency_ms/energy_J 有实测;
3. AP30/AP50/AP70 非空且趋势合理;
4. head/postprocess 分布可解释;
才可以写成 INT8 端到端图内加速路线。
```

### P2: FP16 rewritten AP-safe bridge

当前缺口:

```text
已有 PyTorch true FP16 AP 脚本, 但它不等价于 TVM rewritten full-engine AP。
```

执行顺序:

1. 审计现有 AP pipeline, 明确哪些脚本只测 PyTorch true FP16, 哪些能接 TVM 输出。
2. 参考 INT8 real activation/head-postprocess bridge, 为 FP16 rewritten full-engine 建立同样的 output bridge。
3. 对 lhc_07 跑 rewritten AP smoke:
   - default FP16-cast baseline AP30/AP50/AP70
   - rewritten AP30/AP50/AP70
   - prediction 数量
   - score/box 分布
   - output0/output1/output2 error
4. 如果 AP 可接受, 再扩展 original60。
5. 如果 AP 不可接受, 不停止; 回到 reduction/order/default-like schedule 或 partial AP-safe callsite rewrite。

保持 native full ONNX topology route, 不回退 QDQ/static route。

```text
latency_ms
energy_J
lowering inventory
prediction 是否非空

raw artifact/TIR/command/stdout/stderr/traceback
```

### P4: 扩展到 original60

只有在 lhc_07 FP16 和 INT8 smoke 都通过后, 才扩展到 full original60。

每个配置最终必须有:

| 字段 | FP16 | INT8 |
|---|---|---|
| latency_ms | H800/sm90 full-engine 实测 | H800/sm90 native route 实测 |
| energy_J | 与 latency 同 route 测量 | 与 latency 同 route 测量 |
| TIR/lowering gate | `wmma/tvm_mma_sync` | `float32=0, qdq=0` |
| AP | AP30/AP50/AP70 | AP30/AP50/AP70 |

### 9.2 发现并修复 selective tensorization 判定问题

首次 H800 full suite 得到:


这说明真实 full-engine rewrite 已经加速, 但不满足 59 号文档要求的 TensorCore gate。

根因:

```text
_apply_selective_matmul_tensorization 依赖 func.attrs["s_tir"] 判断 TIR PrimFunc。
远端 TVM 0.20 生成的 PrimFunc 没有该 attr, 导致所有 TIR PrimFunc 被标为 skipped_non_tir。
replacement 中实际存在 T.sblock("matmul"), 但提前被跳过, 所以 wmma/tvm_mma_sync=0。
```

修复:

```text
scripts/stage2_fp16_tensorcore_convblock_and_engine_probe.py
删除 _apply_selective_matmul_tensorization 中对 attrs["s_tir"] 的硬依赖, 改为只要对象有 script() 就进入文本判定。
```
