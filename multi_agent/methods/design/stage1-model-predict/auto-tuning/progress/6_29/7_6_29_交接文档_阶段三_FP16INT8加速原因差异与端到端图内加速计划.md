# 61_6_29 交接文档: 阶段三 FP16/INT8 加速原因差异与端到端图内加速计划

日期: 2026-06-29

本交接文档用于清空上下文后继续推进 `original60` 三精度实测中的量化加速问题。当前最重要结论是:

1. **FP16 推理加速不明显的直接原因不是 H800/TVM 不能生成 TensorCore, 而是 default full-engine 的主要耗时算子没有进入 TensorCore fast path。**
2. **INT8 之前推理加速不明显的原因主要是 QDQ-heavy / float32-heavy lowering, 后续 native INT8 route 已经证明 TVM/H800 可以 build/run INT8 backbone/subnet route。**
3. **下一阶段的核心目标不再是解释量化为什么不快, 而是把 FP16/INT8 的快路径真正嵌入完整 backbone/subnet graph, 产出真实 rewritten/full-topology engine 的 latency_ms、energy_J、TIR/lowering 证据和输出误差/AP 证据。**

## 1. 固定规则和口径

1. latency 对外统一使用 `ms`。
2. 当前速度口径是 **H800 TVM compiled backbone/subnet module end-to-end**, 输入为 `spatial_features`, 输出为 backbone/subnet multiscale feature。
3. 所有 row 和文档继续写 `full_network_claim=false`; 不能写成完整 perception pipeline latency, 也不能写成真实 RSU 物理边缘设备绝对速度。
4. 只有完整 engine 自身出现 `wmma/tvm_mma_sync` 并完成 build/run/latency/输出误差后, 才能写成 `FP16 TensorCore full-engine measured`。
5. counterfactual 只能写成 `measured counterfactual`, 不能写成真实 rewritten engine latency。
6. 本轮可访问 FP16 实验使用的是本地 coverage FP32 ONNX 加 `--cast-fp16-source` 生成的 FP16-cast ONNX; 不得写成直接复用了 `/exdata` 原始 FP16 ONNX。
7. 遇到 build/import/eval/TVM/schedule 问题时, 必须保存 raw artifact、command、stdout/stderr、traceback、TIR/script、失败 op/name/shape, 做最小复现后继续推进。

## 2. 当前最可信研究结论

### 2.1 FP16: 加速不明显的原因

当前 FP16 的核心问题是:

```text
default full-engine dtype 虽为 FP16, 但主要耗时 conv/group conv 没有自动 lower 到 TensorCore fast path。
```

直接证据:

| 证据 | 结果 | 解释 |
|---|---:|---|
| default lhc_07 FP16 full engine | `wmma=0`, `tvm_mma_sync=0` | 完整默认 engine 不是 TensorCore engine |
| 真实 1x1 convblock matmul 化 | `wmma=36`, `tvm_mma_sync=1` | H800/TVM 可以稳定生成 FP16 TensorCore |
| all-1x1 counterfactual | 约 `0.076 ms`, `1.004x` | 1x1 能 tensorize, 但不是主要端到端瓶颈 |
| 1x1 rewritten full engine | `wmma=468`, `tvm_mma_sync=13`, 但 `42.5305 ms` 慢于 default `38.5926 ms` | 1x1 ONNX rewrite 引入 transpose/reshape/runtime overhead, 不是加速解 |
| 两个 3x3/group conv full im2col 单层 | `7.635x` 和 `14.239x` | 主要 group conv 有真实 TensorCore 加速空间 |
| group conv full-engine counterfactual | default `32.6908 ms`, counterfactual `29.8747 ms`, delta `2.8161 ms`, `1.0943x` | 如果替换能嵌入 full engine, 有可观端到端收益 |
| 最新真实 full-engine group-conv rewrite | `replace_records=2`, `wmma=72`, `tvm_mma_sync=2`, rewritten `22.2563 ms` 快于 default `33.4367 ms` | 已证明 group conv TensorCore rewrite 可以显著降低 full-engine latency, 但 output2 误差仍需解释/校准 |

因此 FP16 与 FP32 速度接近的解释应写成:

```text
FP16 只是 dtype 进入了 full engine, 但 default lowering/schedule 未把主要耗时算子送入 TensorCore。
单层、反事实和真实 rewritten full-engine 实验已经证明 TensorCore 对目标算子有效; 当前缺口从“能否命中 full-engine rewrite”推进为“如何让 rewritten full-engine 的 output2 误差可解释/可接受”。
```

### 2.2 INT8: 之前加速不明显的原因

INT8 之前的主要问题不是 TVM/H800 天然不能跑 INT8, 而是旧 route 更像:

```text
static QDQ artifact + float32-heavy lowered graph
```

典型证据来自早期 QDQ route:

- ONNX 中大量 `QuantizeLinear/DequantizeLinear`。
- lowered inventory 中仍有大量 `float32` token。
- 手工 lowering 证据能看到 `dequantize*` 和 `fused_conv*_quantize*_dequantize*`。

后续 native INT8 smoke 和 full ONNX topology route 已证明:

| route | label | latency_ms | energy_J | dtype/QDQ gate |
|---|---|---:|---:|---|
| native INT8 smoke | `base` | 0.508514 | 0.144209023342 | `float32=0`, `quantize=0`, `dequantize=0` |
| native INT8 smoke | `s0_024` | 0.450200 | 0.128370079340 | `float32=0`, `quantize=0`, `dequantize=0` |
| native INT8 smoke | `s1_048` | 0.189394 | 0.046026392511 | `float32=0`, `quantize=0`, `dequantize=0` |
| native INT8 full ONNX topology | `base` | 11.095775 | 2.853151923181 | `float32=0`, `quantize=0`, `dequantize=0` |
| native INT8 full ONNX topology | `s0_024` | 9.235392 | 2.290300810919 | `float32=0`, `quantize=0`, `dequantize=0` |
| native INT8 full ONNX topology | `s1_048` | 8.109461 | 2.118255342182 | `float32=0`, `quantize=0`, `dequantize=0` |

因此 INT8 的当前状态应写成:

```text
速度 route 已经从 QDQ/float32-heavy 推进到 native INT8/full ONNX topology 证据;
但 AP/数值侧仍需要 scale-aware requant/Add/ReLU/output dequant/head-postprocess bridge 收口。
```

## 3. FP16 与 INT8 加速不明显原因的区别

| 维度 | FP16 当前问题 | INT8 之前问题 |
|---|---|---|
| 表象 | precision 变为 FP16, 但 latency 与 FP32 接近 | precision 变为 INT8, 但早期 latency 没有明显收益 |
| 核心原因 | default full-engine 主要 conv/group conv 没有进入 TensorCore fast path | 旧 route 是 QDQ-heavy / float32-heavy lowering, 不是 native INT8 hot path |
| 快路径证据 | 单个 1x1、group conv im2col、full im2col 单层均已出现 `wmma/tvm_mma_sync` | tiny INT8 conv、ResNet-style block、target/full ONNX topology native INT8 route 已 build/run |
| 当前工程缺口 | 把 3x3/group conv TensorCore 替换真正嵌入 full engine, 让 rewritten full engine 自身产生 WMMA 并变快 | scale-aware 数值一致性、AP 非空且有合理 AP30/AP50/AP70 趋势 |
| 主要下一步 | full-engine TIR/Relax rewrite + selective TensorCore schedule + 输出误差 gate | INT8 AP smoke/full-val + requant/Add/ReLU/output dequant/head-postprocess bridge |
| 不能再犯的错误 | 把 counterfactual 或 default FP16 engine 写成 TensorCore measured | 把 QDQ/static route 或 AP=0 route 写成 native INT8 精度已解决 |

共同点:

```text
不能只看 precision 字段; 必须看 lowering/TIR/runtime 证据。
FP16 看 wmma/tvm_mma_sync; INT8 看 native int8/int32 accumulation、QDQ/float32 token、route identity、AP 数值 gate。
```

## 6. 下一步如何实现端到端图里的真实加速

### P0: 先冻结现有结论, 禁止错误归因

必须写清:

1. FP16 default full engine 没有 TensorCore 证据, 不能称为 TensorCore engine。
2. FP16 group conv counterfactual 证明有收益空间, 但不是 rewritten full engine。
3. 当前 `fp16_lhc07_full_engine_group_conv_rewrite_latest` 已是成功 build/run 的真实 rewritten full-engine: `replace_records=2`, `wmma=72`, `tvm_mma_sync=2`, latency 从 `33.4367 ms` 降到 `22.2563 ms`, speedup `1.5024x`。
4. 该 rewritten full-engine 仍不能直接视为 AP-safe final engine: output0/output1 完全一致, 但 output2 `max_abs_err=0.7744`, `mean_abs_err=0.08119`, `mean_err/orig_mean=0.1934`, 需要 callsite-aware 或 AP smoke 解释。
5. one-PrimFunc filter 对照已完成: downsample-only `2.0454 ms / 1.0652x`, output2 mean relative error `0.0474`; repeated-only `9.3440 ms / 1.3932x`, output2 mean relative error `0.1900`。主要速度收益和主要误差都来自 repeated `fused_conv2d16_add8_relu6`。
4. INT8 早期慢的主要原因是 QDQ/float32-heavy; 现在 native latency/energy route 已打通, 但 AP 精度侧仍未完整收口。

### P1: FP16 真实 full-engine group conv rewrite

目标:

```text
把 lhc_07 full engine 中真实耗时的 group=32 3x3 conv PrimFunc 替换为同签名 im2col + TensorCore MatMul + NCHW restore 实现, 并将 output2 误差收口到可解释/可接受。
```

当前已解决的问题:

```text
历史名 `fused_conv2d4_add10_relu6` / `fused_conv2d6_add10_relu6` 不等于当前 full-engine legalize/fuse 后的 PrimFunc 名。
当前已按 PrimFunc script shape 命中 `fused_conv2d12_add8_relu6` 和 `fused_conv2d16_add8_relu6`。
真实 rewritten full engine 已有 TensorCore 和 latency 加速证据。
```

下一步执行:

1. 不再重复证明 replace/tensorcore/speed gate, 先以当前结果为基线:
   - default `33.4367 ms`, rewritten `22.2563 ms`, speedup `1.5024x`。
   - `wmma=72`, `tvm_mma_sync=2`。
   - replaced: `fused_conv2d12_add8_relu6`, `fused_conv2d16_add8_relu6`。
2. 做 correctness 收口:
   - 已完成 one-PrimFunc filter: downsample-only 和 repeated-only。
   - 下一步做 callsite-aware rewrite: 只替换 `fused_conv2d16_add8_relu6` 的部分 callsite, 记录它在 main 中的 callsite 数和每个 callsite 的输出影响。
   - 若单层差异小但 full output2 差异大, 解释为 repeated multi-callsite + 后续 residual/conv 放大, 并补 AP smoke 判断业务影响。
   - 若某个单 block 已有大误差, 回到 im2col indexing、bias/ReLU、padding/stride 或 accumulation dtype 继续修。
3. 保存:
   - rewritten unscheduled IRModule。
   - selective scheduled IRModule。
   - generated `.so`。
   - TIR counts: `wmma/tvm_mma_sync/mma.sync/ldmatrix/conv2d/matmul`。
   - `replace_records`。
   - 输出 shape、max_abs_err、mean_abs_err、original_abs_max/original_abs_mean、相对误差。
   - latency_ms。

验收:

| gate | pass 条件 |
|---|---|
| replace gate | 已通过: `replace_records=2` |
| TensorCore gate | 已通过: rewritten full engine 自身 `wmma=72`, `tvm_mma_sync=2` |
| correctness gate | 未完全通过: output2 相对误差需解释/校准 |
| speed gate | 已通过: rewritten `22.2563 ms` 小于同脚本同 GPU default `33.4367 ms` |
| artifact gate | raw TIR/IRModule/.so/stdout/stderr/traceback 全部保存 |

### P2: 如果 same-signature PrimFunc 替换仍失败

不要停止, 按以下顺序反思和推进:

1. 检查目标 PrimFunc 是否被多处 call_tir 复用; 如果一个 PrimFunc 多 callsite 复用, 记录每个 callsite 的 shape 和影响。
2. 如果 TE same-signature PrimFunc 无法被 TensorCore scheduler 识别, 改成 Relax graph-level 插入:
   `call_tir(im2col_materialize) -> matmul TensorCore -> call_tir(restore_nchw)`。
3. 如果 Relax main 参数/shape 对不上, 先只替换一个 target block, 产出 one-block rewritten full engine。
4. 如果 full-engine build 成功但不快, 对比 kernel launch 数、transpose/layout copy、VM overhead、conv2d 残留数量。
5. 如果 full-engine rewrite 仍不可行, 必须给出明确 blocker:
   op/name/shape、失败 pass、traceback、最小复现脚本、下一条可行路线。

### P3: INT8 端到端图内加速和 AP 收口

INT8 下一步不是再证明 TVM 能 build INT8, 而是:

1. 保持 native full ONNX topology latency/energy route, 不回退到 QDQ/static route。
2. 对 5 个 original60 配置点做 AP smoke:
   `s0_040`, `s0_024`, `s0_056`, `s1_048`, `s2_160`。
3. 按 gate 运行:
   `numeric_sanity -> 5-sample AP smoke -> full AP`。
4. 精度收口标准:
   - prediction 非空。
   - AP30/AP50/AP70 有合理非零趋势。
   - head/postprocess 分布与 FP16 baseline 可解释。
5. 如果 AP 恢复但 TIR 仍有 float32-heavy requant/Add, 不能宣称最终 native INT8 全部完成; 需要继续 fixed-point multiplier/shift 收口。
