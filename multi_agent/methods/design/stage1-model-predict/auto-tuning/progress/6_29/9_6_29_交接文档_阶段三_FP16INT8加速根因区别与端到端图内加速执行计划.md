## 1. 固定口径

1. latency 对外统一使用 `ms`。
2. 当前速度口径是 TVM compiled backbone/subnet module end-to-end, 输入为 `spatial_features`, 输出为 backbone/subnet 多尺度 feature。
3. `full_network_claim=false`; 不能写成完整 perception pipeline latency, 也不能写成真实 RSU 边缘物理设备绝对速度。
4. 每次实测必须记录 `nvidia-smi` 与 TVM target。当前一批 FP16 rewrite 诊断的 target 是 `sm_89/RTX4090`, 因此只能作为结构诊断; 如果总表/论文要求 H800 口径, 必须在 H800/sm90 重跑。
5. 不能把 default FP16 engine 写成 TensorCore engine。只有 rewritten full-engine 自身出现 `wmma/tvm_mma_sync` 且完成 build/run/latency/输出误差, 才能写成 FP16 TensorCore measured。
6. 不能把 counterfactual 写成真实 rewritten binary。
7. INT8 只有 native full ONNX/topology route 且 lowering inventory 满足 `float32=0, quantize=0, dequantize=0`, 才能写成 native INT8 hot path。

## 2. 当前研究结论

### 2.1 FP16 推理加速不明显的原因

FP16 历史上没有明显快于 FP32, 直接原因是:

```text
default FP16 full-engine 虽然 dtype 是 FP16, 但主要耗时的 conv/group conv 没有自动 lower 到 TensorCore fast path。
```

关键证据:

| 证据 | 结果 | 结论 |
|---|---:|---|
| default lhc_07 FP16 full engine | `wmma=0`, `tvm_mma_sync=0` | default FP16 engine 不是 TensorCore engine |
| 1x1 rewritten full engine | `wmma=468`, `tvm_mma_sync=13`, latency 反而慢 | TVM 能在 full engine 产生 TensorCore, 但 1x1 rewrite 不是加速解 |
| 两个 3x3/group conv 单层 | `7.6350x` 和 `14.2388x` | group conv 是主要加速空间 |
| lhc_07 group-conv真实 full-engine rewrite | `33.4367 ms -> 22.2563 ms`, `1.5024x`, `wmma=72`, `tvm_mma_sync=2` | 图内真实加速已经被证明, 但还不是 AP-safe final |

因此准确表述是:

```text
FP16 default route 不快, 是因为默认 lowering 没有自动进入 TensorCore fast path。
目前已经证明对 lhc_07 主要 group conv 做 same-signature TensorCore rewrite 可以在 full-engine 图内真实加速。
剩余问题不是“能不能加速”, 而是 rewritten full-engine 的 output2 误差和 AP-safe 是否能收口。
```

### 2.2 FP16 当前正确性问题的最新定位

最新诊断显示, output2 漂移不是单一 outlier callsite 或 TensorCore intrinsic 单独造成的。

| 诊断 | 结果 | 解释 |
|---|---:|---|
| repeated callsite 单点替换 | 每个 callsite 都降 latency, 同时都有 output2 drift | 不是单个异常 callsite |
| cumulative callsite 替换 | callsite 越多, latency 总体下降, output2 mean_rel 总体上升到约 `0.18326` | 更像多 callsite 误差叠加或下游 residual/conv 放大 |
| intermediate debug | 单个 callsite 的即时输出 already drift, mean_rel `0.08385-0.15544` | replacement 本身已有可见差异 |
| same-signature scale sweep | 不启用 TensorCore 时仍有 scale-dependent error, scale 1.0 mean_rel `0.15071` | 根因更偏向 FP16 reduction/order 数值差异 |
| FP16 vs FP32 accumulation compare | scale 1.0 mean_rel 从 `0.13976` 改善到 `0.10620`, scale 2.0 从 `0.15455` 改善到 `0.11415` | FP32 accumulation 能缓解, 但不能完全消除与 default TOPI group conv 的差异 |

最新更可信根因:

```text
same-signature im2col/matmul replacement 与 default TOPI group_conv 的 reduction 组织不同。
FP16 非结合性和舍入顺序差异导致 replacement 输出与 default TIR 出现差异; full engine 中该差异经 residual/conv 继续传播。
FP32 accumulation 可以降低误差, 但由于 default TIR 本身也有特定 loop/reduction/rounding 组织, 仅改 FP32 accumulation 不能自动完全对齐 default 输出。
```

下一步不要优先把问题归因于 TensorCore intrinsic。更合理的顺序是:

```text
先做 default-order accumulation / default-like schedule 对照;
再做 AP smoke 判断当前误差是否实际影响检测 AP;
如果 AP 不可接受, 再局部修 replacement 的 reduction/order 或只启用 AP-safe callsite。
```

### 2.3 INT8 之前推理加速不明显的原因

INT8 历史问题与 FP16 不同。INT8 之前慢的主要原因是 route/lowering 走错:

```text
旧 INT8 route 更接近 QDQ-heavy / float32-heavy lowering, hot path 中仍有 QuantizeLinear/DequantizeLinear 或 float32-heavy 残留。
```

native INT8 route 已经证明 TVM 可以 build/run INT8 backbone/subnet:

| route | label | latency_ms | energy_J | lowering gate |
|---|---|---:|---:|---|
| native INT8 smoke | `base` | 0.508514 | 0.144209023342 | `float32=0, quantize=0, dequantize=0` |
| native INT8 smoke | `s0_024` | 0.450200 | 0.128370079340 | `float32=0, quantize=0, dequantize=0` |
| native INT8 smoke | `s1_048` | 0.189394 | 0.046026392511 | `float32=0, quantize=0, dequantize=0` |
| native INT8 full ONNX topology | `base` | 11.095775 | 2.853151923181 | `float32=0, quantize=0, dequantize=0` |
| native INT8 full ONNX topology | `s0_024` | 9.235392 | 2.290300810919 | `float32=0, quantize=0, dequantize=0` |
| native INT8 full ONNX topology | `s1_048` | 8.109461 | 2.118255342182 | `float32=0, quantize=0, dequantize=0` |

因此准确表述是:

```text
INT8 速度 route 问题已经从旧 QDQ/float32-heavy 推进到 native INT8/full ONNX topology。
INT8 当前主要缺口不是“TVM 能不能 build INT8 route”, 而是 scale-aware 数值、head/postprocess bridge、AP smoke/full-val 是否能收口。
```

## 3. FP16 与 INT8 慢的根因区别

| 维度 | FP16 | INT8 |
|---|---|---|
| 历史表象 | latency 与 FP32 接近 | latency 没有明显收益 |
| 根因类型 | dtype 是 FP16, 但默认 lowering 没有进 TensorCore | route 是 QDQ-heavy/float32-heavy, 不是真 native INT8 hot path |
| 关键 gate | full-engine TIR 中 `wmma/tvm_mma_sync > 0` | lowering inventory `float32=0, quantize=0, dequantize=0` |
| 已证明内容 | lhc_07 group-conv rewrite 可让 full-engine `33.4367 ms -> 22.2563 ms` | native INT8 smoke/full ONNX topology 已有 latency+energy route |
| 当前风险 | output2 drift, AP-safe 未收口 | scale-aware 精度、prediction 非空、AP30/AP50/AP70 趋势 |
| 下一步重点 | default-like reduction/order 或 AP-safe callsite + H800 重跑 + AP smoke | AP full-val/smoke 补点 + head/postprocess 数值分布解释 |

一句话区分:

```text
FP16 是“默认 FP16 没有自动走 TensorCore fast path”。
INT8 是“旧 INT8 route 不是 native INT8 hot path, 而是 QDQ/float32-heavy lowering”。
```

## 4. 端到端图内加速应该如何实现

### 4.1 FP16 图内加速路线

目标不是单层 kernel 快, 而是:

```text
在 full-engine backbone/subnet TVM module 的 main graph 中替换热点 group conv,
生成包含 TensorCore TIR 的 rewritten binary,
并在同脚本、同设备、同输入口径下证明 end-to-end latency_ms 降低。
```

执行路径:

1. 从 default full-engine 中定位热点 group conv PrimFunc 和 callsite。
2. 只对 shape/signature 完全匹配的热点 PrimFunc 做 replacement, 避免 fuse 名称漂移导致误替换。
3. replacement 必须保持 same-signature, main graph 不得引入额外 layout copy 或 host fallback。
4. 对 replacement 做 TensorCore schedule, build 后检查 `wmma/tvm_mma_sync`。
5. 对 rewritten full-engine 直接运行 end-to-end latency, 不使用 counterfactual 替代真实结果。
6. 同时保存:
   - default/rewrite TIR
   - lowered IRModule
   - compiled artifact
   - command/stdout/stderr/traceback
   - output0/output1/output2 error
   - AP smoke 或 AP full-val

当前 lhc_07 已经满足速度侧第 1-5 步, 但 correctness/AP-safe 还没有收口。

### 4.2 INT8 图内加速路线

目标不是保留 QDQ ONNX 然后期待 TVM 自动变快, 而是:

```text
构建 native INT8/full ONNX topology route, 让 hot path 中不再残留 QuantizeLinear/DequantizeLinear 和 float32-heavy lowering。
```

执行路径:

1. 保持 native full ONNX topology route, 不回退旧 static/QDQ route。
2. build 后先查 lowering inventory:
   - `float32=0`
   - `quantize=0`
   - `dequantize=0`
   - int8/int32 accumulation 符合预期
3. 在同设备同脚本下测 latency_ms 与 energy_J。
4. 再做 AP smoke/full-val, 重点检查:
   - prediction 非空
   - AP30/AP50/AP70 合理非零趋势
   - head/postprocess 分布与 FP16/FP32 baseline 可解释
5. 若 AP 崩溃, 优先查 scale-aware requant、Add/ReLU scale 对齐、output dequant、head/postprocess bridge。

## 5. 下一步执行计划

### P0: 冻结证据和设备口径

1. 把现有 `sm_89/RTX4090` FP16 rewrite 产物标注为结构诊断, 不写入 H800 总表最终口径。
2. 在目标 H800/sm90 环境重跑 lhc_07:
   - default FP16 full-engine
   - all group-conv rewrite
   - repeated-only
   - downsample-only
   - cumulative callsite `0` 到 `0,1,2,3,4,5,6`
3. 每个结果都保存 latency_ms、TIR、target、raw artifact、output error。

验收:

```text
同一设备、同一脚本、同一输入口径下, rewritten latency_ms 明显低于 default, 且 rewritten TIR 中有 wmma/tvm_mma_sync。
```

### P1: FP16 correctness/AP-safe 收口

优先级顺序:

1. 做 default-order accumulation 或 default-like reduction schedule 对照, 判断是否能减少 output2 drift。
2. 做 FP32 accumulation hybrid 对照, 目前已看到误差下降但未完全消除:
   - scale 1.0: FP16 accumulation mean_rel `0.13976`, FP32 accumulation mean_rel `0.10620`
   - scale 2.0: FP16 accumulation mean_rel `0.15455`, FP32 accumulation mean_rel `0.11415`
3. 跑 lhc_07 FP16 rewritten AP smoke:
   - default FP16-cast baseline AP30/AP50/AP70
   - rewritten AP30/AP50/AP70
   - prediction 数量和 score/box 分布
4. 如果 AP 可接受, 记录为 AP-safe fast path 并扩展更多配置。
5. 如果 AP 不可接受, 不停止; 回到具体 op/name/shape/pass 修:
   - reduction/order
   - im2col indexing
   - padding/stride
   - group channel mapping
   - bias/ReLU 顺序
   - 只启用 AP-safe callsite 的 partial rewrite

### P2: FP16 扩展到 original60

只有 lhc_07 通过 speed gate 和 AP-safe gate 后再扩展。

每个配置必须输出:

| 字段 | 要求 |
|---|---|
| config_id | original60 配置名 |
| default_fp16_latency_ms | 同设备同脚本 default |
| rewritten_fp16_latency_ms | 同设备同脚本 rewritten |
| speedup | rewritten 相对 default |
| energy_J | 与 latency 同 route 测量 |
| TensorCore gate | `wmma/tvm_mma_sync` |
| correctness | output error 或 AP smoke |
| AP | AP30/AP50/AP70 |
| target | H800/sm90 或明确标注其他设备 |

### P3: INT8 AP/full-val 补点

保持 native full ONNX topology route, 不回退 QDQ/static route。

建议先跑 5 个点:

```text
s0_040
s0_024
s0_056
s1_048
s2_160
```

每点记录:

```text
latency_ms
energy_J
lowering inventory
prediction 是否非空
AP30/AP50/AP70
head/postprocess 分布
raw artifact/TIR/command/stdout/stderr/traceback
```

