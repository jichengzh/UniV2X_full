## 0. 一句话主张

本文框架不应叙述为“手写 INT8 算子打赢自动调优”，也不应叙述为“INT8/FP16 量化没有加速效果”。当前最有利且最符合项目事实的叙事是:

> 低精度和剪枝是否带来真实收益，取决于目标后端能否把对应配置送入正确的 TensorCore fast path，并以足够融合的方式执行。因此本文的方法贡献不是固定某个手写算子，而是把 P(结构)×Q(精度)×S(自动后端/调度)作为联合决策空间，用真实后端反馈驱动多目标搜索。

这句话同时解决三个矛盾:

1. Phase1 `int8_tc` 快，是旧 hand-rewrite family 的真实诊断结果，但它不等于最终自动框架的主后端。
2. Route B fp16 快，证明 TVM 自动后端并非不能利用 TensorCore；早期“FP16 无加速”的根因是没有走到正确 lowering/search/fix。
3. Route B-int8 auto-decomp v1 慢，不说明 INT8 TensorCore 不可用；它说明当前自动 INT8 实现形态仍有 padded accum、独立 pack/requant 和 unfused per-block 组合税。

## 2. 需要纠正的旧叙事

旧叙事的问题不是早期实验本身造假，而是解释层级过度外推。

早期 FP16/INT8 没有体现出应有加速，真实原因是主要耗时算子没有进入对应的 TensorCore/INT8-TC fast path。更准确地说:

- default/generic lowering 可以把 dtype 变成 fp16/int8，但不保证 hot grouped conv 进入 TensorCore fast path。
- generic/default MetaSchedule 路线确实曾经失败、很慢或组合崩溃，这个负结果是真实的。
- 当时为了证明 fast path 可行，手写 im2col+MMA 是合理诊断路线。
- 后续 12_7_14 的 Route B split-fix 证明，问题不是 TVM/H800 不支持，也不是 auto-tune 没有加速能力，而是早期没有走到正确自动后端路径。

所以旧表述应被替换:

| 不应再写 | 应改写为 |
|---|---|
| TVM 不支持 FP16/INT8 加速 | 早期/default lowering 未把主要耗时算子送入低精度 fast path |
| 量化没有加速效果 | 量化收益依赖 Q 与 S 的匹配，不能脱离后端实现形态判断 |
| 手写 im2col+MMA 是最终正解 | 手写 route 是诊断路线，证明 fast path 可行，但最终框架应采用自动后端 |
| Phase1 int8_tc 前沿就是最终 TVM auto-tune 前沿 | Phase1 int8_tc 是当时 hand-rewrite/measure_config 口径下的真实历史前沿，最终自动口径需重算或明确标注 |

## 3. 关键矛盾的统一解释

### 3.1 Phase1 hand-rewrite 很快 vs Route B-int8 v1 较慢

这不是同一后端的矛盾，而是后端实现形态不同。

- Phase1 `int8_tc` 的 `[24,32,96] = 1.779ms` 等结果，是 hand-rewrite family 下的真实测量/历史结果。
- Route B-int8 auto-decomp v1 的 `[24,32,96] = 3.599ms` 是自动 per-block 全图闭合后的真实结果。
- 两者都可以是真实的。区别在于 Phase1 route 更接近 fused/hand-engine 形态，而当前 Route B-int8 v1 为了 correctness 采用了 padded int32 accum、独立 pack/requant 和 163 个 unfused PrimFunc。

因此，正确结论不是“回退到手写算子”，而是:

> Phase1 hand-rewrite 证明了 fused INT8 rewrite shape 可以很快；Route B-int8 v1 证明自动暴露和 tensorize 可以闭合。下一步应把 hand-rewrite 中有效的融合/数据流思想转化为自动 rewrite/backend transformation，而不是把固定手写算子当成最终方法。

### 3.2 “手写不如 auto-tune”到底指什么

12_7_14 中“手写不如 auto-tune”指的是 base `[64,128,256]` fp16 full-engine route:

- hand-rewrite im2col TC:约 6.51ms，且 output_2 有 17-18% 错误。
- Route B auto-tune split-fix:约 3.53-3.56ms，正确性干净。

这不能直接外推成“任何 hand-rewrite INT8 都一定慢”。它只说明最终框架的主实现不应依赖那个 buggy fp16 hand full-engine route。对于 INT8，Phase1 hand-rewrite 的快值应作为诊断上界/设计启发，而不是最终自动主结果。

### 3.3 为什么 TRT 的 INT8/FP16 更容易表现为加速

TRT 也有 Q/DQ、scale、requant 和数值转换；区别不在于 TRT 没有转换，而在于 TRT 通常会把这些转换与 conv/bias/activation/residual 等区域融合，并通过 tactic selection 避免大量中间 materialization。

当前 Route B-int8 v1 的慢点恰好相反:

- `int8 accum` 和 `pack/requant` 是独立 PrimFunc。
- padded int32 accumulator 被显式写回，特别是小 `nper` grouped conv 被放大到 `nper_compute=128`。
- Relu/Add 等尾部没有并入 conv epilogue。
- full graph 由大量 per-block PrimFunc 组成，fusion 层级低于当前 Route B fp16 full-engine 路线。

所以不能写“TRT 没有量化转换所以快”。应写:

> TRT 的优势来自成熟的融合、scale propagation 和 tactic selection；转换存在，但多数情况下不以大量独立 kernel 和中间写回的方式暴露在热路径中。

同时也不能写“TRT INT8 绝对加速”。本项目现有 TRT 侧结果是小幅或 mixed 的，真正强结论是 TRT 可以通过真实后端反馈避开 width-trap，而不是 INT8 在 TRT 上无条件赢。

## 4. 底层理论支撑

低精度加速不是由 bitwidth 单独决定，而由以下近似模型决定:

```text
T_layer ~= max(F_ops / P_eff, Bytes / BW_eff) + T_launch + T_sync
```

INT8 只有在 TensorCore 有效算力收益超过额外开销时才会端到端加速。对本项目的 grouped conv，关键额外开销包括:

1. tile 利用率不足:小 per-group GEMM 的 `M/N/K` 可能低于 TensorCore tile 的有效粒度。
2. padding 放大:当前 auto-decomp v1 对小 `nper` 使用 `nper_compute=128`，使 accumulator 远大于真实输出。
3. accumulator materialization:int32 accum 写回比 uint8 输出重得多。
4. requant/pack 暴露:scale/zero-point/clip/cast 若成为独立 kernel，会吃掉低精度算力收益。
5. graph fusion 不足:Conv 后的 Relu/Add/residual 未进 epilogue，会增加 launch 和 memory traffic。

本轮 root-cause profiling 与该模型一致:

- base `[64,128,256]` isolated PrimFunc sum / VM latency = 0.973，说明慢因主要来自已暴露的 kernel 本身，而不是测量噪声。
- base Conv accum 占 65.1%，pack/requant 占 22.1%。
- padded int32 accumulator bytes / uint8 output bytes:base 31.3x，`[64,32,96]` 55.7x，`[32,32,128]` 73.6x，`[24,32,96]` 101.7x。
- `[24,32,96]` Route B-int8 v1 为 3.599ms，是 Phase1 旧 hand-rewrite/int8_tc 1.779ms 的 2.02x，符合“小宽度 padding 和 materialization 更重”的解释。

这给论文提供了理论边界:

> INT8 是搜索臂，而不是必胜臂。本文搜索框架的价值正是把 Q 的收益交给目标后端真实测量来判断，而不是用 bitwidth 或参数量 proxy 预设答案。

## 5. 最终推荐叙事

### 5.1 方法主线

论文主线应从“后端感知联合搜索”出发:

1. P 和 Q 的效果不是静态的。相同剪枝/量化配置在不同后端、不同 layout、不同 fusion 能力下会产生不同 latency/energy。
2. 因此本文将后端真实反馈纳入搜索，而不是先压缩再事后调度，也不是用 FLOPs/params/bitwidth proxy 替代真实硬件反馈。
3. S 轴不是我们手写 schedule 的所有权，而是“目标自动后端如何实际执行该配置”。TVM Route B、TRT builder、BYOC vendor backend 都可以是合法的 S 实现。
4. 本文贡献是联合选择 P×Q×S 下的配置，并以 AP/latency/energy 多目标方式形成 Pareto 或 arm comparison。

### 5.2 FP16 叙事

FP16 应作为“自动后端修复有效”的正例:

- default/no-MS fp16 p50 53.249ms。
- Route B auto-tune split-fix p50 3.558ms。
- speedup 14.97x，输出正确性可接受。
- hand-rewrite 6.51ms 且 output_2 错 17-18%，不能作为最终实现。

推荐写法:

> FP16 的早期失败来自错误的 lowering/search path，而不是硬件或 TVM 不支持。Route B split-fix 后，自动后端能够把 grouped conv 送入可用的 TensorCore 路线，并获得约 15x 的端到端加速。

### 5.3 INT8 叙事

INT8 应作为“机制可用但实现形态待优化”的边界例:

- native no-handrewrite 9/9 build 成功，旧 dp4a buildability wall 不是当前主矛盾。
- QDQ default lowering 不暴露 `wmma/mma_sync/tvm_mma_sync/dp4a`，不能算 INT8 TensorCore 后端。
- 单 block int8 matmul gate 可以 tensorize 并生成 `tvm_mma_sync`。
- Route B-int8 auto-decomp v1 base 全图闭合，49/50 Conv tensorized，correctness exact，快于 native direct INT8 和 fp32 no-tune，但慢于 Route B fp16。
- 慢因已定位到 padded accum、pack/requant、unfused per-block，而不是 INT8 TensorCore 机制失败。

推荐写法:

> INT8 在当前自动后端 v1 中尚未成为优于 FP16 的最终 Pareto 臂，但这不是量化搜索轴无效，而是 Q 与 S 的耦合没有优化到足够融合的实现形态。后续应将 INT8 从 per-block auto-decomp 推进到 fused/full-engine 等级，再用真实测量决定其 Pareto 价值。

### 5.4 TRT 叙事

TRT 不应被设为“需要被 TVM 打败的外部对手”，而应作为第二个自动后端/对比秤:

- 在 TVM 上验证 joint/co-design 相对 non-joint/serial/noS 的收益。
- 在 TRT 上验证同一个搜索思想是否仍能通过真实后端反馈避开 bad tactic 或 width-trap。
- 不跨 device/scope/precision 混比，不用“TVM 前沿支配 TRT”作为主命题。

推荐写法:

> We evaluate the search policy under multiple backend realizations rather than treating backend speed as the contribution itself.

## 9. 下一步实验策略

当前不建议只盲跑更多 Phase1 Pareto 点，因为 Route B-int8 v1 的慢因已经定位到实现形态。更合理的顺序是:

1. 先优化 Route B-int8 v2:
   - 融合 `pack/requant` 与 Relu/Add/epilogue。
   - 减少或避免小 `nper` group conv 的 `nper_compute=128` 无差别 padding。
   - 降低 int32 accumulator materialization。
   - 减少 per-block PrimFunc 数量，向 fp16 full-engine/fused Route B 靠近。
2. 再对 9-grid / Phase1 representative / Table 1 candidates 做同口径多点真测。
3. 最后根据真实 AP/latency/energy 判断:
   - INT8 是最终 Pareto 有利臂；
   - 还是特定宽度区域有利；
   - 还是在当前模型上作为慢值臂被搜索自然淘汰。

这一路线不会伤害自动搜索叙事。相反，它把“手写算子经验”降级为后端设计启发，把最终选择权交还给自动后端和真实硬件反馈，正好服务于本文的 co-design 主题。
