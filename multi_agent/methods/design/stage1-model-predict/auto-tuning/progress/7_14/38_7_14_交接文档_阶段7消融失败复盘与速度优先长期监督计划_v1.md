## 3. 为什么此前看起来做了很多工作，但消融仍是 0/192

### 3.1 把“完整理想框架”当成了“本轮快速消融”的启动前提

最初把尚未存在的 candidate-level capability scanner 设为 Full 的前置
门禁，导致四行核心组件消融被第五个、尚未实现的 scanner 组件阻塞。后续
虽然已经批准 scanner deferred，但旧合同的复杂度仍持续影响部署和恢复。

正确区分应为：

```text
本轮论文问题：
surrogate / measured feedback / backend features 是否有效

后续框架问题：
candidate-level capability scanner 是否有效
```

两者不应互相阻塞。

### 3.2 错误地认为“v3 全链路已通”等于“Stage7 无需接线”

actual-feedback v3 的真实测量原语是可用的，但 Stage7 仍需正确完成：

- selector request 到 Stage5/Stage3 physical request 的身份绑定；
- source checkpoint/ONNX/calibration 的解析；
- exact cache reveal 的时序；
- terminal wrapper 到 actual graph feedback 的回流；
- 四候选原子 feedback barrier；
- 下一轮 selector 输入。

此前先后暴露了 worker 未传 deployment pins、真实
`exact_selection_binding` schema 与 worker 预期不一致等接线问题。这些
属于 Stage7 适配缺陷，不应被解释为要重写一套 v3 框架。

### 3.3 no-GPU gate 与真实 source 之间形成循环依赖

冻结的 `w/o surrogate` 首轮候选中存在尚未物化的 source。如果要求：

```text
先完整 no-GPU exact admission
  → 才允许 source materialization
```

而 exact admission 又要求真实 source SHA，就会形成循环。后来通过
source-only 物化和真实 SHA 重绑定解决，证明该问题是流程顺序问题，不是
搜索算法问题。

### 3.4 “逻辑四候选一轮”被误写成“物理上必须四卡同时启动”

一轮四候选必须在 feedback 上保持原子性，但并不要求四个物理 job 同时
启动。此前 source-only 和部分正式调度把四卡同时可用作为前提，造成两张
或三张卡明明空闲却仍然等待。

正确语义是：

```text
逻辑合同：四个候选全部 terminal 后才能形成该轮 feedback
物理调度：四个候选可以按 1、2、3 或 4 张空闲卡分波执行
```

### 3.5 把等待命令、暂停进程和未来计划当成实际 GPU 占用

当前最直接的阻塞来自资源解析过度保守：

- 其他用户存在从 7 月 22 日起处于 `T` 状态的暂停 shell；
- 后续 shell 等待这些暂停进程结束；
- 更后级等待 shell 的未来命令行声明了多个 GPU；
- Stage7 将这条等待链上的未来 `--physical-gpu(s)` 参数解释为当前硬占用；
- 实际 `nvidia-smi` 显示空闲的 GPU2–GPU5 仍被判为不可用。

“将来可能使用某张卡”不等于“当前正在使用某张卡”。为了等待一个未知时间
才可能启动的外部命令，让当前真实空闲 GPU 数小时不工作，直接违背了本轮
“尽快完成消融”的目标。

### 3.6 为修补资源解析又创建 sentinel，最终阻塞了自己

为了防止 Stage7 抢占被认为已预留的 GPU，曾创建本实验自己的 reservation
sentinel：

```text
PID 1583206 → GPU0
PID 1583211 → GPU1
PID 1583215 → GPU6
```

这些 sentinel 不执行正式实验，却被资源扫描识别为活跃 reservation。它们
将外部等待链的保守解释固化为本实验自己的硬阻塞，增加了
`reserved_uuid_conflict` 的概率。

### 3.7 资源参数解析不完整导致调度器和运行时看到不同世界

旧冻结 runtime 能识别部分 `--gpu`、`--gpu-id` 和
`--physical-gpu-id`，但曾遗漏 `--physical-gpu`、`--physical-gpus`。这会
导致调度器选出一组 GPU，运行前 admission 又从更完整的进程语义中得出
不同结论，最终在 launch 前失败。

该问题已经有针对性修复和 `91 passed` 的 focused test 证据，但修复未进入
当前冻结生产 release，因此当前 root 仍在用旧语义重试。

### 3.8 将运行身份和科学身份混为一谈

候选 ID、source SHA、ONNX SHA、seed、预算和测量协议属于科学身份，必须
冻结。编排器 PID、worker PID、一次 deployment manifest、GPU UUID 和
波次划分只是运行身份，应允许审计后变化。

此前 root 把 orchestrator PID 等运行身份冻结为不可变合同。PID 死亡后，
即使没有消耗任何正式预算，也需要整体归档和重建 canonical root。一次普通
恢复因此演变成新的部署周期。

### 3.9 过度 fail-closed，却缺少“必须产生进度”的对称门禁

现有系统对以下情况都能迅速停止：

- SHA 漂移；
- PID 漂移；
- reservation 解释不一致；
- 部署清单变化；
- source admission 不完整。

但没有一个同等强度的规则要求：

> 当存在真实空闲 GPU、实验尚未完成，而且连续多次没有 terminal 或预算
> 进展时，必须主动恢复。

结果是系统可以长时间保持“安全地重试”，同时一个正式候选也不运行。

### 3.10 短命重试造成“后台看起来没有进程”

当前并非完全没有后台进程。编排器每约 5 秒创建一个 worker，worker 在
pre-GPU admission 阶段退出。用户查看进程列表时往往刚好看不到这个数秒
生命周期的 child，因此表象是“没有任务”，本质是“重试风暴但零进度”。

### 3.11 审计产物数量替代了论文进度

目前已经积累了大量测试、SHA、source、deployment、dry-run 和归档证据，
但论文真正需要的是：

- 192 个 selected-event 的可信 terminal；
- 48 个 round feedback barrier；
- 四条消融的 3-seed 指标；
- 论文表格和 root-cause summary。

后续监督必须把 `terminal_count`、`barrier_count` 和表格闭合度作为主要
进度，而不是把新的 gate、archive 或 test 数量当作实验已经推进。

## 4. 反思：哪些合同必须保留，哪些合同必须删除

### 4.1 必须保留的最低科学合同

以下内容直接决定消融是否公平，不能为了速度改变：

1. 同一 686 点候选池及其有序内容；
2. 同一四条 variant 定义；
3. 同一 seeds、`B=4`、四轮和 `T=16`；
4. 候选选中前不得读取 cache membership 或真实标签；
5. 选中后只允许 exact-key cache hit；
6. cache miss 必须调用 actual-feedback v3 真实物化和测量；
7. 禁止 surrogate 填补真实 latency、energy 或 AP；
8. 同一轮四候选全部 terminal 后才能回流 feedback；
9. latency/energy/AP/numerical gate 使用统一正式合同；
10. 真实 capability failure 消耗候选名额，infra failure 原 request 重试；
11. 每个结果必须可追溯到 candidate ID、request SHA、source SHA 和 terminal
    evidence；
12. Scanner deferred 和 Full-core 的论文表述必须准确。

### 4.2 不再作为启动硬门禁的运行条件

以下条件不影响消融的科学公平性，不得继续导致数小时零进度：

- 固定 GPU 编号或固定 GPU UUID；
- 必须同时得到四张空闲 GPU；
- GPU7 永久排除；
- 等待 shell、暂停进程或未来命令行参数构成当前 GPU 硬预留；
- 固定 orchestrator/worker PID；
- 一次部署 SHA 永远不可替换；
- 一次 operational fix 后必须重跑全部 1000+ 测试；
- PID 改变就整体重建所有 source；
- 一条 trajectory 的四个物理 job 必须同时开始；
- 为预防未来冲突而维持不做实际计算的 reservation sentinel。

运行身份发生变化时，保存旧值、新值、原因和时间即可。只要科学身份未变，
不得因为运行身份变化清零已验证 source 或重新选择候选。

## 5. 新的 GPU 使用原则：不固定资源，只保证真实测量窗口

### 5.1 可用性的唯一实质标准

GPU 是否可用，以**当前真实运行状态**为准：

- 当前没有外部 compute process 实际占用该 GPU；
- 当前显存和利用率表明它处于可启动状态；
- 启动前做一次短间隔复核，避免刚释放或刚启动的瞬时误判。

等待 shell、`T` 状态暂停进程、未来命令参数、历史 PID、无计算负载的
reservation sentinel 均不单独构成 GPU 占用。

这里不固定显卡编号、UUID、卡数或某一张卡的永久归属。GPU7 与其他 GPU
使用同一实时判定规则：当前真忙则不用，当前真空闲则可用。

### 5.2 弹性并行

- 有 1 张空闲卡就立即启动 1 个 ready candidate；
- 有 2 张就运行 2 个；
- 有更多空闲卡就继续填充 ready queue；
- 每张 GPU 同一时刻最多运行 1 个本实验的正式测量 worker；
- 不等待凑齐四卡；
- 可以并发运行来自不同 variant/seed 的 ready candidate；
- 每条 trajectory 内仍遵守 round feedback barrier；
- 当前轮 4 个候选可以分波完成。

### 5.3 与其他用户发生真实冲突时

不停止、不修改、不抢占其他用户进程。如果本实验启动后检测到外部 compute
process 进入同一 GPU，或正式测量窗口不再独占：

1. 只终止或隔离本实验在该 GPU 上受影响的 candidate；
2. 将其记录为 infra retry，不消耗新的 selected-event 名额；
3. 保留相同 candidate ID 和 logical request；
4. 换到下一张真实空闲卡重新执行；
5. 其他 GPU 上未受影响的候选继续运行；
6. 不因为一张卡冲突而取消整批或停住全部 trajectory。

### 5.4 禁止重新引入隐性强合同

监督器不得通过下列方式变相恢复旧问题：

- 为每个外部等待命令创建新的 sentinel；
- 把所有未来可能使用的卡加入永久 blacklist；
- 要求两次、三次或四次固定长度的“持续空闲小时数”；
- 因为没有固定四卡而等待；
- 因为某个历史 F-Cooper PID 或历史 GPU7 规则而永久排除卡；
- 将当前空闲卡仅登记为“候选资源”却不提交 ready job。

## 6. 当发现空闲 GPU，但实验尚未完成时必须怎么办

这是本计划的核心进度合同。

监督器每次轮询同时检查：

```text
实验是否完成
当前真实空闲 GPU 数
ready candidate 数
running formal GPU worker 数
selected-event / terminal / barrier 计数
最后一次真实进度时间
```

只要满足：

```text
实验未完成
AND 至少一张 GPU 真实空闲
AND 存在 ready candidate
AND 没有对应正式 worker 在运行
```

就必须立即提交候选，不得进入长时间 `waiting_retryable`。

如果连续两个监督轮询周期仍未出现正式 worker 或进度，必须将其判定为
`stalled_with_idle_gpu`，按以下顺序自动恢复：

1. 保存当前进程树、GPU 快照、scheduler/controller state 和最后错误；
2. 确认是否是本实验自己的旧 lock、lease、sentinel 或短命 retry 阻塞；
3. 在核对 owner、PID 和无活跃 child 后，清理本实验自己的过期资源状态；
4. 停止本实验自己的无效重试 worker；必要时平滑重启 Stage7 编排器；
5. 保留原 selected IDs、logical request、source 和已完成 terminal；
6. 如果是资源解析或 schema bug，编写最小失败测试、完成最小修复并运行
   focused regression；
7. 重新部署修复后的薄适配层，记录 old/new SHA，但不把部署 SHA 变化当成
   科学身份变化；
8. 立即在当时真实空闲的 GPU 上恢复同一 candidate；
9. 验证至少一个正式 GPU worker 已运行或产生 terminal 后，才退出恢复态。

如果空闲 GPU 存在但 ready candidate 为 0，则必须检查：

- 前一轮是否已经四项 terminal 但 feedback barrier 未生成；
- cache/terminal 是否已写入但 finalizer 未推进；
- selector 是否因 operational PID/SHA gate 未产生下一轮；
- infra failure 是否错误消耗了预算；
- trajectory 是否错误标记为 running。

找到后立即修复对应 Stage7 控制层。不得以“没有 ready candidate”为理由
无限等待。

只有以下情况属于合理等待：

- 所有 GPU 都有当前真实 compute process；
- 本实验已有 candidate 在真实运行，日志/heartbeat/GPU 利用率仍在推进；
- 当前 trajectory 正在等待其已启动候选自然完成。

即使合理等待，也必须持续轮询；任何 GPU 一旦真实释放，立即填充 ready
queue。

## 10. 完成与停止条件

只有同时满足以下条件才停止长期监督：

```text
12 / 12 trajectories have trusted terminal state
192 / 192 selected events are closed
48 / 48 round feedback barriers are closed
all cache misses have actual-v3 terminal evidence
silent_surrogate_fallback_count = 0
paper Markdown/CSV tables generated
raw JSON/CSV generated
root-cause summary generated
core_ablation_ready = true
full_gear_s7_ready = false
scanner_component_status = deferred_important_fix
```

以下情况不能作为停止理由：

- 当前只有一张或两张卡空闲；
- GPU 编号与上次不同；
- 编排器 PID 改变；
- 为修复 operational bug 更新了部署 SHA；
- 某条 trajectory 因 infra failure 需要重试；
- 外部等待 shell 声明未来可能使用 GPU；
- 已完成大量测试但正式结果仍为 0。
