# 18_7_14 交接文档：INT8 慢因验证后三组对照实验设计

## 0. 本文定位

第一组 `Pyramid + TVM RouteB` 已完成，当前要继续补齐后三组实验：

1. `CoDriving + TVM RouteB`
2. `Pyramid + TRT`
3. `CoDriving + TRT`

目标不是重新证明某一个固定结论，而是用真实测量把 “为什么当前 INT8 搜索臂弱于 FP16” 拆成可验证的因果问题：

- 是否主要来自 Pyramid 网络中的 grouped convolution 结构。
- 是否主要来自 TVM 自动后端当前的 fusion boundary / materialization 问题。
- 是否来自 INT8 路线本身不可避免的 int32 accumulate、requant、scale/layout 转换代价。

实验口径必须服务于自动搜索叙事：最终框架不写死 “INT8 一定弱” 或 “FP16 一定强”，而是把结构、后端、量化臂作为可观测变量，通过冷启动数据和实测回流让模型学习哪些组合有效。

## 1. 已完成基线：G0 Pyramid + TVM RouteB

- `${V2X_ROOT}/results/route_b_qxs32_pair_comparison_20260708.csv`

已知结论：

- 16 个 paired width 点全部完成 `fp16` 与 `int8` 配对测量。
- 16/16 个点均为 `fp16` 更快。
- `int8 / fp16` 延迟比：最小约 `1.9774x`，中位数约 `3.6670x`，最大约 `4.8876x`。
- 典型点：
  - `16x32x64`: `fp16=0.710336 ms`, `int8=3.3164272 ms`, `int8/fp16=4.6688x`

  - `64x128x256`: `fp16=3.523648 ms`, `int8=6.96770245 ms`, `int8/fp16=1.9774x`

当前不能直接把这个结论外推为 “INT8 无效”。它只说明：在 `Pyramid + TVM RouteB` 这一组合下，当前自动 INT8 路线明显慢于自动 FP16 路线。

## 2. 三个待验证假设

### H1：grouped convolution 结构假设

Pyramid 中大量 grouped convolution 可能导致 INT8 路线出现更严重的 tile 不匹配、padding、低 arithmetic intensity 和 im2col/materialization 代价。若该假设成立，则换成普通卷积网络 `CoDriving` 后，`TVM RouteB int8/fp16` 差距应明显缩小，甚至出现 INT8 快于 FP16 的点。

### H2：TVM fusion boundary 假设

TVM RouteB 当前可能把 conv / dequant / requant / layout transform / add 等阶段切开，导致 INT8 的理论计算优势被中间张量落地和额外 kernel launch 吃掉。若该假设成立，则在同一 Pyramid 宽度点上换成 TRT 后，TRT INT8 应显著优于 TVM INT8，并可能接近或快于 TRT FP16。

### H3：INT8 本征开销假设

INT8 并不是 “天然一定快”。它需要 int32 accumulate、scale/zero-point 处理、requant、layout transform，并且小通道、小 batch、小空间或 group 后每个 GEMM 很小的时候，这些开销可能压过 int8 tensorcore 的吞吐收益。若该假设成立，则即使换成 CoDriving 或 TRT，INT8 也可能只在部分大点上有效。

## 10. 推荐执行顺序

1. 先做 preflight：确认三组所需 ONNX、输入 shape、calibration 数据、GPU、driver、TensorRT、TVM 版本。
2. 先跑 G1 的 8 点，因为它直接验证 grouped convolution 假设，且可复用现有 TVM RouteB 思路。
3. 同时或随后跑 G2 的 8 点，优先复用 G0 的 Pyramid ONNX，避免结构不一致。
4. 最后跑 G3 的 8 点，作为普通卷积 + TRT 的正控制。
5. 三组完成后生成 `int8_cause_matrix_qxs8_20260708.{json,csv}`，并把每个 paired 点都标记可信度。
6. 若某组出现 build failure，不要删除失败点；应记录为 `build_status=failed`，这是搜索空间有效性的重要信号。

## 11. 对自动搜索框架的影响

这轮实验不应把规则写死为：

- `INT8` 永远弱于 `FP16`。
- `TRT` 永远强于 `TVM`。
- `hand-rewrite prior` 可以作为最终 gold。

应该把结果用于支持下一步框架改造：

- 搜索变量从 `Q={fp16,int8}` 扩展为 `Q x S`，其中 `S` 表示后端/调度路线。
- `INT8` 只有在绑定合适自动后端时才是有效加速臂。
- hand-rewrite 结果最多作为 warm-start prior 或后端设计灵感，不能直接作为最终主结果。
- cost model 特征需要加入：
  - group count
  - per-group channel
  - padding/tile waste ratio
  - expected materialization count
  - quant/requant operator count
  - backend/fusion capability

这能保持论文叙事一致：框架不是人为规定哪个量化臂更好，而是通过搜索空间建模和真实测量学习不同结构、精度和后端组合下的性能。

## 12. 最小完成标准

后三组每组至少满足：

- 8 个 width 点。
- 每个 width 点有 `fp16` 和 `int8` paired latency。
- 每个点记录 build 成败。
- 每个 INT8 点记录校准来源。
- 每个 TRT INT8 点记录层精度摘要，防止伪 INT8。
- 每个 TVM 点记录 tensorization / lowering 证据。
- 所有结果合并成统一 summary 表。

完成后，至少能够回答：

1. Pyramid 的 grouped convolution 是否足以解释 INT8 慢。
2. TVM RouteB 的 fusion boundary 是否足以解释 INT8 慢。
3. 在普通卷积网络和强融合后端下，INT8 是否能恢复优势。
4. 下一步搜索空间是否必须从 `Q` 扩展到 `Q x S`。

## 13. G4：TVM 内部 QxS 翻盘小闭环实验计划

### 13.1 新问题

截至 2026-07-08，G0/G1/G2/G3 已经支持如下判断：

- `Pyramid + TVM RouteB`：pure INT8 全点慢于 FP16，且小模型最严重。
- `CoDriving + TVM RouteB`：去掉 group conv 后，pure INT8 仍全点慢于 FP16，但差距缩小到约 `1.10-1.29x`。
- `CoDriving + TRT`：INT8 能稳定快于 FP16，说明 INT8 本身不是不可加速。

因此当前真正削弱叙事的点不是 “INT8 是否天然有效”，而是：如果最终主后端仍是 TVM，那么 `S` 维必须在 TVM 内部真正改变 INT8 的收益排序。否则 `Q={fp16,int8}` 会退化成一个在 TVM 下恒弱的无效维度。

### 13.2 本轮目标

本轮不再继续大规模补 pure INT8 点，而是启动 `G4: TVM-internal QxS repair`，目标是在不切换到 TRT、也不回退旧 hand-rewrite final gold 的前提下，验证 TVM 内部是否存在能改变 INT8 表现的 `S` 变体。

最小成功标准：

- 至少一个 CoDriving width 点上，`mixed_policy` 延迟低于 pure INT8。
- 更强成功标准：至少一个点上，`mixed_policy <= RouteB FP16`。
- 若 mixed 仍慢，也必须输出可解释证据：哪些 conv 被选为 int8、tensorize 是否发生、latency 相对 pure fp16/int8 的位置。

### 13.3 优先实验臂

| 组别 | TVM 内 S 变体 | 目的 | 预期解释 |
|---|---|---|---|
| G4-S0 | current pure fp16 / pure int8 baseline | 复用 G1 作为锚点 | 给 mixed 提供同点比较 |
| G4-S1 | `mixed_top25_flops` | 只让最大计算量 conv 走 INT8 | 验证 INT8 是否只在大 GEMM 上有收益 |
| G4-S2 | `mixed_top50_flops` | 半数高 FLOPs conv 走 INT8 | 验证 mixed 是否比 pure INT8 更优 |
| G4-S3 | `mixed_stride2_or_1x1` | 选择 stride2 或 1x1 conv 走 INT8 | 验证 shape/tile 类型对 INT8 有效性的影响 |
| G4-S4 | fused epilogue / requant 合并 | 后续实现项 | 直接攻击 TVM INT8 materialization 开销 |
| G4-S5 | CUTLASS BYOC / library-backed INT8 | 后续实现项 | 验证 TVM 入口下的后端 S 维能否接近 TRT |

当前先启动 G4-S2 smoke，因为 CoDriving 当前 pure INT8 只慢约 `1.10-1.29x`，是最容易观察 mixed 是否翻盘的场景。

### 13.4 已新增代码入口

在 `${V2X_ROOT}/scripts/stage2_codriving_whole_engine_tc_v1.py` 中新增：

- `--precision mixed`
- `--mixed-policy {none,all,top25_flops,top50_flops,top75_flops,stride2_or_1x1}`

实现口径：

- 仍使用同一个 CoDriving backbone ONNX。
- 每个被替换的 `fused_conv2d*` PrimFunc 保持 float32 I/O，不改变图级接口。
- mixed policy 只决定该 PrimFunc 内部使用 `fp16 TC` 还是 `int8 TC`。
- 调度规则同时启用 `MatmulInt8Tensorization` 和 `MatmulTensorization`，使 mixed 图在同一个 TVM 编译入口里构建。

这不是最终量化 AP 结论，而是 latency/backend 诊断实验；可信度应标为 `trusted_for_diagnosis=conditional_latency_backend_probe`，不能直接进入最终 Pareto。

#### 13.9.1 G4-S4: fp16 graph boundary / materialization 对照

G4-S4 本轮不是完整 fused requant epilogue 实现，而是一个最小可证伪的 boundary/materialization 对照：将 CoDriving RouteB 的 graph boundary 从上一批 `fp32` 改为 `fp16`，然后同点重测 `pure FP16`、`pure INT8`、`mixed_top25_flops`、`mixed_stride2_or_1x1`。

| width | pure FP16 ms | pure INT8 ms | INT8/FP16 | mixed top25 ms | top25/FP16 | mixed stride/1x1 ms | stride/FP16 | best arm |

| `16x32x64` | 1.793 | 2.003 | 1.117 | 1.729 | 0.965 | 1.814 | 1.012 | `mixed_top25_flops` |
| `24x32x96` | 2.105 | 2.534 | 1.204 | 2.145 | 1.019 | 2.140 | 1.017 | `fp16` |
| `32x32x128` | 2.396 | 2.937 | 1.226 | 2.404 | 1.003 | 2.444 | 1.020 | `fp16` |
| `32x64x128` | 2.597 | 3.247 | 1.250 | 2.578 | 0.993 | 2.660 | 1.024 | `mixed_top25_flops` |
| `48x96x192` | 3.386 | 4.401 | 1.300 | 3.388 | 1.001 | 3.469 | 1.025 | `fp16` |

聚合结果：

- `pure INT8` 仍然 8/8 慢于 `pure FP16`，`INT8/FP16` 中位数为 `1.275x`。
- `mixed_top25_flops` 只有 2/8 快于 `pure FP16`，`top25/FP16` 中位数为 `1.011x`。
- `mixed_stride2_or_1x1` 0/8 快于 `pure FP16`，`stride/FP16` 中位数为 `1.024x`。
- 最优臂统计：`pure FP16` 为 6/8，`mixed_top25_flops` 为 2/8。
- 相对上一批 `fp32-boundary` 结果，`pure FP16`、`mixed_top25_flops`、`mixed_stride2_or_1x1` 的中位延迟都约降到 `0.57x` 左右。

关键结论修正：

- 不能写成“G4-S4 证明 fp32 boundary/materialization 是 INT8 慢于 FP16 的主因”。
- 更准确的结论是：G4-S4 证明上一批 CoDriving TVM 测量中存在显著的 `fp32 graph boundary / dtype materialization` 公共开销；但该开销不是 INT8 特有的。把 graph boundary 改成 fp16 后，FP16、mixed INT8 路线同步变快，而 INT8 相对 FP16 的排序没有根本翻转。
- 因此，G4-S4 实际上排除了“fp32 boundary 是 INT8 恒弱主因”的解释。当前 INT8 慢因仍应主要指向 INT8-specific 成本，包括 int32 accumulator、padding、pack/requant、TensorCore tile 利用率和调度开销。

对论文叙事的影响：

- `S` 维仍然有价值，因为同一组 width 在不同 boundary / mixed policy 下 latency 明显变化。
- 但不能把 `mixed_top25_flops` 写成强制规则；它只应作为候选 `search_arm_id`，由实测回流和 cost model 学习何时选用。
- 当前最稳妥表述是：`Q x S` 扩展有必要，但 `S4(fp16 boundary)` 只是消除公共开销，尚未让 INT8 系统性超过 FP16。

#### 13.9.2 G4-S5: CUTLASS BYOC smoke

本轮对 `16x32x64` CoDriving backbone-only ONNX 启动 CUTLASS BYOC smoke，测试过程：

1. `from_onnx` 成功。
2. `ToMixedPrecision(out_dtype="float16")` 成功。
3. `ConvertLayout({"relax.nn.conv2d": ["NHWC", "OHWI"]})` 成功。

```text

```

G4-S5 当前结论：

- CUTLASS BYOC 对 CoDriving 普通 Conv 有入口可行性：12 个 conv/bias/relu 子图已经能被识别并 partition 到 CUTLASS。
- 当前失败不是“普通 Conv 无法进入 CUTLASS”，而是 full-engine 中残留的 `conv2d_transpose` 没有在 BYOC build pipeline 中被正确 lowering。
- 因此本轮不能给 CUTLASS BYOC latency 结论，也不能写成 CUTLASS BYOC 性能失败。
- 下一步若继续 G4-S5，应先解决 `conv2d_transpose` 的 lowering/隔离问题，再做 full-engine latency；或者先构造 conv-only 子图做 CUTLASS 性能 smoke，但该结果只能作为诊断，不能替代完整 backbone-only 结论。

关键比例：

- 单层 `s8s8_i32 / fp16_ref = 1.382x`，说明当前 CUTLASS INT8 单 kernel 本身没有快于 FP16。
- `s8s8_i32_deconv / fp16_deconv = 1.627x`，说明 native int8 deconv 也没有快于 FP16。
- `int8_two_conv_with_intermediate_astype / fp16_two_conv_relu = 1.287x`。
- `int8_single_conv_plus_output_astype / raw_int8_conv = 1.078x`。
- `int8_two_conv_with_intermediate_astype / (2 x int8_single_conv_plus_output_astype) = 1.419x`，说明中间 dtype/materialization boundary 会继续放大 INT8 劣势。

#### 13.10.3 本轮验证后的判断修正

当前判断应收紧为：

1. 不能再说 `CUTLASS BYOC full-engine 被 conv2d_transpose 阻断` 是当前状态。该问题已经通过 `conv2d_transpose=NCHW/IOHW + LegalizeOps` 修复，FP16-CUTLASS full-engine 8 点已闭合。
2. 不能说 `INT8 无法进入 CUTLASS`。最小 `int8/uint8 input + int8 weight -> int32` conv 可以 partition/build/run，`conv+bias+relu` 也能 fused。
3. 也不能把 INT8 慢完全归因于 graph boundary/materialization。控制实验显示 boundary 会放大 INT8 劣势，但单层 INT8 CUTLASS conv 与 int8 deconv 本身已经慢于 FP16。
4. 更准确的慢因组合是：当前 TVM/CUTLASS INT8 路线下，raw INT8 kernel 没有赢 FP16；再叠加 `int32 accumulator`、padding、requant/pack、dtype materialization、deconv/native mixed boundary 后，全图 INT8 更难超过 FP16。

对框架优化的直接含义：

- `S5_fp16_cutlass` 可以作为新的强 baseline backend arm 纳入后续搜索框架评估。
- `S5_int8_cutlass` 不能直接宣称成功，但也不应放弃；下一步应实现 fullgraph mixed runner：普通 Conv 优先尝试 CUTLASS INT8 fused，`ConvTranspose/BN/Concat` 先保守走 native 或 FP16 fallback。
- 搜索空间仍应保持 `Q x S` 叙事，但 `Q=int8` 必须绑定具体后端/边界策略后才有意义，不能再作为单独的整网开关。
- 下一轮实验优先在 `16x32x64` 与 `64x128x256` 两点闭合 `S5_int8_mixed_fullgraph`，验证它是否能接近或超过 `S5_fp16_cutlass`；若仍慢，应将 INT8-specific kernel 与 requant/materialization 成本作为 cost model 特征，而不是人工写死禁用 INT8。
