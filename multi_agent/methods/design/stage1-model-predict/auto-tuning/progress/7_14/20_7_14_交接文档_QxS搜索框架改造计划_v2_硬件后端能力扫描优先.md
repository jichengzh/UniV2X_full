# 20_7_14 交接文档：QxS 搜索框架改造计划 v2 - 硬件/后端能力扫描优先

**日期**: 2026-07-08  
**状态**: 计划修正稿，取代 `19_7_14_交接文档_QxS搜索框架改造计划_v1.md` 中把 `backend/schedule_route/evidence trust` 放入 `search_arm_id` 的表述  
**核心修正**: `backend` 不是搜索基因，不应由外界作为先验策略传入；它应来自 Stage0/Stage1 的硬件与编译后端能力扫描，并作为测量上下文参与数据记录和 cost model 条件化。
**量化 genome 二次修正**: 量化不默认做 per-stage 划分。剪枝仍按 stage 表达为 `[p1,p2,p3]`；量化按全模型表达为 `q_mode x mixed_policy_id`。`graph_boundary` 暂不作为主搜索维度，而是由 mixed mask 自动产生并作为观测/诊断特征记录。

---

## 1. 本轮修正的原因

v1 计划中曾把 `search_arm_id` 扩展为类似：

```text
(q_axis, backend, schedule_route, evidence_trust)
```

这个设计不合适，原因如下：

1. **backend 不应是人为绑定的搜索臂**  
   如果 `search_arm_id` 直接写入 `tvm_routeb_int8`、`trt_int8`、`cutlass_byoc_fp16`，框架就隐含接收了外部先验：哪个后端应当采用哪种量化策略、哪条 schedule route 更可能有效。  
   这违背当前研究前提：框架应依靠冷启动数据与实测回流学习，而不是靠人工规则写死。

2. **schedule_route 也不应是主搜索变量**  
   `RouteB_auto`、`CUTLASS_BYOC`、`TRT_QDQ` 等更像是某个编译后端在实际 build/run 过程中实现策略时形成的 realization。  
   搜索器应提出“逻辑策略”，例如 FP16、pure INT8、不同 mixed INT8 覆盖策略，而不是直接指定某个后端内部 schedule。

3. **evidence trust policy 是数据治理字段，不是搜索变量**  
   `trusted_for_final_frontier`、`conditional`、`historical_prior` 这类字段只用于构建训练表、过滤最终 Pareto、区分冷启动与历史先验，不能进入 genome。  
   否则模型会把“可信度标签”误当成可优化策略。

因此 v2 计划将搜索变量收敛为：

```text
genome = (width/prune knobs, q_mode, mixed_policy_id)
```

其中 `backend/compiler_profile` 是环境上下文，由能力扫描确定；`schedule_route` 是运行后记录的实现路径；`evidence_trust` 是数据集治理与最终结果过滤字段。`graph_boundary` 暂不进入主 genome，而是从 mixed policy 形成的量化 mask 中推导出 `boundary_count/cast_count/requant_count/fusion_break_count` 等测量特征。

## 2. 重新定义 search_arm_id

建议将 `search_arm_id` 改名为 `strategy_id`，或至少严格定义为 **logical strategy id**。

### 2.1 允许进入 strategy_id 的字段

`strategy_id` 只包含框架真正需要探索的逻辑策略：

| 字段 | 含义 | 示例 |
|---|---|---|
| `q_mode` | 全模型主量化轴 | `fp16`, `int8` |
| `mixed_policy_id` | 全模型 eligible conv 的 INT8 覆盖策略 | `none`, `top10_flops`, `top25_flops`, `top50_flops`, `top75_flops`, `all_eligible_conv` |

示例：

```json
{
  "strategy_id": "q=int8|mixed=top25_flops",
  "q_mode": "int8",
  "mixed_policy_id": "top25_flops"
}
```

这里没有 `tvm`、`trt`、`route_b`、`cutlass`、`trusted`。

有效组合建议先收敛为：

```text
q_mode = fp16 -> mixed_policy_id = none
q_mode = int8 -> mixed_policy_id in {top10_flops, top25_flops, top50_flops, top75_flops, all_eligible_conv}
```

这样既保留 `fp16`、`pure int8`、`mixed int8` 三类策略，又避免出现 `fp16 x top25_flops` 这种语义重复的搜索点。

### 2.2 量化维度不默认做 per-stage

剪枝旋钮可以自然写成：

```text
P = [p1, p2, p3]
```

因为三个 stage 的 width/prune ratio 本来就是架构变量。但量化不应直接类比为：

```text
Q = [q1, q2, q3]
```

原因是 stage 本身不是量化收益的直接因果变量。量化收益更可能来自：

```text
剪枝后 Cin/Cout
operator type
FLOPs 占比
TensorCore tile alignment / padding
requant/cast/materialization 边界
fusion boundary
backend compiler profile
```

因此第一版量化 genome 建议写成全模型策略：

```text
P = [p1, p2, p3]
Q = q_mode
M = mixed_policy_id
```

也就是：

```text
genome = ([p1,p2,p3], q_mode, mixed_policy_id)
```

其中 `mixed_policy_id` 是全模型 eligible conv 的选择策略：

| id | 含义 |
|---|---|
| `none` | 不启用 INT8，纯 FP16 |
| `top10_flops` | 只把 FLOPs 占比最高的约 10% eligible conv 尝试 INT8 |
| `top25_flops` | 只把 FLOPs 占比最高的约 25% eligible conv 尝试 INT8 |
| `top50_flops` | 只把 FLOPs 占比最高的约 50% eligible conv 尝试 INT8 |
| `top75_flops` | 只把 FLOPs 占比最高的约 75% eligible conv 尝试 INT8 |
| `all_eligible_conv` | 所有当前 backend profile 判定可承载的 conv 尝试 INT8，即 pure INT8 主臂 |

这里的 `eligible conv` 不由人工经验规则直接写死，而由前置 compiler backend capability scan、build/run probe、以及历史实测回流共同确定。框架学习的是：

```text
([p1,p2,p3], q_mode, mixed_policy_id, layer_features, backend_capability_features) -> latency / accuracy
```

而不是学习“stage1 应该 INT8、stage2 应该 FP16”。

### 2.3 不允许进入 strategy_id 的字段

| 字段 | 正确归属 | 原因 |
|---|---|---|
| `backend` / `compiler_backend` | 能力扫描输出、测量上下文 | 不是搜索策略本身，而是当前硬件/软件环境 |
| `schedule_route` | build/run 后的 realization 记录 | 由后端实现过程决定，不能作为人工先验注入 |
| `graph_boundary` | mixed mask 推导出的观测/诊断特征 | 第一版不单独搜索，先记录边界数量、cast/requant、fusion break 等实测特征 |
| `evidence_trust` | 数据治理字段 | 用于过滤和训练权重，不是模型可选择策略 |
| `source_confidence` | 数据治理字段或样本权重 | 不能成为搜索动作 |
| `historical_hand_rewrite_prior` | warm-start 来源标记 | 可辅助初始化，但不能作为 final gold |

## 3. backend 的正确位置：硬件/编译后端能力扫描

当前框架已有硬件能力扫描入口：

- `framework/stage1/hardware_scan.py`
- `framework/capability_schema.py`
- `framework/stage1_bridge.py`
- `configs/hardware/*.yaml`

但现状偏静态：

1. `hardware_scan.py` 主要读取 YAML，文档中明确写了 v1 不探测真硬件。
2. `capability_schema.py` 有 `Toolchain` 信息，但没有完整的 `compiler_backend_capability`。
3. `stage1_bridge.py` 当前 `_quant_policies()` 仍存在类似 `backend_scope: measured_h800_tvm` 的硬编码表述。
4. `configs/hardware/` 目前主要是 `rtx4090.yaml`、`orin_agx.yaml`，缺少 H800 的正式能力描述与后端扫描结果。

v2 的关键改造是：**把 backend 从搜索臂中拿出来，提前放到 Stage0/Stage1 能力扫描。**

## 4. 新的能力扫描架构

### 4.1 输入

能力扫描入口接收：

```text
hardware_target: h800 / rtx4090 / orin
candidate_compilers: tvm / tensorrt / cutlass_byoc / torch_inductor 等
model_family_probe: pyramid / codriving / minimal_conv_suite
```

注意：这里的 `candidate_compilers` 不是搜索臂，而是当前机器可用工具链枚举。  
枚举后端等价于识别“当前环境能测什么”，不是告诉模型“哪个后端更好”。

### 4.2 输出

能力扫描输出 `compiler_backend_profiles`：

```json
{
  "hardware_target": "h800",
  "compiler_backend_profiles": [
    {
      "compiler_profile_id": "h800_tvm_cuda12_meta_schedule_20260708",
      "backend": "tvm",
      "version": "...",
      "supports_fp16": true,
      "supports_int8": true,
      "supports_explicit_qdq": false,
      "supports_calibrator_int8": false,
      "supports_cutlass_byoc": true,
      "supports_conv2d": true,
      "supports_group_conv": "partial",
      "supports_conv2d_transpose": false,
      "supports_requant_fusion": "unknown_or_partial",
      "supports_cast_fusion": "unknown_or_partial",
      "probe_results": {
        "fp16_conv2d_build_run": "pass",
        "int8_conv2d_build_run": "pass",
        "int8_group_conv_build_run": "pass_but_slow",
        "conv2d_transpose_cutlass_lowering": "fail"
      }
    }
  ]
}
```

这些字段进入训练表和测量日志，作为 **context features**，而不是 `strategy_id`。

### 4.3 必要 micro-probe

为了让框架自己学习 TRT/TVM 在量化策略上的差异，能力扫描不能只读版本号，必须补充最小真测：

| probe | 目的 |
|---|---|
| `fp16_conv2d` | 验证 FP16 TensorCore 基线 |
| `int8_conv2d` | 验证 INT8 TensorCore/QDQ/DP4A 路线是否可 build/run |
| `int8_conv2d_bias_relu` | 验证融合边界 |
| `int8_two_conv_with_boundary` | 验证 materialization/cast/requant 边界成本 |
| `group_conv_fp16/int8` | 验证 Pyramid/CoDriving 中 group conv 相关假设 |
| `conv2d_transpose_fp16/int8` | 验证 CoDriving G4-S5 中 CUTLASS BYOC 阻断点 |
| `mixed_topk_flops` | 验证 mixed policy 是否可由后端稳定实现 |

能力扫描只回答“这个后端能否承载这些逻辑策略，以及初始性能证据如何”，不直接替搜索器做最终选择。

## 5. 搜索器如何使用 backend

### 5.1 搜索 genome

搜索器 genome 应为：

```text
genome = (w0, w1, w2, strategy_id)
strategy_id = (q_mode, mixed_policy_id)
```

对于更一般的网络，可以写为：

```text
genome = (architecture/pruning knobs, q_mode, mixed_policy_id)
```

当前不建议把量化做成 per-stage 向量，例如 `[q1,q2,q3]`。原因是 stage 分组本身不是量化收益的直接因果变量；INT8/FP16 收益更可能由剪枝后的通道形状、operator type、FLOPs 占比、TensorCore tile alignment、requant/cast/materialization 边界成本和 backend capability 共同决定。因此剪枝保持 per-stage：

```text
P = [p1, p2, p3]
```

量化保持全模型策略：

```text
Q = q_mode
M = mixed_policy_id
```

整体搜索写成：

```text
genome = ([p1,p2,p3], q_mode, mixed_policy_id)
```

`mixed_policy_id` 表示“全模型 eligible conv 中选择多少/哪些 conv 进入 INT8”，而不是“哪个 stage 进入 INT8”。

### 5.2 backend 是 measurement context

同一个 genome 可以在不同 `compiler_profile_id` 下测量：

```text
(w0,w1,w2, q=int8, mixed=top25_flops) @ h800_tvm
(w0,w1,w2, q=int8, mixed=top25_flops) @ h800_trt
```

这两个点不是两个人为策略，而是同一个逻辑策略在不同编译后端上下文中的实测结果。

训练表可以包含：

```json
{
  "w0": 16,
  "w1": 32,
  "w2": 64,
  "strategy_id": "q=int8|mixed=top25_flops",
  "q_mode": "int8",
  "mixed_policy_id": "top25_flops",
  "compiler_profile_id": "h800_tvm_cuda12_meta_schedule_20260708",
  "backend_context_features": {
    "backend": "tvm",
    "supports_int8": true,
    "supports_group_conv": "partial",
    "supports_requant_fusion": "partial"
  },
  "derived_boundary_features": {
    "dtype_boundary_count": 7,
    "requant_count": 5,
    "cast_count": 2,
    "fusion_break_count": 3
  },
  "latency_ms": 4.12,
  "measurement_source": "real",
  "trusted_for_final_frontier": true
}
```

最终 cost model 可以选择两种实现：

1. **per-backend model**  
   每个 `compiler_profile_id` 单独训练一个 cost model。优点是简单，避免不同后端分布混杂。

2. **context-conditioned model**  
   把 `compiler_profile` 的能力扫描特征作为输入，让模型学习 TVM/TRT/CUTLASS 的差异。优点是更符合统一框架叙事，但需要更多样本。

无论哪种实现，`backend` 都不是人工指定的策略先验。

## 6. TRT 与 TVM 策略差异如何让框架自己学会

正确流程如下：

1. Stage0/Stage1 扫描 H800 上可用后端：TVM、TensorRT、CUTLASS BYOC 等。
2. 每个后端运行同一组 micro-probe，形成 `compiler_backend_profiles`。
3. 框架生成相同的逻辑策略空间：

   ```text
   Q x MixedPolicy
   ```

   其中 `Q = {fp16, int8}`，`MixedPolicy = {none, top10_flops, top25_flops, top50_flops, top75_flops, all_eligible_conv}`。`graph_boundary` 不在第一版主搜索空间中单独枚举，而是由 mixed mask 产生并作为实测特征回填。

4. measurement dispatcher 根据 `compiler_profile_id` 把逻辑策略翻译成后端实际构建命令。
5. 搜索器只看到：

   ```text
   当前逻辑策略在当前 compiler profile 下的实测 latency/accuracy/build_status
   ```

6. 经过冷启动数据与实测回流，模型自动学习：

   - TRT 下 `pure_int8` 或 `mixed_int8` 是否更快；
   - TVM 下 pure INT8 是否因 group conv、requant、materialization、fusion boundary 变慢；
   - mixed policy 是否在某些网络规模或算子结构上更优；
   - FP16 在某些后端是否是更稳的主臂。

这样论文叙事可以保持为：

> 框架不预设 INT8 一定优于 FP16，也不预设 TRT/TVM 某后端一定更好；它先扫描硬件与编译后端能力，再通过冷启动和在线实测回流学习不同策略在不同后端上下文中的真实收益。

## 9. 对论文叙事的影响

这个修正对自动搜索叙事是有利的。

原先容易被质疑为：

> 你们把 TVM/TRT/RouteB/CUTLASS 手工编码进搜索臂，所以模型只是选择了人工设计好的后端策略。

v2 可以表述为：

> 框架先通过硬件与编译后端能力扫描建立可执行策略空间，再对统一的逻辑策略进行冷启动测量和在线回流。后端差异不作为人工先验策略输入，而作为环境上下文和实测证据被模型学习。

这使得当前发现也更容易解释：

1. TVM 下 pure INT8 恒弱于 FP16，不表示 INT8 理论无效，而表示当前 TVM compiler profile 对该网络结构的 INT8 realization 存在边界成本。
2. TRT 下 INT8 可加速，不需要手工写规则，而是会通过 TRT profile 的实测数据被 cost model 学到。
3. mixed policy 可以进入搜索空间，但是否采用由冷启动与回流决定。
4. historical hand-rewrite 结果只作为 backend realization 的历史证据或 warm-start prior，不作为 final gold。

不包含人为绑定的 backend search arm。

### Step 3: 生成 context-aware training table

输出文件建议：

```text
results/phase1_qxs_training_table_context_backend_20260708.json
```

训练表中保留 backend context，但 `strategy_id` 只保留逻辑策略。

### Step 4: 跑最小 8-16 点闭环

建议每个 backend profile 至少覆盖：

- `q=fp16,mixed=none`
- `q=int8,mixed=top10_flops`
- `q=int8,mixed=top25_flops`
- `q=int8,mixed=top50_flops`
- `q=int8,mixed=top75_flops`
- `q=int8,mixed=all_eligible_conv`

目标不是立刻宣称性能，而是验证：

1. 搜索器是否不再依赖 backend 先验臂；
2. 同一 logical strategy 能否在 TVM/TRT profile 下形成不同实测结果；
3. cost model 是否可以通过 backend context 学到差异；
4. final Pareto 是否只由可信实测点构成。
5. `derived graph features` 是否能解释 mixed policy 造成的 dtype boundary、requant、cast 和 fusion break 成本。

## 11. 需要避免的错误实现

1. 不要写：

   ```text
   search_arm_id = tvm_int8_routeb
   search_arm_id = trt_int8_qdq
   ```

2. 不要把 `trusted_for_final_frontier` 编进模型输入的策略 one-hot。

3. 不要把 `historical_hand_rewrite_prior` 当成 final gold。

4. 不要在搜索器里硬编码：

   ```text
   if backend == trt then prefer int8
   if backend == tvm then prefer fp16
   ```

5. 不要把 backend probe 失败简单解释成该策略理论无效；应记录为当前 compiler profile 的 realization failure。
