## 1. 本次审计问题

本次审计回答四个问题：

1. CoDriving 的三个宽度维度来自框架扫描，还是人工模仿 Pyramid；
2. 当前搜索是离线预测还是带真实测量回流的闭环搜索；
3. 哪些部分由框架自主决定，哪些部分仍是人工定义的方法协议；
4. latency、energy、AP 已经真实测量时，为什么图结构特征仍然不是实测值，以及这是否影响论文叙事。

## 2. CoDriving 三维宽度编码的来源

CoDriving 原始 `base_bev_backbone` 本身包含三个宏观 stage：

```text
layer_nums           = [3, 4, 5]
layer_strides        = [2, 2, 2]
num_filters          = [64, 128, 256]
upsample_strides     = [1, 2, 4]
num_upsample_filter  = [128, 128, 128]
```

因此，`(w0,w1,w2)` 对应三个原生 BEV backbone stage 的输出通道数。三个 stage 不是能力扫描临时创造的，也不是为了模仿 Pyramid 而人为拆分出来的。

但以下内容属于框架设计者预先定义的模型适配合同，而不是扫描结果：

- 将三个 `num_filters` 暴露为结构搜索基因；
- 将 Pyramid 和 CoDriving 统一编码为 `(w0,w1,w2,q_mode)`；
- 暂时使用相同的三个绝对宽度集合；
- CoDriving 配置生成器将 `num_upsample_filter` 确定性绑定为 `[w1,w1,w1]`，以保持融合头接口一致。

准确口径是：

> 三个 stage 来自模型原生拓扑；模型适配器负责把它们映射为统一搜索旋钮。当前框架尚未实现对任意输入网络自动发现剪枝 stage 和搜索边界。

## 3. 当前搜索属于什么流程

当前流程不是只在 Gold176 上运行的离线 replay，而是：

```text
冻结 Gold176 冷启动
-> 离线拟合初始 cost model
-> 对当前单模型、单 profile 候选池预测
-> acquisition 自动选择 B=4 个独立 genome
-> H800 真实生成/编译/测量 latency、energy、full AP
-> 四行原子回流
-> 重训 cost model
-> 生成下一轮请求
```

因此应称为**部署前的顺序式 hardware-in-the-loop 闭环搜索**。它含有在线实测反馈，但不是部署运行期间动态改变网络的 online inference。

启动后，候选预测、批量选择、模型物化、后端测量、反馈提交和下一轮生成均由控制器执行。人工规定的是搜索空间、目标、预算、acquisition 算法及模型适配合同，而不是每轮具体选择哪个宽度或精度。

本轮出现过 runner 修复、任务恢复和文件锁处理，但修复过程中冻结的 `measurement_request` 及其 SHA 不得改变。因此这些操作属于基础设施恢复，不构成人工替换候选。当前正在运行的 Stage5 v2 搜索不因本次文档审计而修改。

## 4. 重点反思：为什么目标已实测，图特征却仍是预测值

### 4.1 两类数据的角色不同

当前表中的数据分为两类：

| 类型 | 作用 | 当前来源 |
|---|---|---|
| `latency/energy/AP` | cost model 的监督目标，也是最终 Pareto 指标 | acquisition 选中后在真实后端和数据集上测量 |
| graph features | cost model 的输入上下文，用于描述候选计算图 | Gold176 的图特征训练 surrogate，再由 `(model,width)` 预测 |

acquisition 在选择前需要为全部 343 个 width、686 个精度 genome 获得统一输入特征。此时大部分候选尚未物化，因此如果先为全部候选训练模型、导出 ONNX 并提取真实图特征，候选准备成本会接近穷举。**这个理由只支持未选候选在当前轮暂时使用 surrogate graph features，不支持已选且已物化候选继续使用 surrogate 回流。**

每个任务只有被选中的 16 个 genome（四任务共 64 个）需要支付真实测量成本。这些点本来就必须生成 checkpoint/配置、导出 ONNX、编译并执行 latency、energy 和 AP 测量，因此可以直接从已经生成的真实 ONNX 提取 actual graph features。它不要求额外物化其余候选，也不会使主动搜索退化为穷举。

正确结论应为：

> 未选候选使用 surrogate graph features 参与当前轮 acquisition；选中候选物化后，必须将 actual graph features 与实测 latency、energy、AP 一起原子回流，供下一轮 cost model 重训。

此前把“全候选预物化成本过高”用于解释“已测点为何没有 actual feature 回流”，混淆了候选预测和反馈训练两个阶段，是本轮流程设计中的重大错误。实测闭环的目的不是只回流三个目标值，而是回流该实测样本能够获得的完整可信训练记录：真实输入上下文、真实目标、可行性状态及证据 SHA。

### 4.2 当前真正缺失的环节

问题不在于“未选择候选没有真实图特征”，而在于：

> 一个候选被 acquisition 选中并完成 checkpoint、ONNX、编译、latency、energy 和 AP 实测后，当前流水线仍没有重新调用图特征提取器。

当前 source registry 在搜索前通过 `coldstart_width_conditioned_surrogate_v1` 为每个候选生成 graph features。measurement request 携带这份预测特征，反馈 finalizer 又把 request 原样并入在线反馈行。因此，本轮在线行虽然具有真实目标标签，`graph_features` 仍保留候选阶段的 surrogate 值。

这不是因为图特征无法提取，也不是因为 latency、energy、AP 可以替代图特征，而是当前 v2 流水线遗漏了“物化后重新扫描并替换输入特征”这一步。

### 4.3 为什么这是实质问题

该遗漏产生四项风险：

1. **输入误差不随反馈消失**：真实标签已经回流，但对应输入仍可能偏离物化后的真实计算图；
2. **结构变化可能被宽度代理掩盖**：padding、通道对齐、算子数、FLOPs、融合边界和 reformat 数不一定只由三个宽度线性决定；
3. **不确定度可能偏乐观**：模型把 surrogate 误差当成确定输入，预测区间没有覆盖这部分误差；
4. **论文表述风险**：当前不能宣称“每轮实测后真实图结构特征也已回流”，只能宣称“真实目标回流，候选结构上下文由冷启动 surrogate 提供”。

### 4.4 正确的双层特征合同

后续正确流程应为：

```text
未选择候选：surrogate graph features
被选择并物化：执行真实 graph extractor
本轮测量请求：保留选择时 surrogate 快照，保证决策可复现
在线反馈行：写入 actual graph features，并记录 surrogate/actual 差异
下一轮 cost model：冷启动真实特征 + 已测点真实特征
```

至少新增以下字段：

```text
graph_feature_provenance = surrogate | extracted_actual
candidate_graph_features_sha256
materialized_graph_features_sha256
graph_feature_drift_report
```

真实特征提取发生在候选已经选定之后，不得反向修改当前批次选择，也不能利用真实 AP、latency 或 energy 生成图特征。

### 4.5 当前 Stage5 v2 如何处理

当前四任务已经执行大部分固定预算，不能在中途改变特征合同，否则前后轮次不再可比。因此：

1. 保持当前后端和请求不变，完成 v2 固定预算搜索；
2. 搜索完成后，对全部 64 个已物化在线 genome 回填真实图特征；
3. 统计每类特征的 surrogate/actual 误差、排序变化和 Pareto/HV replay 差异；
4. 若误差较小且不改变主要选择/Pareto结论，v2 可作为 surrogate-assisted 搜索，并在论文中准确披露；
5. 若误差显著或改变主要结论，则当前轨迹只能作为 pilot，正式论文搜索需要使用修正后的 actual-feedback v3 协议重跑。

禁止直接用回填后的真实特征重写历史 acquisition 记录；只能进行带版本号的离线 replay 或启动新搜索。

## 5. 两个模型能否暂时固定相同剪枝旋钮和宽度编码

### 5.1 当前阶段可以固定

对当前 Pyramid 和 CoDriving 两个受控模型，可以暂时固定三维宽度编码，理由是：

- 两者都存在三个按空间尺度顺序排列的主干 stage；
- 三个 stage 的主要结构压缩动作都是调整输出通道数；
- `(w0,w1,w2)` 在两个模型中具有一致的宏观语义，而不是用无关参数强行凑成三维；
- 统一编码有利于 Gold176 学习跨模型的通道规模、计算量和性能趋势；
- 当前论文首先需要验证“固定合法搜索空间内，能力条件化的自主搜索是否有效”，不必同时解决任意网络的自动旋钮发现问题。

因此，当前阶段无需为了追求通用性立即把 genome 改成可变长度，也不应中断正在运行的 Stage5 搜索。

### 5.2 必须限定论文表述

两个模型可以共用编码，不等于两个模型结构完全相同，也不等于搜索空间由扫描自动生成。论文应写为：

> 针对具有三级多尺度主干的 Pyramid 和 CoDriving，模型适配器暴露三个同语义的 stage-width 旋钮；框架在该合法空间内自主联合搜索结构宽度和精度。

当前不能写为：

> 框架输入任意模型后自动发现三个剪枝层级，并自动确定所有宽度范围。

### 5.3 当前固定方案的约束

暂时固定编码需要满足：

1. 每个模型 adapter 明确记录 `w0/w1/w2` 到真实层组的映射；
2. adapter 自动验证残差、上采样和融合头的通道合同；
3. 对齐或 build failure 由真实 feasibility 结果回流，不用人工删除候选；
4. CoDriving 的 `[w1,w1,w1]` deblock 绑定作为确定性拓扑约束披露，不冒充搜索结果；
5. 两个模型使用同一编码不代表必须选择相同宽度，最终配置仍由各自独立搜索决定。

### 5.4 后续扩展方向

扩展到层级数量不同、存在 depthwise/group convolution、分支结构或 Transformer block 的模型时，再实现：

- 从计算图识别可压缩通道等价类和依赖关系；
- 按原始通道数生成相对剪枝率与硬件对齐后的合法宽度；
- 支持不同数量的 stage 或结构组；
- 将残差、concat、deblock 和融合边界约束纳入合法性生成器；
- 由 capability profile 约束可执行域，但不写死 FP16/INT8 的优劣。

这属于框架通用化工作，不是当前两个模型论文级搜索收口的前置条件。

## 6. 本次审计结论

1. CoDriving 的三层来自模型原生三级 BEV backbone，不是模仿 Pyramid；但搜索旋钮、绝对宽度集合和 deblock 绑定是人工定义的 adapter 合同。
2. 当前是部署前的顺序式硬件闭环搜索，不是纯离线预测；每轮 latency、energy、AP 均为真实测量并回流。
3. 当前每轮具体 genome 由 cost model 和 acquisition 自动决定，人工只定义统一协议并处理基础设施异常。
4. 未测候选使用 surrogate 图特征是控制搜索成本所必需的近似；已物化候选没有回填真实图特征则是当前实现缺口。
5. Stage5 v2 已按原协议完成，并已对 64 个在线点执行 actual feature 回填与 drift/replay；因 10/12 个可比较轮次改变候选选择，v2 只能作为 pilot，正式轨迹必须使用 actual-feature feedback。
6. Pyramid 和 CoDriving 可以在当前受控实验中暂时共用 `(w0,w1,w2,q_mode)`；论文必须将其描述为模型适配器定义的三级主干搜索空间，而不是任意模型自动旋钮发现。

## 7. 阶段5新增收口门禁

除 28 号文档已有门禁外，增加以下检查：

- 冻结并保留所有历史 request 中的 surrogate graph feature SHA；

## 8. 修正后需要重新进行的实验与耗时

### 8.1 不需要重做的部分

以下证据在修正后仍然有效：

1. Gold176 冷启动表及其 44 组真实 graph features；
2. H800 capability profile 与 S1/S1-P 探针；
3. 阶段 4 的 cost-model、loss 和 acquisition 选择；
4. 两个模型的 adapter、686-genome 合法候选注册表；
5. v2 的流程 pilot、图特征 drift 和 teacher-forced replay；
6. v2 四任务的结果可作为方法调试和轨迹敏感性对照，但不能进入正式主结果。

### 8.2 round 0 是否需要重新实测

四个任务的 round 0 尚无在线反馈，因此 surrogate-feedback 与 actual-feedback 使用完全相同的 Gold176、profile、seed、候选池和 acquisition。回放审计也确认 4 个 round 0 按构造不变。

因此，可以在满足以下条件时复用 v2 round 0 的 16 行真实测量，而不重复 GPU 实验：

1. v3 重新生成的四份 round-0 measurement request 与 v2 的 selected IDs 完全一致；
2. genome、profile、seed、request-row SHA 和测量产物 SHA 均通过等价审计；
3. 从绑定的真实 ONNX 重新提取 actual graph features；
4. v3 训练视图只导入这 16 行 round-0 反馈，不导入 v2 round 1～3 的任何标签；
5. 导入过程生成独立的 provenance 与 round-0 import audit。

这不是使用 pilot 先验，因为这 16 行正是 v3 在相同初始条件下必然选择并测量的第一批配置。若任一 SHA 或 selected ID 不一致，则放弃复用并完整重跑 64 行。

### 8.3 必须重新进行的实验

| 顺序 | 实验 | 规模 | 必须重做的原因 |
|---:|---|---:|---|
| 1 | actual-feedback 原子回流 smoke | 1 个历史/临时四行批次 | 验证 feedback 同时保存 surrogate 快照与 actual 特征，且下一轮实际读取 actual |
| 2 | round-0 等价导入审计 | 4 任务、16 行 | 决定是否可复用首轮真实测量 |
| 3 | v3 正式 round 1～3 | 4 任务、12 轮、48 个新实测点 | v2 的 10/12 个后续轮次选择会改变，不能复用 |
| 4 | v3 provenance 完整性审计 | 64 行 | 验证所有在线行均为 `extracted_actual`，无静默 surrogate fallback |
| 5 | v3 Pareto/HV 与 v2/v3 轨迹对照 | 4 任务 | 最终候选和标签改变后必须重新计算 |
| 6 | v3 独立复测 | 16 配置 × 3 次性能 + 16 次 full AP | v3 最终前沿和代表点可能改变，v2 复测不能代替 |

其中第 1 项可以使用已有物化 ONNX 完成 CPU 合同测试，不需要重新训练模型。第 3 项才是主要 GPU 成本。

### 8.4 基于 v2 实测的耗时估计

v2 四任务 round 1～3 的累计任务时间为：

| 任务 | v2 round 1～3 实测耗时 |
|---|---:|
| Pyramid + TVM | 3 小时 45 分 |
| Pyramid + TensorRT | 3 小时 03 分 |
| CoDriving + TVM | 10 小时 26 分 |
| CoDriving + TensorRT | 10 小时 22 分 |

四任务并行时，关键路径约为 `10 小时 26 分`。48 行 actual graph feature 提取按历史平均每行约 10 秒计算，约增加 8 分钟；v2 独立复测实耗约 3 小时 42 分。

若 round 0 等价审计通过并复用，理想墙钟为：

```text
round-0 审计与 smoke       约 0.5~1 小时
v3 round 1~3              约 10.5 小时
actual/provenance/closure 约 0.2~0.5 小时
独立复测                  约 3.7 小时
合计理想值                约 15~16 小时
考虑新候选训练和重试缓冲  建议预留 17~20 小时
```

如果 round 0 不能通过等价审计，需要完整重跑 64 行。依据 v2 实测：

```text
四任务完整搜索  约 33 小时 28 分
独立复测        约 3 小时 42 分
审计与回填      约 0.2~0.5 小时
总计            约 38 小时，建议预留 40~42 小时
```

### 8.5 修正后的阶段 5 停止条件

只有同时满足以下条件，阶段 5 才能正式收口：

```text
4/4 tasks budget_exhausted
16/16 rounds have atomic feedback
64/64 online rows use extracted_actual graph features for subsequent training
0 silent surrogate fallback
four v3 Pareto/HV audits complete
16/16 independent validation configurations pass the frozen consistency policy
```
