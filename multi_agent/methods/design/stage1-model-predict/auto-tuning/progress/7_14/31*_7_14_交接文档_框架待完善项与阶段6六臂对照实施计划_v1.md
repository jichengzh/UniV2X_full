## 3. 框架仍待完善的部分

### 3.1 最初模型扫描并未自动发现搜索旋钮

29 号文档已经确认：CoDriving 的三个 stage 来自原模型三级 BEV backbone，不是为了模仿 Pyramid 凭空拆分；但把它们暴露为 `(w0,w1,w2)`、采用哪些宽度集合，以及 deblock 使用 `[w1,w1,w1]`，仍是人工编写的 model-adapter 合同。

当前能力边界应准确表述为：

> 对具有三级多尺度主干的 Pyramid 和 CoDriving，模型适配器暴露三个同语义 stage-width 旋钮；框架在适配器给出的合法空间内自主搜索结构宽度与精度。

当前不能表述为：

> 输入任意模型后，框架可以自动识别所有可剪枝层、自动生成通道等价类并自动确定宽度上下界。

后续通用化需要补齐：

1. 从 ONNX/FX/Relay 图中识别 channel dependency 和可压缩等价类；
2. 自动处理 residual、concat、deblock、group/depthwise convolution 的通道约束；
3. 根据原始宽度、硬件对齐和 feasibility probe 生成合法宽度，而不是固定绝对集合；
4. 支持不同 stage 数量和可变长度结构 genome；
5. 扫描器只收束可执行空间，不根据历史性能硬编码 FP16/INT8 优劣。

这不是当前 Pyramid/CoDriving 主表的前置阻塞项，但必须作为论文适用范围和后续扩展限制披露。

**论文描述口径**：本文当前优化对象是协同 3D 感知模型中的多尺度 BEV 特征提取主干，具体为 Pyramid 与 CoDriving 的 ResNet/ResNeXt 类 backbone 子图；框架联合选择主干各 stage 的通道宽度与计算精度，并通过目标硬件后端的内层调度优化和真实测量反馈寻找 Pareto 配置。当前结果属于“协同感知算法主干优化”，不等同于完整协同感知系统的端到端加速。

### 3.2 actual graph feature 双层合同已修复但尚未四任务验证

正确合同已经在 Pyramid v3 跑通：

```text
未选择候选：使用 surrogate graph features 参与 acquisition
选中并物化：从真实 ONNX 提取 actual graph features
当前批次：保留选择时 surrogate 快照，不反改 request
下一轮训练：使用 actual features + 三目标真实标签
```

仍需通过 CoDriving 两任务证明该合同不是 Pyramid 专用实现，并完成四任务 `0 silent fallback` 审计。

### 3.3 `S` 维度采用内外双层搜索

当前方案不是把 `S` 冻结为一个不参与优化的后端常量，也不要求把具体 `schedule_id` 直接编码进外层 genome。框架采用内外双层搜索：

```text
外层搜索：genome = (w0,w1,w2,q_mode)，决定结构压缩 P 与精度 Q
内层搜索：对外层选中的每个候选执行目标后端的 schedule/tactic 搜索 S
真实评估：测量内层优化后产物的 latency、energy、AP 与 feasibility
闭环更新：将包含硬件调度效果的真实结果回流 cost model，驱动下一轮外层选择
```

软硬件联合体现在：外层不是依据 FLOPs 或软件代理独立决定结构与精度，而是依据经过内层硬件调度优化后得到的真实反馈学习哪些 `P×Q` 组合在当前 capability profile 上有效。`S` 因此是每个候选真实评估过程中的内层优化变量，并通过实测结果与外层搜索耦合；它不是被忽略，也不需要作为外层显式基因与 `P×Q` 做笛卡尔积枚举。

Stage6 必须固定每条臂是否执行内层 `S` 搜索、内层 tuning trials/GPU-hours，以及内层结果能否回流外层。这样六臂比较的是软件选择、硬件调度及二者耦合方式，而不是比较谁获得了更多未披露的调优预算。

### 3.4 测量和资源调度仍有工程缺口

以下事项属于必须完成的框架优化，目标是缩短搜索墙钟、提高 GPU 利用率，并保证不同搜索臂和不同后端在相同资源合同下公平测量：

1. 多用户 GPU 占用会触发 preflight 失败，控制器虽能保持 request SHA 恢复，但还需统一资源租约和自动迁移策略；
2. Bash 控制器运行中不能热覆盖脚本；后续必须按版本目录启动，不修改正在执行的文件；
3. AP 是当前关键路径，应保留跨 GPU 分片，同时保证 sparse shard 不映射到同一 GPU；
4. 每阶段需要统一 monotonic start/end、GPU-hours、backend tuning trials 和失败等待时间，便于阶段6公平比较；
5. feasibility failure 必须保留真实失败原因，不能写成 `AP=0`，也不能被基础设施失败错误消耗预算。

优化完成后应同时输出吞吐与公平性审计：每批有效 GPU 并行度、排队/重试时间、AP 与 build/tune 占比、外层实测 genome 数、内层 tuning trials、GPU-hours 和 wall-clock。调度优化只能减少基础设施空转，不能改变已冻结候选、测量次数或某一实验臂的有效计算预算。

### 3.5 Cost model 与论文创新性仍有后续项

阶段4已经支持 Stage5 搜索启动，但仍未证明所有复杂组件都有增益。后续需要：

- 用正式 v3 轨迹补齐 value model、uncertainty、acquisition 和 feedback 消融；
- 报告 Pareto recall、HV/regret、区间 coverage，而不只报告单目标误差；
- 保持主预测目标为 latency、energy、AP，避免无证据增加独立预测头；
- 将 v3 在线反馈用于闭环 replay，证明性能来自真实反馈而不是候选池先验。

## 5. `original/default` 固定基线到底是什么

### 5.1 它不是一条需要执行 16 点预算的搜索臂

固定基线用于回答：在不做结构压缩、不量化、不使用 TVM/TensorRT 编译与调度优化时，原始模型按原生 FP32 执行路径的性能是多少。

基线定义冻结为：

```text
width = 原始宽度 [64,128,256]
q_mode = fp32
model/scope/input/batch = 与 Stage6 主实验完全相同
backend policy = none
execution = 原始框架的原生 FP32 推理，不使用 TVM/TRT 编译产物
```

它只需要一个配置，不应为了凑 `T=16` 重复选择 16 次。公平做法是对冻结的原生 FP32 路径执行与其他臂最终点相同的独立测量重复，并报告 latency、energy 和 AP。该基线预期明显慢于最终优化版本，可报告是否达到 `10x` 以上加速；但不能以“必须得到 10x”为条件挑选或人为降速基线。

### 5.2 已有实测数据能否直接使用

**可以复用，但必须先通过合同审计；不是默认重测。**

已有行只有同时满足以下条件，才能直接成为 Stage6 baseline：

1. 同一 target model 和同一原始 checkpoint；
2. 同一 H800、同一 backbone/full-engine scope、同一输入 shape 和 batch；
3. 同一 `q_mode=fp32` 数值合同；
4. 明确为原始框架原生执行，未使用 TVM、TensorRT、量化或其他编译加速产物；
5. latency、energy、AP 均完整，并绑定 checkpoint、运行配置与 AP 报告 SHA；
6. 测量脚本、warmup/iteration 和能耗积分口径兼容；
7. 具备当前独立重复要求，或只补缺少的重复测量。

Gold176 和 Pyramid v3 的 base 行是 FP16 且经过目标后端，不能作为本节定义的 `original/default`。若历史结果中存在满足以上七项的原始宽度 native-FP32 行，可以直接复用并只补缺失的独立重复；否则补测一个固定基线，不重新训练、不执行搜索。旧 13 号文档中的 `56.235 ms` 已确认来自 TVM default/untuned，排除出 native `original/default`，只保留为 TVM 内部 lowering/schedule 参考；`6.52 ms` 和 TRT `0.870 ms` 也已含后端优化，分别属于 schedule-only/后端优化证据，不能作为 default。

### 5.3 `default` 口径已确认

`original/default` 统一指原始宽度、FP32、无 TVM/TRT 加速的原生推理。TVM 和 TRT 六臂表共享这一相同起点；`schedule-only` 则保持原始宽度与 FP32 不变，只引入对应目标后端的内层调度/编译优化，从而隔离硬件调度本身的收益。

## 6. Stage6 六臂的推荐实现定义

### 6.1 共同实验口径

第一轮主实验建议固定：

```text
model = Pyramid
device = H800
backend = TVM / TRT 分别独立执行完整六臂
scope/input/batch/AP contract = 与 Pyramid actual-feedback v3 一致
cold-start = 每个后端使用各自隔离且冻结的 Gold176 训练视图
candidate grid = 343 widths x {fp16,int8}
B = 4
可搜索臂 candidate measurement upper bound = 16
最终验证 = 每臂最多 4 个可信前沿点，性能 3 次重复 + full AP
```

TVM 与 TRT 均执行完整六臂。两张表中的 `original/default` 都是后端之外的原生 FP32 推理；`schedule-only` 是原始宽度与 FP32 保持不变、只交给当前目标后端执行编译与内层调度优化，因此不会与 default 退化成同一项。两个后端仍是彼此独立的搜索任务，不在同一次搜索中作为可选基因。

### 6.2 六臂定义与待冻结内容

| # | 臂 | 推荐定义 | 必须冻结的内容 |
|---:|---|---|---|
| 1 | original/default | 原始宽度 + FP32 + 原始框架原生推理；不使用 TVM/TRT，无搜索 | 审计历史 native-FP32 行能否复用；统一 warmup、重复次数、scope 和输入 |
| 2 | compression-only | 在 `(w0,w1,w2,q_mode)` 中搜索 FP16/INT8，但 acquisition 不读取目标后端实测 latency/energy；最终选中点仍统一真测 | 冻结为参数量/FLOPs、AP surrogate 和静态图特征驱动的 hardware-blind acquisition |
| 3 | schedule-only | 固定原始宽度与 FP32，只引入当前目标后端的编译和内层 schedule/tactic 搜索 | TVM/TRT 各自的 tuning/tactic 合同、trials、GPU-hours、seed 和最终测量重复；它不使用 `T=16 genome` |
| 4 | compress -> tune | 第一阶段在无 tuned-backend feedback 下选择 12 个 FP16/INT8 压缩候选；第二阶段锁定最多 4 点执行冻结的目标后端 tuning | 固定 `12+4`，第二阶段每点使用相同 tuning trials，运行中不得修改预算 |
| 5 | tune -> compress | 先在 base 图上得到 schedule policy，再压缩；压缩后不重新 tune，用于检验 shape/schedule 失配 | 保留反序串行；不兼容记为真实 feasibility failure，禁止 fallback 或压缩后 retune |
| 6 | joint SHCoSearch | 复用 Pyramid TVM actual-feedback v3：外层搜索 P×Q，选中候选执行内层 S 调度优化，内层优化后的真实结果回流并更新下一轮外层选择 | 固定每个候选的内层 tuning 合同并统计 trials/GPU-hours；不要求将具体 schedule_id 编码为外层基因 |

### 6.3 推荐预算归一化

不能只用一个 `T=16` 掩盖不同计算成本。建议同时报告两类预算：

1. **外层样本预算**：真实物化并获得终态的网络 genome 数；搜索型臂上限 16；
2. **内层编译预算**：backend tuning trials、GPU-hours 和 wall-clock。

推荐第一版冻结方式：

| 臂 | 外层 genome 预算 | 内层调优预算 |
|---|---:|---|
| original/default | 1 个固定配置 | 无内层后端调优；只做原生 FP32 独立重复测量 |
| compression-only | 16 | 所有点使用同一 default/标准 build effort |
| schedule-only | 1 个固定网络 | TVM/TRT 分别使用预先冻结的 tuning/tactic 合同，并报告 trials/GPU-hours |
| compress -> tune | 第一阶段最多 12，第二阶段最多 4 个锁定点 | 每个锁定点相同 trials，总 GPU-hour 不超过预定上限 |
| tune -> compress | base tune 1 次，压缩候选最多 16 | 只允许复用 base-derived policy，不允许压缩后 retune |
| joint | 16 | 每个点使用当前 v3 冻结 profile；记录累计 trials/GPU-hours |

`12+4` 已冻结为正式预算合同，运行中不得根据第一阶段结果修改。

### 6.4 `tune -> compress` 的语义风险

TVM schedule 通常绑定具体 tensor shape。base `[64,128,256]` 的具体 schedule artifact 不能保证直接用于其他宽度。因此臂5不能模糊地写成“先调优再剪枝”然后对剪枝图重新 autotune；那会退化成臂4并获得额外预算。

正式实现冻结为：保留反序串行臂，冻结 base 图得到的 schedule rule/template 或 tactic policy，在新 shape 上尝试实例化但不重新搜索。不可迁移、不兼容或构建失败均记录为该臂的真实 feasibility failure，并将成功率/失败率纳入结果表；禁止 fallback 到重新调优路径，也禁止删除失败点后只汇报成功子集。

该臂的研究假设是反序串行容易因 shape/schedule 失配而弱于双层联合搜索，但实验必须忠实执行冻结合同。失败率可以成为机制证据，不能通过人为减少其预算、选择已知坏模板或改变输入口径来预设结论。

## 10. Native FP32、历史 `50+ ms` 与 TVM 对比口径修正（2026-07-20）

### 10.1 当前 `3.2187 ms` 到底是什么

当前固定基线的证据为：

- 产物：[`stage6_native_fp32_baseline_v1.json`](${V2X_ROOT}/results/stage6_pyramid_launch_gate_20260720/stage6_native_fp32_baseline_v1.json)；
- 硬件：H800；
- scope：`pyramid_multiscale_backbone`，不是完整协同感知端到端网络；
- 输入：`[2,64,128,256]`；原始宽度：`[64,128,256]`；
- 实现：PyTorch eager FP32，CUDA `Conv2d` 默认使用 cuDNN；
- 三次独立重复的 p50 分别为 `3.218688 / 3.220368 / 3.218480 ms`。

因此 `3.2187 ms` 是可信的**原生框架部署基线**，但不能表述成“不使用任何优化库的朴素 FP32 计算”，也不能扩展成完整模型延迟。cuDNN 本身是 NVIDIA 平台上高度优化的工业级卷积后端；PyTorch 没有显式写出 `cudnn` 调用，不等于执行时没有使用 cuDNN。

### 10.2 图中 `50+ ms` 的准确来源

论文图 [`fig_background_latency_prune_curves.png`](${V2X_ROOT}/multi_agent/paper/Latex/Figures/fig_background_latency_prune_curves.png) 由 [`draw_background_latency_evidence.py`](${V2X_ROOT}/multi_agent/paper/Latex/Figures/draw_background_latency_evidence.py) 生成，直接读取早期 180 行表：

[`original60_quant_three_metric_summary_latest.csv`](${V2X_ROOT}/multi_agent/data/stage2_lut_generation_v1/generated/original60_quant_20260627/exports/original60_quant_three_metric_summary_latest.csv)

其中三条曲线并非同一实现路径下只切换 dtype：

| 曲线 | 历史表中的实际实现 | 60 点延迟范围 |
|---|---|---:|
| FP32 | H800 TVM Relax FP32；表中标记为 `metaschedule_tuned`，不少行由早期疑似 FP16 标签记录重分类而来 | `9.827～54.444 ms` |
| FP16 | `h800_tvm_fp16_rewritten_tensorcore` 手工重写路径 | `3.024～15.099 ms` |
| INT8 | `h800_tvm_native_int8_backbone_subnet` 路径 | `1.723～10.573 ms` |

另一个经常引用的 `56.235 ms` 来自 [`exp1_untuned.json`](${V2X_ROOT}/results/exp1_untuned.json)，对应原始宽度 `[64,128,256]` 的 TVM default/untuned 测量。2026-07-20 对同一宽度重新执行 TVM FP32 smoke，default 为 `56.266551 ms`，说明该数量级可以复现；但 4-trial smoke 的所谓 tuned 值 `64.613633 ms` 只证明入口可运行，不构成充分调优结果。

图中随着剪枝率增大而总体下降、局部反弹的现象仍可作为“FLOPs/宽度与真实延迟不严格单调”的背景证据；但是该图混合了不同 schedule、rewrite 和量化实现，不能再用于以下主张：

1. 原始 PyTorch FP32 推理需要 `50+ ms`；
2. 同一后端、同一调度合同下 FP16/INT8 必然比 FP32 快约 `5～10x`；
3. 旧 hand-rewrite 路径代表当前自动后端的最终性能。

正式论文若保留该图，图注和正文必须将其降级为“历史异构实现下的硬件响应背景图”，或者使用统一后端、统一调优预算的新数据重绘，不能把它当作公平的精度消融图。

### 10.3 为什么历史 `50+ ms` 不能作为 `original/default`

`original/default` 要回答的是“用户直接运行原始模型时的实际性能”。在 NVIDIA GPU 上，PyTorch 默认调用 cuDNN 是正常部署行为。人为关闭 cuDNN 会构造一个弱化基线，可能扩大加速比，但不具备公平性。

历史 `50+ ms` 回答的是另一个问题：特定 TVM generic/default 或早期 MetaSchedule 路径在 Pyramid 图上的 lowering/schedule 质量如何。它可以作为 TVM 内部消融或失败案例，但不能替代 native PyTorch + cuDNN 基线。禁止为了获得 `10x` 加速而将二者交换命名。

### 10.4 当前 TVM 为什么弱于 cuDNN

当前证据只支持以下受限结论：**在 H800 + Pyramid backbone + 当前 TVM 自动路径和预算下，TVM 尚未超过 PyTorch/cuDNN**。主要原因包括：

1. cuDNN 针对 NVIDIA Conv 形状拥有成熟的内核库、tactic 选择和长期工程优化；
2. 当前 TVM generic lowering 对该图中的 group Conv、shape 和布局映射效率不足；
3. 早期较快的 FP16/INT8 行依赖 hand-rewrite 或不同执行路径，不能证明统一自动 TVM pipeline 的优势；
4. 当前 4-trial smoke 远不足以代表 TVM 的调优上限，也不能据此宣称 TVM 一定弱于 cuDNN。

因此，论文不能把“TVM 在 H800 上必然比 cuDNN 快”作为预设结论，也不能把当前失败扩大成“TVM 本身没有价值”。

### 10.5 TVM 的优势应如何体现

TVM 的主要研究价值应放在**可移植、可编程和跨硬件的自动后端**，而不是在 NVIDIA Conv 上与 cuDNN/TRT 做预设的单点速度胜负：

1. TRT/cuDNN 主要服务 NVIDIA 平台，TVM 可以面向不同 GPU、CPU 和边缘加速器生成代码；
2. TVM 提供可检查、可扩展的 IR、图改写、tensorization 和 schedule 搜索空间，适合承载本文内外双层自动搜索；
3. 不同硬件/编译 profile 下最优剪枝与精度配置可能变化，TVM 可用于证明框架能够根据能力探针和真实反馈重新学习，而不是复用 NVIDIA 先验；
4. 开源、可控的编译链有利于复现实验和分析 layout、fusion、materialization 等机制，TRT 更适合作为 NVIDIA 上限参照。

这些优势必须最终由至少一个非 NVIDIA 设备上的同协议实验支撑。在跨硬件实验完成前，只能写成设计动机与待验证假设，不能宣称已证明 TVM 的跨硬件性能优势。

### 10.6 对 Stage6 本轮比较范围的修正

本轮 H800 实验**不取消 TVM，也不把 TVM 搜索臂从框架中删除**，但调整其论文角色：

- TRT 六臂作为 NVIDIA/H800 上的主要性能对照，回答联合搜索能否在强部署后端上取得实际收益；
- native PyTorch/cuDNN FP32 `3.2187 ms` 作为共同的真实原始基线；
- TVM 在 H800 上保留完整协议或最小充分对照，用于验证后端条件变化、失败率、搜索决策变化和自动框架的适应性，不预设其必须超过 cuDNN；
- `56 ms` 级 TVM default/untuned 只作为 TVM 内部 lowering/schedule 参考，不作为原始模型基线；
- TVM 的正向性能优势留到非 NVIDIA 硬件的跨平台实验中验证。

本节修正第5～7节中可能引起误解的表述：Stage6 可以继续记录 H800+TVM 结果，但本轮论文主结论不再依赖“TVM 必须在 H800 上实现相对 cuDNN 的加速”。若时间受限，执行顺序为 `TRT 六臂正式表 -> H800 TVM 最小充分对照 -> 非 NVIDIA TVM 跨硬件表`，不得用 TVM `50+ ms` 代替 native baseline 夸大收益。

### 11.6 收口证据与结论边界

- 正式状态：`11/11` 执行槽获得可信成功终态或带 SHA 的明确 failure；四张表均为 `paper_ready=true`；

- TRT 上 joint SHCoSearch 在两个精度阈值下均为最低延迟方案；TVM/H800 上 native PyTorch/cuDNN FP32 延迟仍优于当前 TVM 自动路径，joint 的价值体现为后端条件改变后框架自动学习到不同结果，而不是预设 TVM 必须胜出。

## 12. 六臂正式实验的完整执行流程

### 12.1 共同实验边界

一次正式任务固定 `target model + hardware + capability profile`。TVM 与 TRT 分别运行独立任务，后端不进入 genome；结构与精度 genome 为 `(w0,w1,w2,q_mode)`。六臂共享相同候选全集、模型 checkpoint、数据集、AP 评估合同、能耗采样合同和最终独立复测协议，禁止读取其他臂的在线标签或用 surrogate 补齐实测指标。

### 12.2 Arm 1：original/default

1. 固定原始宽度 `(64,128,256)` 和 `q_mode=fp32`；
2. 使用 PyTorch eager + CUDA 默认部署路径，不经过 TVM/TRT 编译和额外调优；
3. 在 H800 上执行三次独立 latency/energy 重复和一次完整 AP；
4. 该结果作为两张后端表共享的速度、能耗和精度参考，不把 TVM default/untuned 伪装成原始部署基线。

### 12.3 Arm 2：compression-only

1. 在完整 `P x Q` 候选池中进行 backend-blind 排序，允许 `q_mode={fp16,int8}`；
2. acquisition 只能使用结构宽度、静态图特征、backend-neutral AP surrogate 和理论压缩成本，不允许读取目标 TVM/TRT latency、energy 或 tactic 标签；
3. 选择 16 个独立 genome，在目标 profile 下执行标准 build 和真实 latency/energy/AP 测量，但不追加 backend tuning trials；
4. 从实测点中按 AP floor 选择最低延迟点，并执行统一独立复测；若没有点满足阈值，仍报告最快可信实测点并将 AP 标记为约束违反；
5. **CoDriving 收口状态**：第14章正式计划已改为 backend-neutral `parameter_bits/BitOPs`，在 648 点有效池上重新排序并冻结 16 点，且审计确认没有使用 backend 标签。修正后 Top-16 仍全部为 FP16，这是联合分数的输出，不是沿用旧 FLOPs-only 排名；第11章 Pyramid 旧排名不因此自动获得同等证明。

### 12.4 Arm 3：schedule-only

1. 固定原始宽度 `(64,128,256)` 和 `q_mode=fp32`，不搜索结构或精度；
2. TVM 执行固定预算的自动 schedule/tuning，TRT 执行标准 tactic/build；
3. 产物必须先通过 backend 数值合同，再测量 latency、energy 和完整 AP；
4. 数值合同失败时以 feasibility failure 收口，不允许回退 native baseline、替换精度或用失败前 latency 填表。

### 12.5 Arm 4：compress -> tune

1. 第一阶段使用与 compression-only 相同的 backend-blind 准则筛选 12 个 genome；
2. 冻结其中 4 个候选后，才允许目标后端对每个候选使用相同 tuning trials；预算固定为 `12+4`，运行中不得根据结果改变拆分；
3. 4 个候选全部完成真实 latency/energy/AP 后生成可信前沿；
4. 最终点执行独立复测，并同时报告外层 genome、内层 trials、GPU-hours 和 wall-clock；
5. CoDriving 第14章已随 bit-cost 修复同步重新冻结 `12+4` 候选并完成补测；Pyramid 若沿用旧候选，仍须单独修复与复测。

### 12.6 Arm 5：tune -> compress

1. 只在原始宽度图上完成一次 backend tuning，冻结 schedule rule/template 或 TRT tactic policy；
2. 将冻结 policy 原样迁移到 16 个压缩 genome，不允许压缩后重新 tune；
3. 每个 genome 记录迁移成功、构建失败或不可迁移终态；
4. 成功点继续执行 latency/energy/AP 和独立复测；失败点计入正式失败率，禁止静默 fallback；
5. 若 16/16 均不可迁移，则该臂以 complete failure 进入论文表，指标记为 `N/A`，失败率作为实验结论。

### 12.7 Arm 6：joint SHCoSearch

1. 以 Gold176 和固定 capability profile 拟合初始 cost model；候选池中的 backend 由任务固定，genome 只含结构和精度；
2. 每轮对尚未实测候选预测 AP、latency、energy 与 uncertainty，并由 Pareto、探索价值和多样性 acquisition 选择 `B=4`；
3. 被选点依次完成 checkpoint/ONNX 物化、目标后端 build/tune、真实 latency/energy/AP 和 actual graph features 提取；
4. 4 点必须原子回流；任一点为公共 runner/基础设施失败时不消耗预算，可信 feasibility failure 可作为终态证据回流；
5. 将 actual graph features 和真实三指标加入训练集，重新拟合 cost model 后生成下一轮；共 4 轮，总实测预算 `T=16`，达到预算前不提前停止；
6. 预算结束后生成可信 Pareto/HV，并对代表点执行独立复测。Pyramid 与 CoDriving、TVM 与 TRT 均按此协议运行，任务之间不得共享在线反馈。

### 12.8 统一独立复测与制表

1. 只有 terminal、independently validated 且 evidence SHA verified 的成功点进入数值比较；
2. 每个最终候选执行三次独立 latency/energy 重复和一次完整 AP 评估；
3. 分别生成 TVM/TRT 表，并报告 config、AP70、latency、energy、speedup、HV、Pareto count、外层预算、tuning trials、GPU-hours、wall-clock 和失败率；
4. 主精度阈值为 `DeltaAP_max={0.05,0.10}`，补充宽松表使用 `0.20`；无阈值内点时展示最快可信实测点并突出 AP 违反，硬 failure 不伪造数值；
5. 六臂比较不得预设 joint 必须获胜。任何臂更优、不可迁移或数值失败都按冻结合同报告。

### 14.7 收口结论与论文边界

1. CoDriving Stage6 在当前冻结协议下正式收口，`paper_ready=true`，没有缺失臂或缺失证据；两档 AP 阈值得到相同胜出点，是因为各胜出点均已满足更严格的 `DeltaAP_max=0.05`；
2. TRT/H800 上 joint SHCoSearch 选择 `(16,32,64,int8)`，取得 `0.2976 ms/0.0708 J/6.2158x`，相对次优 compression-only 延迟降低约 `16.84%`、能耗降低约 `30.16%`；
3. TVM/H800 上 joint SHCoSearch 自动选择 `(16,32,64,fp16)` 而非 INT8，取得 `1.5027 ms/0.2076 J/1.2311x`；这说明同一搜索框架会随固定 backend profile 学到不同精度决策，而不是写死“INT8 必然更快”；
4. `tune -> compress` 在两个后端均 100% 不可迁移，证明 schedule/tactic 与压缩 shape 强耦合；`compress -> tune` 可运行且明显优于 TVM compression-only，但仍弱于 joint；
5. 本轮只证明 CoDriving 在 H800 的两种固定 profile 下的六臂有效性。TVM 的跨硬件优势仍需非 NVIDIA 实验，不能由本章 H800 结果外推。
