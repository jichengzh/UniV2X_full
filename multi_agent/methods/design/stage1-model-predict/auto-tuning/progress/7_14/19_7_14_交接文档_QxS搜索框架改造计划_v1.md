# 19_7_14 交接文档 - QxS 搜索框架改造计划 v1

> **状态修正 2026-07-08**: 本 v1 文档把 `backend/schedule_route/evidence trust policy` 过度放进了 `search_arm_id`，容易造成“外界传入先验策略”的误解。后续以 `20_7_14_交接文档_QxS搜索框架改造计划_v2_硬件后端能力扫描优先.md` 为准：backend/schedule/trust 是硬件/编译后端能力扫描与证据层字段，不是搜索 genome。搜索变量应收敛到 `q_axis + graph_boundary + mixed_policy`。

> 日期: 2026-07-08  
> 目的: 在阅读 `8_7_14_交接文档_Phase1_SMBO三精度Pareto_v3_框架驱动正解.md` 与 `9_7_14_交接文档_Phase1完成_SMBO框架执行全记录_v1.md` 后，结合 18* 文档中 G4-S4/G4-S5 的最新实测，制定下一阶段搜索框架改造计划。  
> 总原则: 保留“自动搜索 + 实测回流 + cost model 学习”的论文叙事，不把任何人工经验规则写死成最终决策。

## 0. 先读结论

现有 Phase1 框架的正确主线是：

```text
joint search space
  -> surrogate-assisted NSGA-II
  -> top-k candidate real measurement on H800
  -> feedback retrain
  -> final Pareto assembly with gold/evidence filter
```

8/9 两份文档已经纠正过两个关键错误：

1. 不能把 `fp32/fp16/int8` 拆成三个独立空间分别搜索，精度必须进入同一个 joint genome。
2. 不能把小空间穷举当成可推广方法，正确入口应是 `scripts/stage2_smbo_joint_nsga2_v1.py` 这类可 scale 的 surrogate-assisted NSGA-II。

现在新的问题是：`Q={fp32,fp16,int8}` 仍然太粗。G4-S4/G4-S5 证明，同一个 `q_axis` 下，不同 backend/schedule/fusion boundary 会产生完全不同的 latency 排序。因此下一阶段框架应从 `P x Q` 升级为：

```text
P x search_arm_id

其中 search_arm_id 显式绑定:
  q_axis
  backend
  schedule_route
  graph_boundary / mixed policy
  evidence trust policy
```

也可以在论文中表述为 `P x (Q x S)`，但工程实现上建议以 `search_arm_id` 为唯一搜索臂，避免 `Q` 与 `S/backend` 脱钩。

## 2. 最新实测对框架的约束

### 2.1 S5 FP16-CUTLASS 已可作为强 backend arm

结果文件：

- `${V2X_ROOT}/results/codriving_qxs_g4_s5_buildrun_summary_20260708.csv`
- `${V2X_ROOT}/results/codriving_qxs_g4_s5_buildrun_summary_20260708.json`

验证结果：

- 8/8 个 CoDriving backbone-only 点 full-engine build/run 成功。
- 8/8 个点均有 12 个 CUTLASS partition。
- 8/8 个点快于 S4 FP16 和 S4 当前 best arm。
- `median(S5/S4-FP16)=0.824`
- `median(S5/S4-best)=0.832`

框架含义：

- `fp16` 不再只是一个 precision，而至少有多个 backend arm：
  - `fp16__route_b_auto_tc`
  - `fp16__s5_cutlass_byoc`
- 搜索器必须能让 cost model 自动学习二者何时谁更优。

### 2.2 INT8-CUTLASS 入口可行，但不能直接作为主结果

结果文件：

- `${V2X_ROOT}/results/codriving_qxs_g4_s5_int8_probe_summary_20260708.csv`
- `${V2X_ROOT}/results/codriving_qxs_g4_s5_int8_probe_summary_20260708.json`

关键比例：

- 单层 `s8s8_i32 / fp16_ref = 1.382x`
- `s8s8_i32_deconv / fp16_deconv = 1.627x`
- 两层 INT8 带中间 boundary 相对两层 FP16: `1.287x`
- 两层 INT8 带中间 boundary 相对两次单层 INT8+output astype: `1.419x`

框架含义：

- `int8` 不能作为单独的整网开关。
- `int8` 只有绑定具体 backend 与 graph boundary 策略后才有意义。
- 当前可以把 INT8-CUTLASS 入口探针作为 backend design evidence，但不能进入 final Pareto。

### 2.3 跨模型证据不能直接混入同一 final frontier

Phase1 的 canonical final Pareto 是 Pyramid-LiDAR。G4-S5 最新 8 点是 CoDriving backbone-only。二者可以共同指导框架设计，但不能直接混入同一个 final frontier。

因此新的数据 schema 必须显式记录：

- `model_family`
- `network_scope`
- `dataset_or_input`
- `measurement_pipeline`
- `trusted_for_final_frontier`
- `trusted_for_backend_design`

否则会出现“用 CoDriving backend 结果替代 Pyramid final gold”的口径错误。

## 3. 改造目标

### 3.1 框架目标

把 Phase1/Stage2 搜索框架升级为：

```text
输入:
  search_space_manifest_v2
  model_scoped_training_table_v2
  evidence_registry

搜索 genome:
  (w0,w1,w2,search_arm_id)

特征:
  widths
  width interactions
  q_axis one-hot
  backend one-hot
  schedule_route one-hot
  graph_boundary one-hot
  source_confidence
  model_family one-hot or scoped model id

闭环:
  NSGA-II on surrogate
  measurement registry dispatch by search_arm_id
  real measurement feedback
  final Pareto filter by trust policy and model_scope
```

### 3.2 论文叙事目标

保留并强化下面叙事：

1. 框架不是固定选择 FP16 或 INT8。
2. 框架搜索的是 `shape x precision x backend/schedule` 的组合。
3. INT8 不一定总是优于 FP16，这不是叙事削弱，而是搜索框架必须存在的理由。
4. 搜索器不能靠人工规则禁用 INT8；应通过冷启动数据、真实测量回流、source confidence 和 cost model 自动学到 INT8 何时有效。
5. historical hand-rewrite 只能作为 backend design hint 或 warm-start prior，不能作为 final gold result。

## 7. 风险与防错

1. **跨模型污染风险**  
   CoDriving 的 S5 结果不能直接更新 Pyramid final Pareto。必须通过 `model_family/network_scope` 隔离。

2. **INT8 误判风险**  
   不能因为 pure INT8 慢就禁用 INT8。应保留 INT8 arm，让 cost model 从实测中学习。

3. **历史 hand-rewrite 过度提升风险**  
   hand-rewrite prior 可以 warm-start，但不能作为 final gold，也不能作为“自动框架最终结果”。

4. **AP 轴混淆风险**  
   latency/backend smoke 没有 AP gold。主论文三目标 Pareto 必须标出 AP 来源。

5. **measurement dispatch 失败重提风险**  
   joint search 必须继承 `stage2_smbo_joint_nsga2_v1.py` 的 failed set，失败 arm 不应无限重复提交。

6. **能量指标缺失风险**  
   S5 当前主要是 latency。若 final Pareto 仍要求 energy，应先补 energy measurement，或在结果中明确 energy 不可声明。

## 8. 当前最优修改方向

最有利于框架实现与论文叙事的方向是：

```text
不要选择 “固定 FP16” 或 “固定 INT8”。
也不要回退到 historical hand-rewrite final gold。

应把 backend/schedule/mixed policy 显式变成 search_arm_id，
让搜索框架通过冷启动数据和真实测量回流自动选择:
  fp16 RouteB
  fp16 CUTLASS BYOC
  mixed INT8 RouteB
  mixed INT8 CUTLASS
  或者放弃当前点上的 INT8
```

这样可以同时解释两类发现：

- `S5_fp16_cutlass` 在当前 CoDriving 8 点上明显强，是一个新强 backend arm。
- INT8 在当前 TVM/CUTLASS 路线下不保证快，说明搜索空间必须包含 backend 与 boundary，而不是把 `int8` 当孤立精度开关。
