**2026-07-07 主口径审查结论**:
- 7/5 前后的 `int8_tc` 数据证明:旧 NCHWc dp4a buildability wall 不是当前手写 tensorcore lowering 下的硬约束。
- 12_7_14 与 2026-07-07 快速复测共同证明:fp16 自动后端 **不是没有加速效果**。同一 base `[64,128,256]`、H800 GPU4 上，default/no-MS fp16 p50 **53.249ms**，Route B auto-tune split-fix p50 **3.558ms**，speedup **14.97x**，3 个输出 mean_rel_err 分别约 0.0017/0.0023/0.0034。手写 im2col+MMA full-engine route 虽为 6.51ms，但 output_2 错 17-18%，且慢于 Route B，因此不能作为最终自动框架实现。
- 2026-07-07 新增 H800 审查:无手写 im2col+MMA 的 native `int8` 路线在 9 个 PQS 粗格宽度上 **9/9 build_success=true**，所以当前真实问题不是“没有手写算子就无法 build INT8”。但这个 native direct route 不是 Route B auto-tune，不能被外推成“最终自动 INT8 无加速”。它只说明当前未接入同等级自动后端的 native INT8 多数点没有速度收益；在有历史 fp16 对照的 6 个点里，5 个 native INT8 慢于 fp16，只有 p50 小幅快于 fp16。
- 若最终框架采用 auto-tune，则 INT8 也应接入同等级自动后端口径。当前缺口是 **Route B-int8/等价自动 INT8 TensorCore 后端尚未落地验证**，不是 auto-tune 无效，也不是 INT8 理论无效。实现前不能用手写 int8_tc 结果补主结果，也不能用 native direct route 一锤定音地否定 INT8 搜索臂。
- 2026-07-07 14点启动 Route B-int8 闭合实验后的最新边界:QDQ ONNX 经过 Route-B-style Relax lowering 后没有暴露 `wmma/mma_sync/dp4a`，不能作为自动 INT8 TensorCore 后端；native full-graph INT8 TE PrimFunc 直接 `tune_tir(max_trials=8)` 在 Task #0 初始化后 17 分钟无进展、GPU4 空闲，已终止并归档；单 block 暴露为 int8 matmul 后 `MatmulInt8Tensorization` 可生成 `tvm_mma_sync=1` 并真测 p50 1.258ms。因此当前结论是:INT8 TensorCore 机制可用，但最终全图自动 Route B-int8 还缺“按 PrimFunc/block 分解并自动 tensorize/tune”的组合实现，不能用 monolithic tune_tir 或 QDQ 默认 lowering 闭合。
- 2026-07-07 15点 Route B-int8 base `[64,128,256]` 已完成第一版自动全图闭合:新增 `scripts/stage2_route_b_int8_auto_decomp.py`，按 Conv/Relu/Add 自动拆成 per-block Relax `call_tir`；49/50 Conv 使用 `MatmulInt8Tensorization`，`tvm_mma_sync=49`，首个 graph-input Conv 因 `uint8 zp=0` 不满足 s8 TensorCore 输入约束，自动 native fallback。H800 GPU4 full-range uint8 输入下，对 native direct INT8 full-ONNX reference 三个输出 **exact_equal=true**；p50 **6.975ms**，energy **1.317J**。相对 native direct INT8 base 11.099ms 加速 **1.59x**，相对同宽 fp32 no-tune 56.266ms 加速 **8.07x**/能耗降低 **8.65x**；但仍慢于 Route B fp16 3.558ms，只能说明 INT8 自动臂“可闭合且快于 native/fp32”，不能说明已优于 fp16。
- 2026-07-07 17点 Route B-int8 慢于 Route B-fp16 的根因定位已完成第一轮闭合:base `[64,128,256]` 的 isolated PrimFunc sum / VM latency = **0.973**，说明 6.968ms 几乎能被 per-block 分项解释；Conv accum 占 **4.538ms/65.1%**，独立 pack/requant 占 **1.539ms/22.1%**，Relu/Add 合计约 **0.468ms/6.7%**。静态字节上，padded int32 accumulator bytes 是真实 uint8 Conv output bytes 的 **31.3x**，padded/logical accumulator 为 **7.83x**。3 个 Phase1 代表点 `[24,32,96]`、`[32,32,128]`、`[64,32,96]` 也 exact，通过同口径 profiling 显示 pack/requant 稳定占 **19-20%**，小宽度 `[24,32,96]` 的 padded accumulator/output 高达 **101.7x**，实测 3.599ms 是 Phase1 旧 int8_tc 预测 1.779ms 的 **2.02x**。因此当前慢因不是“INT8 TensorCore 不工作”，而是 auto-decomp v1 为 correctness 采用了 padded int32 accum + 独立 pack/requant + 163 个 unfused PrimFunc，尚未达到 fp16 full-engine Route B 的融合/调度层级。

**2026-07-08 CoDriving G4/S5 最新补充**:
- G4 mixed QxS 8 点验证:CoDriving + TVM RouteB 下 pure INT8 8/8 慢于 FP16；`mixed_top25_flops` 4/8 快于 FP16 且 8/8 快于 pure INT8；`mixed_stride2_or_1x1` 0/8 快于 FP16 但 8/8 快于 pure INT8。结论是 `Q x S` 搜索空间有保留价值，但不能把 top25/mixed 写成固定规则。
- G4-S4 fp16 graph boundary 对照:把 graph boundary 从 fp32 改成 fp16 后，FP16/mixed/INT8 全部同步变快，但 INT8 相对 FP16 的排序没有翻转。该实验证明 fp32 boundary 是公共开销，不是 INT8 恒弱主因。
- G4-S5 FP16-CUTLASS:修复 `conv2d_transpose=NCHW/IOHW + LegalizeOps` 后，8 个 CoDriving 点 full-engine build/run 全部成功；`median(S5/S4-FP16)=0.824`，`median(S5/S4-best)=0.832`，8/8 快于 S4 FP16 与 S4 best。`S5_fp16_cutlass` 可作为新的强 backend arm。
- INT8-CUTLASS 入口探针:最小 `int8/uint8 input + int8 weight -> int32` conv 可进入 CUTLASS，`conv+bias+relu` 也可 fused；但单层 INT8 CUTLASS 已比 FP16 慢约 **1.38x**，int8 deconv native 比 fp16 deconv 慢约 **1.63x**，两层 INT8 中间 dtype/materialization boundary 相对两层 FP16 慢约 **1.29x**。因此当前不能说 INT8 无法进入 CUTLASS，也不能把 INT8 慢完全归因于 boundary；更准确是 raw INT8 kernel 未赢 FP16，叠加 accumulator/requant/padding/materialization/deconv mixed boundary 后全图更难超过 FP16。

## 7. 当前审阅结论

1. `results/phase1_pyramid_pareto.{json,csv}` 仍应被明确标注为 **9_7_14 Phase1 正式收口文件**；它证明了当时的 SMBO 闭环、precision-as-gene、前沿验证/回流流程。但其 TVM lat/energy 不是 12_7_14 之后的最终 auto-tune 主口径。
2. 12_7_14 是当前后端口径的覆盖性结论:手写 im2col+MMA route 已被降级为诊断/历史路线；最终论文框架应优先采用自动后端(Route B auto-tune 或后续同级自动后端)。因此所有依赖 `h800_tvm_int8_rewritten_tensorcore` 的 Q 轴结果只能作为诊断数据。
3. 当前最可信的数据应拆开使用:
   - **AP**: `AP_SOURCE_ORDER_README.md` 指向的 `front_ap_finetune_block1.json` + 4 对角 gold 锚。
   - **TRT lat/energy baseline**: `exp1_measured_data_v1.json` 中 TRT 侧 backbone-scope 真测。
   - **TVM auto-tune backend**: 以 12_7_14 Route B 3.53ms 及其 H800 `/exdata/.../la_fulltune/` 产物为准；2026-07-07 快速复测文件进一步确认 default/no-MS 53.249ms -> Route B 3.558ms。本 results 索引里尚无完整 Route B 化的 Phase1/Table1 文件。
   - **native INT8 无手写审查**: `native_int8_no_handrewrite_audit_20260707.json/csv`。结论是 build 不丢，但它不是 Route B-int8；只能说明 native direct route 多数点速度收益不成立，不能否定最终自动 INT8 后端。
   - **Route B-int8 启动证据**: `route_b_int8_tir_smoke_max8_result.json`、`qdq_lowering_audit_20260707.json`、`int8_tensorcore_gate_base_block_20260707.json`。结论是 QDQ 默认 lowering 不暴露 INT8 TensorCore，全图 monolithic `tune_tir` 路径卡住；但单 block 暴露为 int8 matmul 后可 tensorize 并真测。下一步要做的是自动分解/自动 tensorize 的全图组合，而不是回退到手写 full-engine 口径。
   - **hand-rewrite/int8_tc 诊断**: `q_int8tc_real_ratios_v1.json`、`pqs_ablation_results_real_v1.json`、`phase1_pyramid_pareto.{json,csv}` 的 int8_tc 部分。
4. `exp1_arms_v2.json` 最新但不最高可信；除 AP 源问题外，还需要按最终 auto-tune backend 口径重算 TVM 侧 latency/energy 后才能成为 Table 1 终稿。
5. 下一步推荐产物(等待用户确认调整方向后执行):
   - `results/exp1_table_arms_v3_autotune_goldap.json/csv`: 用 gold AP + Route B/自动后端口径重算 6 臂。

## 8. FP16/INT8 加速结论反思

### 8.1 需要纠正的历史叙事

不能再把早期结果概括为“FP16/INT8 量化在 TVM/H800 上没有加速效果”。更准确的表述是:

> FP16 和 INT8 早期没有体现出应有加速，核心原因是主要耗时算子没有进入对应的 TensorCore/INT8-TC fast path；这不是 H800 或 TVM 不支持低精度计算本身。

6_29 系列文档对根因的第一层判断其实是对的。`6_6_29` 已经写明:TVM/H800 并非不能在 full engine 中生成 FP16 TensorCore；1x1 rewrite 不加速，是因为 1x1 不是 lhc_07 的主要瓶颈，真正应处理的是 3x3/group conv。后续 `7_6_29`、`8_6_29`、`9_6_29`、`10_6_29` 也反复收敛到同一事实:default FP16 full-engine 虽然 dtype 是 FP16，但主要 conv/group conv 没有自动 lower 到 TensorCore fast path；INT8 早期问题则是旧 route 偏 QDQ-heavy/float32-heavy 或 native pack route 未张量化，不是真正公平的 INT8-TC 后端。

真正需要反思的错误在第二层:我们一度把 **generic/default MetaSchedule 路线慢或崩** 扩大解释成“自动后端不适合/不可行”，于是把手写 im2col+MMA TensorCore rewrite 提升为“正解”。`10_7_3` 当时记录“fp16_true(metaschedule)=47.53ms 是慢路线，正确的 11.64ms 来自 TIR 组卷积 TensorCore 重写”，这在当时用于纠正错误复现是合理的；但后来被过度外推成“最终框架应依赖手写算子”，这一步现在看是不成立的。

### 8.2 后续实验如何推翻旧收口

`12_7_14` 的 Route B 专项攻坚证明，问题不是 TVM 不支持，也不是 auto-tune 没有加速能力，而是早期没有走到正确的自动后端路径、搜索空间和修复:

- 早期 generic/default MetaSchedule 确实失败或很慢，典型表现包括 47ms 级慢路线、组合 build/measure 触发 CUDA illegal address。
- Route B 找到并修复 grouped-conv auto-tune 组合崩的根因:pre-split grouped-conv 的 group 边界，避免 floordiv 通道索引导致 buffer-region/静态内存推断越界。
- 修复后得到第一个“正确 + 组合真测”的自动后端数:base fp16 从 TVM-default 约 53.2ms 到 Route B auto-tune split-fix 约 3.53ms，3 个输出正确性干净。
- 2026-07-07 快速复测进一步确认同一事实:default/no-MS fp16 p50 53.249ms，Route B auto-tune split-fix p50 3.558ms，speedup 14.97x；手写 im2col+MMA 的 6.51ms 不仅更慢，而且 output_2 有 17-18% 错误。

因此，旧结论应改写为:

> 早期 FP16/INT8 不快，并不是 TVM/H800 不支持低精度，也不是量化搜索轴无意义，而是 default lowering/早期 generic MetaSchedule/native pack route 没有把主要耗时 grouped conv 送入正确的 TensorCore/INT8-TC fast path。手写 im2col+MMA 是定位和证明 fast path 可行性的诊断路线，不应作为最终自动框架实现。最终框架应把 S(schedule/backend lowering) 委托给正确的自动后端，并把 P×Q 搜索建立在该自动后端的真实 latency/energy 上。

### 8.3 对 INT8 搜索臂的当前边界

INT8 不能因为 native direct route 多数点不快而被判死。`native_int8_no_handrewrite_audit_20260707.json/csv` 证明无手写 im2col+MMA 时 9 个 PQS 粗格点 9/9 build 成功，所以“没有手写算子就 build 不了 INT8”不是当前主问题。但这个 native route 不是 Route B-int8，也不是同等级自动 INT8 TensorCore 后端；它只能说明当前 direct/native 路线大多没有速度收益，不能证明 INT8 自动后端无效。

当前应保留的判断是:

- FP16:Route B 自动后端已证明强加速，主结果应以 Route B 或后续同等级自动后端为准。
- INT8:机制上已有 `MatmulInt8Tensorization` 和 int8_tc 诊断证据，native direct route 也能 build；2026-07-07 单 block gate 证明暴露为 int8 matmul 后可以生成 `tvm_mma_sync` 并真测。随后 base `[64,128,256]` 的 Route B-int8 auto-decomp 已完成全图组合真测:49/50 Conv TensorCore + 1 Conv native fallback，correctness exact，lat p50 6.975ms，energy 1.317J。当前结论从“未闭合”更新为“base 单点已闭合，但未优于 Route B fp16，需多点重算判断 Pareto 价值”。
- 论文叙事中，Q 轴不应被“native direct INT8 不快”否定；应写成“INT8 需要接入与 fp16 同等级的自动 TensorCore 后端后再判定其搜索价值”。

### 8.4 2026-07-07 Route B-int8 闭合状态

本轮对“没有手写 im2col+MMA 时会怎样、auto-tune 是否真的失去 INT8 搜索臂”的最小真测结论如下:

1. **不会因为缺手写算子而普遍 build 失败**:`native_int8_no_handrewrite_audit_20260707.json/csv` 显示 9 个 PQS 粗格宽度 native INT8 均 build 成功。旧 NCHWc dp4a buildability wall 不是当前主矛盾。
2. **QDQ 默认导入不能算 Route B-int8**:`qdq_lowering_audit_20260707.json` 显示 QDQ ONNX 的输入/输出仍是 float32，标准 Relax lowering 后没有 `wmma/mma_sync/tvm_mma_sync/dp4a`。它没有把主要耗时层送到 INT8 TensorCore。
3. **全图 monolithic `tune_tir` 不是可行闭合路线**:`route_b_int8_tir_smoke_max8_result.json` 显示 native full-graph INT8 TE PrimFunc 在 `tune_tir(max_trials=8)` 下卡在 Task #0 初始化，17 分钟无进展且 GPU 空闲。这排除了“把整图一个 PrimFunc 直接交给 MetaSchedule”作为近期方案。
4. **INT8 TensorCore 机制本身可用**:`int8_tensorcore_gate_base_block_20260707.json` 显示代表性 base grouped-conv block 暴露成 int8 matmul 后可被 `MatmulInt8Tensorization` tensorize，生成 `tvm_mma_sync=1/mma_sync=1`，p50 1.258ms。
5. **base 全图自动组合已闭合**:`route_b_int8_auto_decomp_20260707/route_b_int8_auto_decomp_summary_20260707.json` 显示自动 per-block 分解路线在 base `[64,128,256]` 上 build 成功、correctness exact、latency/energy 真测完成。关键修复包括:
   - 不再把整图作为一个 monolithic TIR tune。
   - Conv 拆成 per-block `call_tir`；s8-compatible Conv 走 int8 im2col matmul + `MatmulInt8Tensorization`。
   - group conv 的 padded J 维不直接写真实 NCHW 输出，而是先写 padded int32 accum，再由独立 pack/requant PrimFunc 写真实 channel，修复 padded column alias。
   - graph input 第一层 `uint8 zp=0` 不满足 s8 TensorCore 输入约束，自动 native fallback，避免 uint8 full-range cast 到 int8 的 correctness 错误。
6. **INT8 慢于 fp16 的第一轮根因定位已闭合**:`route_b_int8_rootcause_20260707/route_b_int8_rootcause_summary_20260707.json/csv` 显示 base `[64,128,256]` 的 isolated PrimFunc sum / VM latency = 0.973；Conv accum 占 65.1%，pack/requant 占 22.1%，Relu/Add 约 6.7%。3 个 Phase1 代表点 `[24,32,96]`、`[32,32,128]`、`[64,32,96]` 均 exact，pack/requant 稳定占 19-20%。静态指标显示 padded int32 accumulator bytes 是真实 uint8 Conv output bytes 的 31.3x(base)、55.7x(`[64,32,96]`)、73.6x(`[32,32,128]`)、101.7x(`[24,32,96]`)。所以慢因不是 TensorCore gate 失败，而是 auto-decomp v1 的 padded accum + 独立 pack/requant + unfused per-block 实现形态。

所以，本轮闭合了四个边界:

- INT8 不是 build 不了。
- QDQ/default lowering 不是正确的自动 INT8 TensorCore 后端。
- 单 block INT8 TensorCore fast path 可用，且可以被自动后端在 base 全图中系统性暴露和调度。
- base 单点 Route B-int8 自动后端可复现、正确、快于 native direct INT8 和同宽 fp32，但慢于当前 Route B fp16；慢因已定位到实现形态，而不是 INT8 TensorCore 机制本身。

下一步具体实验不再是证明 Route B-int8 是否存在，也不应只盲跑更多 Pareto 点。应优先优化实现形态:融合 `pack/requant` 与后继 Relu/Add、减少 padded int32 accumulator 写回、为小 `nper` group conv 寻找 narrower tile/分组策略，并把 INT8 路线提升到接近 fp16 full-engine Route B 的融合层级。完成这些后再重跑 9-grid/Phase1 Table1 候选，判断 INT8 自动臂在最终 Pareto 中是有效臂、慢值臂，还是只在特定宽度区域有价值。不要回退到手写 full-engine im2col+MMA 作为最终口径。

### 8.5 对后续写作和实验的约束

1. 不再使用“TVM 不支持 FP16/INT8 加速”或“量化无效”这种表述。
2. 可以写“默认/早期 lowering 未进入低精度 fast path，导致表观无加速”。
3. 可以写“手写 im2col+MMA 曾作为诊断路线证明 fast path 可行，但因正确性和自动化框架不一致，被 Route B 自动后端取代”。
4. 后续所有 Phase1/Table1/PQS 主结果若采用自动框架，应使用 Route B/后续自动后端实测值；历史 hand-rewrite/int8_tc 数据只能放在诊断或消融解释中。
5. INT8 下一步必须先解决 auto-decomp v1 的 padded accum/pack/requant/unfused per-block 问题，再把改进后的 Route B-int8 扩展到多点真测；不能用当前 v1 慢于 fp16 直接否定 INT8 搜索臂，也不能用 native direct route 的慢值作为最终结论。

### 8.6 2026-07-08 G4/S5 后的新增约束

CoDriving G4/S5 后续实验进一步把“自动后端叙事”从 `Route B fp16/int8` 扩展到了 `Q x S_backend x boundary/policy`:

1. `mixed_top25_flops` 在 CoDriving 8 点中 4/8 快于 pure FP16，且 8/8 快于 pure INT8；这说明 `S` 维可以改变 INT8 表现，但不能被写成固定规则。
2. `fp16 graph boundary` 消除了上一批实验中的大量公共 dtype/materialization 开销，但 INT8 相对 FP16 的劣势没有翻转；因此 boundary 是重要控制变量，但不是 INT8 慢的唯一主因。
3. `S5_fp16_cutlass` 已 8/8 full-engine 闭合并快于 S4 FP16/S4 best，说明 library-backed BYOC 后端可以成为新的强自动后端候选。
4. `S5_int8_cutlass` 的入口可行，但当前最小 kernel 已显示 INT8 慢于 FP16；后续研究应聚焦 fullgraph mixed runner 与 cost model 特征，而不是仅证明 buildability。

因此，后续论文表述应避免两种极端:

- 不能说 “TVM 下 INT8 没有价值”，因为 mixed QxS 已经改善 pure INT8，且 INT8-CUTLASS 入口可行。
- 也不能说 “换成 CUTLASS 后 INT8 必然翻盘”，因为入口探针显示 raw INT8 CUTLASS kernel/deconv 当前仍慢于 FP16。

更稳妥的结论是:

> 本框架不把量化精度作为孤立开关，而是把精度、后端、边界和 per-block policy 作为联合搜索变量；不同组合的收益由冷启动数据和实测回流学习，而不是人工写死。

## 9. 对实验框架的修改建议

当前 Phase1/SMBO 框架已经证明了 “P×Q 搜索 + 实测回流” 的流程价值，但 2026-07-08 的结果说明，`Q={fp16,int8}` 过于粗。下一步框架应做如下修改。

### 9.1 搜索变量从 Q 扩展为 Q x S

建议把 genome 从:

```text
(w0, w1, w2, q)
```

扩展为:

```text
(w0, w1, w2, search_arm_id)
```

其中 `search_arm_id` 显式绑定以下字段:

| 字段 | 示例 | 作用 |
|---|---|---|
| `q_dtype` | `fp16`, `int8`, `mixed` | 精度语义，不再单独决定后端。 |
| `backend_id` | `routeb_tvm`, `s5_cutlass_byoc`, `routeb_int8_auto_decomp` | 区分自动后端实现。 |
| `boundary_dtype` | `fp32`, `fp16`, `uint8/int32` | 捕捉 graph boundary / materialization 成本。 |
| `policy_id` | `pure`, `mixed_top25_flops`, `mixed_stride2_or_1x1`, `fullgraph_mixed` | 表示 per-block precision/backend policy。 |
| `deconv_policy` | `native_fp16`, `native_int8`, `fallback_fp16` | CoDriving 中 `ConvTranspose` 的单独后端选择。 |
| `trust_scope` | `final_candidate`, `diagnosis_only`, `warm_start_only` | 控制能否进入 final frontier。 |

这样可以保留自动搜索叙事:框架不是被人工规则告知 “INT8 慢所以不用”，而是把多个 backend/policy 作为候选臂，由真实测量决定。

### 9.2 新增 backend capability manifest

每个 `search_arm_id` 应有 capability manifest，记录它能处理什么、在哪里 fallback、是否允许进最终 Pareto:

| 字段 | 用途 |
|---|---|
| `build_success` | 当前 width/backend 是否能 build。 |
| `run_success` | 是否能 VM/TRT runtime 运行。 |
| `correctness_status` | `exact`, `within_tol`, `failed`, `not_checked`。 |
| `partition_count` | 例如 S5 FP16-CUTLASS 的 12 个 CUTLASS partitions。 |
| `native_fallback_count` | 有多少层没有进入目标 backend。 |
| `diagnostic_counters` | `tvm_mma_sync`, `wmma`, `dp4a`, `call_tir`, `pack/requant` 等。 |
| `trusted_for_final_frontier` | `true`, `conditional`, `false`。 |

这可以避免把 smoke/probe 数据误放进最终主表。

### 9.3 measurement table 统一化

建议把所有真测结果落入统一 measurement table，而不是每条实验线各自写 JSON:

| 字段 | 示例 |
|---|---|
| `model` | `Pyramid`, `CoDriving` |
| `scope` | `backbone_only`, `full_model` |
| `width_key` | `64x128x256` |
| `search_arm_id` | `s5_fp16_cutlass_nhwc_deconv_native` |
| `latency_ms_p50` | 3.146 |
| `energy_j` | nullable |
| `ap_source` | `gold`, `surrogate`, `none_latency_only` |
| `correctness` | `max_abs_err=3.15e-4` |
| `source_file` | 对应 JSON/CSV 路径 |
| `doc_ref` | 例如 `18_7_14 §13.10` |
| `trusted_for_final_frontier` | `true/conditional/false` |

Phase1 的 Pareto 过滤只读取这个 table，并按 `trusted_for_final_frontier` 与当前 pipeline 口径过滤。

### 9.4 cost model 特征更新

新 cost model 不应只看 width 与 q one-hot。建议增加:

- `backend_id` one-hot。
- `boundary_dtype` one-hot。
- `policy_id` one-hot。
- `partition_count` / `native_fallback_count`。
- `n_int8_convs` / `n_fp16_convs`。
- `deconv_policy`。
- `padded_accum_bytes_over_output_bytes`。
- `pack_requant_ratio`。
- `materialization_boundary_count`。
- `source_confidence` / `trusted_scope`。

这些特征直接对应目前已经验证的慢因:INT8 raw kernel、padded accumulator、pack/requant、boundary、fallback 与 fusion depth。

### 9.5 acquisition 和补测策略

建议把补测策略从“只补 Pareto 邻域”扩展为“补不确定 backend/policy 分歧点”:

- 当 `S4 routeb fp16` 与 `S5 fp16_cutlass` 差异超过阈值时，补周围 width，用于学习 backend_id 的收益面。
- 当 `pure INT8` 与 `mixed_top25` 排序不同，补同 width 的 mixed/fullgraph policy。
- 当 `S5_int8_probe` 显示入口可行但 fullgraph 未闭合时，只进入 diagnosis queue，不进入 final Pareto queue。
- 当历史 hand-rewrite prior 与自动后端差异超过阈值，只作为 warm-start/disagreement trigger，不作为 gold。

### 9.6 final frontier 过滤规则

最终 Pareto 必须过滤:

1. `trusted_for_final_frontier=true` 或明确 `conditional` 且 pipeline 与论文主口径匹配。
2. `correctness_status` 通过。
3. 同一模型/scope/backend 下测量口径一致。
4. hand-rewrite/int8_tc、probe、smoke、失败归档只能作为诊断或 warm-start，不进入 final gold。

### 9.7 建议的下一步最小实现

下一步不要直接重跑大规模搜索。建议先做三个最小工程改造:

1. 新建 `phase1_qxs_measurement_registry_20260708.json/csv`，把目前 7/5 之后所有可用测量按统一 schema 装进去。
2. 新建 `phase1_qxs_search_space_manifest_20260708.json`，枚举当前允许进入搜索的 `search_arm_id`:
   - `routeb_fp16_splitfix`
   - `routeb_int8_auto_decomp_v1`
   - `routeb_mixed_top25_flops`
   - `routeb_mixed_stride2_or_1x1`
   - `s5_fp16_cutlass_nhwc_deconv_native`
   - `s5_int8_cutlass_mixed_probe_only`，标记为 `diagnosis_only`，暂不进 final frontier。
3. 修改 Phase1/SMBO 搜索入口，让 genome 使用 `(w0,w1,w2,search_arm_id)`，并让 final frontier 只读取 registry 中 `trusted_for_final_frontier` 合格的真实测量。

这三个改造完成后，再讨论是否启动 `S5_int8_mixed_fullgraph` 两点闭合实验，并把结果回流到同一个 registry。
