## 1. 当前判断

下一阶段主目标改为：稳定测试不同配置对应的 AP，并把 AP 轴从“历史 anchor/import”升级成可重复、可审查、可进入 LUT 的产品化链路。

当前 AP 不合理/不可用的根因不是单个数值错误，而是 AP source contract 没有产品化：

| 问题 | 当前证据 | 风险 |
| --- | --- | --- |
| original60 没有 AP source | `original60_ap_axis_gap_report.json` 中 60/60 为 `missing AP source_path` | 不能为 60 个 latency 配置直接写 measured AP |
| AP 依赖完整模型, 不依赖 TVM backbone workdir | original60 只有 backbone ONNX/TVM DB, 没有 full-model config+ckpt | 不能从 latency artifact 推出 AP |
| 历史 AP rows 是 import/reuse, 不是本轮 fresh eval | smoke 有 11 行, overnight merged 有 22 行, 其中 11 个 width 重复复用 | 可作起点, 但不足以证明当前 eval 链路稳定 |
| eval split 口径混用 | 现有 rows 中 `val_1789` 和 `val` 混用, 但多数 `num_samples=1789` | 需要统一标准写法, 否则不同 rows 可比性弱 |
| ckpt digest 缺失 | 现有 AP rows 的 `ckpt_digest` 均为 `unknown`; 部分 `ckpt_path=unknown` | 无法证明 AP 与具体 checkpoint 一一绑定 |
| 拟合模型文件容易误用 | `results/ap70_model_pyramid.json` 同时包含 fit model、anchor、weight-identity 表 | 不能把 model-fit/interpolation 当 measured AP |
| AP 非单调可能来自训练协议差异 | `mix_b/mix_d/p50b2_136` AP70 高于 base, 来源是不同 finetune/b4 expansion protocol | 不能在不标注 protocol 的情况下比较配置优劣 |

因此下一阶段不再优先补更多 latency 点。AP 轴先做 source registry、replay gate、stable smoke，再扩展 original60 映射。

## 3. AP 稳定测试规则

### 3.1 必须遵守

1. 只允许 `true_eval` 或 `true_import` 进入 measured AP row；predicted、estimated、model-fit、interpolated AP 一律不能写成 measured。
2. AP 测试对象是 full model checkpoint + eval config，不是 backbone-only ONNX 或 TVM workdir。
3. AP primary metric 统一为 `AP70`；同时保留 `AP30/AP50` 到 `secondary_metrics`。
4. dataset 统一写 `DAIR-V2X`，eval split 统一写 `val_1789`；如果历史源写 `val` 但 `num_samples=1789`，先在 source registry 中归一化并记录原始字段。
5. 同一配置 AP row 必须包含 `width`, `ckpt_path`, `ckpt_digest`, `config_path`, `eval_command`, `finetune_protocol`, `training_budget`, `source_files`, `raw_artifact`。
6. `ckpt_digest=unknown` 的 row 只能是 provisional；进入最终 LUT 前必须补 digest 或写明 checkpoint directory manifest digest。
7. `schedule_policy` 对 AP 使用 `not_applicable`；不得把 TVM default/tuned schedule 当成 AP 变化来源。
8. weight-identity transfer 只允许在有明确零填充/同权重证明的 pair 上使用，claim_status 标为 `claimable_weight_identity_transfer`，不得伪装成 fresh eval。
9. 若 AP replay 与历史 anchor 差异超过 0.003 absolute AP70，立即停止扩展，先定位 eval 环境/ckpt/split差异。

### 3.2 AP row claim status

后续 AP rows 或 source map 必须使用以下状态之一：

| claim_status | 含义 |
| --- | --- |
| `claimable_true_eval` | 当前 runner 对完整 DAIR val_1789 fresh eval 产生 |
| `claimable_true_import` | 来源文件是历史真实 eval 结果, 且字段可追溯 |
| `claimable_weight_identity_transfer` | 有明确同权重/零填充证明, AP 可继承 |
| `provisional_missing_digest` | AP 值可信, 但 ckpt digest/config digest 未补齐 |
| `no_claim_missing_source` | 没有 AP source |
| `blocked_model_fit_only` | 只有拟合/预测模型, 不能 claim |
| `blocked_protocol_mismatch` | ckpt、split、eval protocol 与目标配置不一致 |
| `quarantine_unstable_replay` | replay AP 漂移超过门限 |

#### Phase C.0: 首批 AP 稳定产出的硬性定义

本阶段“稳定产出 AP”不是指把任意 AP 数值写进 LUT，而是指每个配置都必须完成同一条可复查链路：

```text
width spec
  -> structural_prune_pyramid 生成 full-model config + init ckpt
  -> init ckpt flat state_dict 检查
  -> train_ddp --half 微调
  -> 锁定 best checkpoint
  -> ONNX export
  -> TRT FP16 engine build
  -> DAIR-V2X val_1789 full AP eval
  -> canonical AP row + raw artifact + claim/quarantine 状态
```

首批稳定产出的判定门槛：

| 项目 | 首批 smoke 默认规则 | 不能满足时的处理 |
| --- | --- | --- |
| 微调次数 | 每个新配置默认 `1` 次 finetune | 不补假 AP；写 failed/quarantine reason |
| 微调预算 | `epoches=31`，从 init@23 到 epoch31，即 8 个 finetune epochs | 若 bestval 在最后 epoch 或 AP 曲线未收敛，标记 `quarantine_unstable_or_underconverged`，下一批延长到 48/70 |
| seed/repeat | 新配置首批不默认做第二 seed；base/p50/mix_d 做 replay repeat | 若 AP 高于 base 或局部趋势异常，对该点补第二 seed 或延长训练 |
| GPU 并行 | H800 GPU0-4 五卡并行，每卡一个配置 | 某卡 OOM 或被大进程占用时，该配置顺延或换 GPU，不结束整批 |
| GPU idle 要求 | 微调和 AP eval 不要求 GPU 完全空闲 | 只要求显存足够、无 OOM 风险；并记录并发状态 |
| 数据集 | train 使用 HEAL/DAIR-V2X-C train split，历史口径 `train=4811` | 找不到数据集路径时该配置 blocked，不改用其他 split |
| AP eval split | DAIR-V2X-C val split，canonical 写 `DAIR-V2X val_1789`，`num_samples=1789` | 不允许用小样本 smoke AP 冒充 measured AP |
| AP row | `metric=AP70`，AP30/AP50 进入 `secondary_metrics` | 缺 ckpt/config digest 只能 provisional |

因此 Phase C 的首批新配置不是“跑到多少算多少”，而是固定 5 个 representative original60 配置同时跑完同一链路。默认配置如下：

| --- | --- | --- | ---: | ---: | ---: | --- | --- |
| ap_ft_01 | s0_024 | [24,128,256] | 0 | 1 | 31 | DAIR-V2X val_1789 | true_eval 或 quarantine |
| ap_ft_02 | s0_040 | [40,128,256] | 1 | 1 | 31 | DAIR-V2X val_1789 | true_eval 或 quarantine |
| ap_ft_03 | s0_056 | [56,128,256] | 2 | 1 | 31 | DAIR-V2X val_1789 | true_eval 或 quarantine |
| ap_ft_04 | s1_048 | [64,48,256] | 3 | 1 | 31 | DAIR-V2X val_1789 | true_eval 或 quarantine |
| ap_ft_05 | s2_160 | [64,128,160] | 4 | 1 | 31 | DAIR-V2X val_1789 | true_eval 或 quarantine |

5GPU 并行执行约束：

1. `CUDA_VISIBLE_DEVICES` 必须固定到上表 GPU；每张卡只跑一个 `train_ddp.py --nproc_per_node=1`。
2. master port 使用 `29700 + GPU`，避免五个单卡 DDP 进程互相冲突。
3. 训练前保存一次 `nvidia-smi` 和 `nvidia-smi pmon -c 1` 到该配置 raw 目录；这是并发状态记录，不是 idle gate。
4. AP eval 可以在对应 finetune 完成后复用同一张 GPU，也可以用空出的 GPU5/任一已完成 GPU；eval 不要求独占 GPU，但必须记录实际 `gpu_id`。

GPU 规则：

- 默认使用 H800 GPU0-4 五卡并行，每张卡一个 `train_ddp.py --nproc_per_node=1` 进程。
- 微调不是 latency/energy 测量，不要求 GPU 完全空闲；只要求目标 GPU 显存足够、没有会导致 OOM 的大进程。
- AP eval 的指标值不依赖 GPU idle，负载只会影响耗时；因此 AP eval 也不套用 latency/energy 的 idle gate，但必须记录 `gpu_id`、并发状态和日志。
- GPU5 默认保留给 replay/eval、digest 扫描、supervisor 或补救任务；如果只有 5 张卡可用，则 eval 等待任一 finetune 完成后再跑。

数据集与协议：

- 训练集：HEAL/DAIR-V2X-C train split，历史口径为 `train=4811`。
- 验证/评测集：DAIR-V2X-C val split，AP canonical 写作 `DAIR-V2X val_1789`，`num_samples=1789`。
- AP eval 命令沿用 stage_a/B2/B4 口径：`--n-samples 1789 --dataset dair --range 102.4,51.2 --collab-spatial-shape 2,64,128,256 --collab-tego-shape 2,2,3`。
- primary metric 为 AP70；AP30/AP50 写入 `secondary_metrics`。

微调过程：

1. 以 DAIR 金标准 base ckpt 为起点：

```text
${V2X_HOME}/heal_research/checkpoints/stage1/Pyramid_DAIR_m1_base_2023_08_14_11_42_29
```

2. 对每个 width 调用 `tools/structural_prune_pyramid.py` 生成对应 full-model config 和 init checkpoint：

```bash
CUDA_VISIBLE_DEVICES=<GPU> \
PYTHONPATH=${V2X_HOME}/heal_research/HEAL \
${V2X_HOME}/miniconda3/envs/UniV2X_2.0/bin/python \
  tools/structural_prune_pyramid.py \
  --orig-dir ${V2X_HOME}/heal_research/checkpoints/stage1/Pyramid_DAIR_m1_base_2023_08_14_11_42_29 \
  --out-dir ${V2X_HOME}/heal_research/checkpoints/stage1/Pyramid_DAIR_m1_stage2_ap_<label>_2026_06_26 \
  --num-filters-new <s0>,<s1>,<s2> \
  --width-per-group 4 \
  --groups 32
```

3. 必须检查并修正 init ckpt 格式：`net_epoch_bestval_at23.pth` 必须是 flat state_dict，不能是 `{"model_state_dict": ...}` 包裹格式。若是包裹格式，先 unwrap；否则 HEAL `load_saved_model(strict=False)` 可能从随机权重开始训，AP 作废。

4. 默认微调预算：

| 用途 | 默认设置 | 说明 |
| --- | --- | --- |
| stable smoke 首跑 | 每配置 1 次 finetune, `epoches=31` | 从 init@23 到 epoch31, 即 8 个 finetune epochs；与 B2/B4/stage_a 扩展口径一致 |
| repeat/噪声估计 | 不默认给 5 个新配置全做二次 seed | 先把 5 个配置跑通；只对异常或关键点补第二 seed |
| paper/final claim | 至少 2 seed 或收敛延长 | 若 AP 反常、bestval 落在最后 epoch、或曲线未收敛, 延长到 `epoches=48` 或 `epoches=70` |

5. 微调命令模板：

```bash
CUDA_VISIBLE_DEVICES=<GPU> \
PYTHONPATH=${V2X_HOME}/heal_research/HEAL \
${V2X_HOME}/miniconda3/envs/UniV2X_2.0/bin/python \
  -m torch.distributed.launch \
  --nproc_per_node=1 \
  --use_env \
  --master_port=<29700+GPU> \
  ${V2X_HOME}/heal_research/HEAL/opencood/tools/train_ddp.py \
  --hypes_yaml ${V2X_HOME}/heal_research/checkpoints/stage1/Pyramid_DAIR_m1_stage2_ap_<label>_2026_06_26/config.yaml \
  --model_dir ${V2X_HOME}/heal_research/checkpoints/stage1/Pyramid_DAIR_m1_stage2_ap_<label>_2026_06_26 \
  --half
```

6. 微调完成后，锁定 best checkpoint，导出 ONNX、构建 TRT FP16 engine、跑 DAIR val 1789 AP：


7. 生成 canonical AP row 时，必须写入：

```text
claim_status=claimable_true_eval 或 provisional_missing_digest
finetune_protocol=structural_prune_pyramid_L1_train_ddp_epoches31_half_TRT_FP16_DAIR_val_1789
training_budget=init23_to_epoch31_8ep_seed20260626
schedule_policy=not_applicable
dataset=DAIR-V2X
eval_split=val_1789
num_samples=1789
```

要求：

- 所有配置使用同一 AP runner 口径。
- base、p50、mix_d 至少做 2 次 repeat；repeat drift <= 0.003 AP70。
- 对 `mix_b/mix_d/p50b2_136` 这类 AP 高于 base 的点，必须保留 finetune protocol，不得写成“剪枝自然提升 AP”的泛化结论。
- 对 5 个新微调配置，首跑只要求每配置 1 次 finetune + 1 次 full val AP；如果出现 AP 高于 base、曲线未收敛、bestval 在最后 epoch、或同类点不符合局部趋势，进入 `quarantine_unstable_or_underconverged`，不得直接 claim。
- 输出 canonical rows：

```text
multi_agent/data/stage2_lut_generation_v1/generated/ap_stability_20260626/rows/ap_anchor_rows_v1.jsonl
```

Phase C stop 条件：

- 10 个已有 source 配置完成 canonical AP import/replay rows。
- 5 个 original60 新配置启动并完成 `epoches=31` smoke finetune；若某配置失败，必须给出明确 failed/quarantine reason。
- 至少 8 个 unique width 有 `claimable_true_eval` / `claimable_true_import` / `provisional_missing_digest` AP row。
- 至少 3 个 repeat anchor 通过 drift gate。
- `ap_stability_summary.md` 给出每个配置的 AP70、AP50、source、claim_status。

### Phase D: original60 AP Mapping

目标：不是强行给 60 个点都填 AP，而是把每个点能否稳定测 AP 的原因说清楚。

输出：

```text
multi_agent/data/stage2_lut_generation_v1/generated/ap_stability_20260626/exports/original60_ap_source_map_v1.jsonl
multi_agent/data/stage2_lut_generation_v1/generated/ap_stability_20260626/exports/original60_ap_axis_gap_report_v2.json
```

映射规则：

| 类型 | 处理 |
| --- | --- |
| exact width + exact ckpt/config | 进入 AP job queue |
| exact width + historical true import | 可生成 true_import row, 但需 digest/protocol |
| weight-identity transfer pair | 可 claim transfer, 但必须标 transfer |
| 只有 AP model prediction | `blocked_model_fit_only` |
| 只有 backbone ONNX/TVM artifact | `no_claim_missing_source` |
| 需要训练/finetune | 进入 separate training queue, 不阻塞 AP stable smoke |
