# FP16 AP 原始生成链路核对 v1

日期: 2026-06-28

## 1. 结论先行

当前 `rows/fp16_true_original60_ap_rows_v1.jsonl` 中 5 条 `measurement_status=measured` 的 FP16 AP row, 真实来源不是 backbone-only ONNX/TVM latency/energy smoke, 也不是旧表导入, 而是：

1. 使用已经存在的 `ckpt_dir` 与对应 `config.yaml`
2. 调用 `scripts/stage2_h800_true_fp16_ap_eval.py --execute --precision-mode amp_fp16`
3. 在 HEAL / OpenCOOD 的 PyTorch 模型评测路径上跑完整 `DAIR-V2X val_1789`
4. 生成 `raw/ap_eval_original60/.../ap_eval_report.json`
5. 同脚本把 report 转成 `ap_anchor_row_v1` 并追加到
   `multi_agent/data/stage2_lut_generation_v1/generated/original60_quant_20260627/rows/fp16_true_original60_ap_rows_v1.jsonl`

因此，当前 original60 的 FP16 AP 主链是：

`finetuned checkpoint -> HEAL PyTorch full eval -> ap_eval_report.json -> measured AP row`

不是：

`backbone ONNX/TVM smoke -> AP row`

## 3. 评测链路

### 3.1 运行前检查

脚本会检查：

- `ckpt_dir` 必须存在
- `ckpt_dir/config.yaml` 必须存在
- `ckpt_dir` 中必须有 `net_epoch_bestval_at*.pth` 或 `net_epoch*.pth`
- `HEAL root` 必须存在

并在 `raw_dir/gpu_preflight.json` 落盘：

- `nvidia-smi --query-gpu=...`
- `nvidia-smi pmon -c 1`

### 3.2 真正执行的模型评测

`run_true_fp16_eval()` 的核心行为：

1. `os.chdir(HEAL)`
2. `yaml_utils.load_yaml(None, opt)` 读取 `ckpt_dir/config.yaml`
3. `train_utils.create_model(hypes)` 创建模型
4. `train_utils.load_saved_model(ckpt_dir, model)` 加载 best checkpoint
5. `build_dataset(hypes, visualize=True, train=False)` 构建 DAIR 验证集
6. `DataLoader(... batch_size=1, num_workers=4, shuffle=False)`
7. 对每个 sample 调用模型前向
8. 通过 `dataset.post_process(...)` 生成 `pred_box_tensor / pred_score / gt_box_tensor`
9. 调用 `opencood.utils.eval_utils.caluclate_tp_fp(...)` 分别累计 IoU 0.3 / 0.5 / 0.7
10. 最后调用 `eval_utils.eval_final_results(...)` 输出 AP30/AP50/AP70

### 3.3 FP16 的具体口径

当前 5 条 measured row 使用的是：

- `--precision-mode amp_fp16`

对应实现不是 `model.half()` 全局半精度，而是：

- 模型参数仍保持 `float32`
- 前向包在 `torch.cuda.amp.autocast(dtype=torch.float16)` 中
- `dataset.post_process` 前把模型输出显式 cast 回 `float32`

对应证据文件：

- `raw/.../layer_precision_summary.json`

其中当前 observed runner 为：

- `torch.cuda.amp.autocast(dtype=float16)`

## 4. AP 如何写回 row

`stage2_h800_true_fp16_ap_eval.py` 在执行完 eval 后会写：

- `ap_eval_report.json`
- `layer_precision_summary.json`

然后 `build_row()` 将 report 转成 `ap_anchor_row_v1`，核心字段为：

- `measurement_status = measured`
- `metric = AP70`
- `metric_value = ap70`
- `secondary_metrics = {AP30, AP50}`
- `backend = model_eval`
- `measurement_source = true_eval`
- `precision = fp16`
- `quant_method = h800_tvm_true_fp16_onnx_relax`
- `quant_scope = full_model_ap_eval_true_fp16`
- `quality_gate_status = true_fp16_original60_ap_eval`
- `full_network_claim = false`

注意：

- `quant_method` 虽然命名里带 `onnx_relax`，但 AP 数值本身来自 HEAL PyTorch full eval，不是 TVM runtime AP。
- 这里的 `quant_method` 更像“该 software point 的工艺标签”，不是“AP 实际通过 TVM 图执行得到”的含义。

## 5. measured row 的 gate

脚本在 append row 前有硬 gate：

- `num_samples < 1789` 时，直接拒绝写 measured row

报错文本：

- `refusing to append measured AP row for partial eval`

所以 partial eval 不能写成 measured，这一点已在脚本层面落死。

## 8. 当前发现的一个口径风险

`s2_160` 存在宽度口径不一致的历史痕迹：

- completion queue 中 `s2_160` 宽度是 `[64,128,160]`
- 早期 smoke 计划文档中 `s2_160` 也写 `[64,128,160]`
- 但当前 measured row / `ap_eval_report.json` / `runner_command.json` 里写的是 `64,160,256`

这说明 `s2_160` 至少需要二次核对：

1. 当前 AP row 的 `width`
2. 对应 checkpoint 的真实结构
3. completion queue 中该 label 的 canonical width

在这三个口径统一前，不应把 `s2_160` 当成可直接复制的模板。

## 9. 对后续大规模补点的最小启示

后续要补 55 个 FP16 AP 空白，最小闭环应当严格复用当前主链：

1. 先拿到 exact-label 的 finetuned `ckpt_dir`
2. 保证 `config.yaml` 与 `net_epoch_bestval_at*.pth` 成对存在
3. 跑 `scripts/stage2_h800_true_fp16_ap_eval.py --execute --precision-mode amp_fp16`
4. 只有 `num_samples=1789` 的 full eval 才允许 append measured row

不需要把 backbone-only ONNX/TVM latency/energy smoke 混入这条 AP 主链。
