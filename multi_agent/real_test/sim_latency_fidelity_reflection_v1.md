## §0 一句话结论 (诚实)

**部分能反映 —— 机制层(时延→帧折算、帧对齐、ZOH、逐次 trace 回灌)真实且已验; 但当前形态(RSU-only 注入 + τ_ego=0 + L0 控制 + r0 易场景)在「物理效应层」存在两处结构性缺陷, 导致它当前不能反映「时延对驾驶的主导影响」:**

1. **漏掉了对驾驶更主导的 ego 自身推理延迟 τ_ego(质疑3)** —— 只注入了路侧 τ_comm 类延迟, 它只降协作感知质量、不拖慢控制回路; 而真正拖慢闭环反应、降低稳定裕度的 τ_ego_compute 被设为 0。
2. **「感知陈旧→驾驶退化」传导链: 存在性已证(r146 d500 致碰), 但脆弱、几何依赖、未鲁棒复现(质疑4 — ★2026-06-09 全 6 臂探针定论)** —— r0 全平真因坐实=场景太易; 难场景探针 6 臂中**唯 r146 d500=23.4(致碰)显现退化, r160 d500=100 未复现**(详见 §5.2)。⇒ 链路**可以**传导时延到驾驶(存在性证明), 但**不是鲁棒效应**(6 臂仅 1 臂, 疑依赖 88°转弯遮挡几何)。**且 d0/norsu 全 6 臂=100 ⇒ 两场景 RSU 均无净增益, "RSU 正向价值"未拿到。**

**机制做对了 ≠ 物理反映对了** —— 这是本反思的核心区分。**探针修正(诚实)**: RSU 路的「陈旧→退化」物理效应**能被触发但脆弱**(仅特定转弯遮挡几何), 当前**没拿到鲁棒的时延→驾驶曲线**; 且 **τ_ego 这条对驾驶更主导、更普适的回路延迟仍完全缺(缺陷 1 不变)**。⇒ 当前能偶发反映「陈旧协作感知有害」, 仍不能反映「端侧推理慢拖累回路反应」。

## §1 现状方法论的两层拆解

把当前仿真策略拆成「机制层」与「物理效应层」, 才能精准定位缺陷:

| 层 | 内容 | 状态 (诚实) |
|----|------|------------|
| **机制层** | 动态时延→帧数折算 Δ=ceil(τ/50); frame-keyed buffer 排队不丢帧; ZOH 融合前只作用 RSU 路; 逐次 trace 回灌驱动 Δ; 6 字段审计 log | ✅ **真实、已验**(C-4 双对照单测 13 项过 + R-4 audit log team-lead 独立核验吻合; τ 分布我已复算: n=153, min47.1/median65.4/max122.3) |
| **物理效应层** | 「这套机制注入的延迟, 是否对应真实驾驶里时延伤害安全的物理路径」 | ⚠️ **存在两处结构性缺陷**(下文质疑3/4), 且尚无任何场景实证传导成立(pilot r0 全平) |

**关键认识**: 机制层的正确性(folding/alignment/ZOH 都自洽)**不能推出**物理效应层的保真度。机制对了只保证「我们注入的延迟被正确施加到了 RSU 路」, 不保证「被施加的这个延迟是真实驾驶中起主导作用的那个延迟」, 也不保证「在测试场景里这个延迟有传导到驾驶行为的通道」。

## §2 逐条质疑剖析

### 质疑 1 — L0 控制是否掩盖时延敏感度?

**判断: 部分成立, 但更准确的描述是「扭曲」而非单纯「掩盖」。**

证据与推理:
- L0 定义(§3.5): 非推理帧**冻结上一条 throttle/steer/brake 指令**; planner 每 skip_frames=4=200ms 重算一次。
- **稀释效应(支持「掩盖」)**: planner 重算节拍 200ms 本身就比我们 sweep 的 RSU 陈旧量级(trace 真实 τ 50–122ms ⇒ Δ=1–3 帧=50–150ms)**更粗**。RSU 陈旧 1 帧, 但 planner 200ms 才吃一次新感知 —— RSU 50–100ms 的新鲜度差异有相当概率落在同一个 planner 周期内被「采样平滑」掉。这会**系统性压低**低时延档之间的可分辨性。
- **机制错配(「扭曲」而非「掩盖」)**: L0 冻结的是**控制指令**(方向盘角度/油门固定), 而真实自动驾驶栈(§3.5 L1)冻结的是**轨迹**——车沿旧 waypoints 继续推进, 控制器仍在闭环跟踪。两者在弯道/动态场景的行为可以完全不同: L0 在延迟期间「锁死指令」, 既可能比 L1 更早冲出车道(固定转向角累积偏离), 也可能在直道上恰好「碰巧安全」。**L0 不是均匀地削弱时延信号, 而是用一个非物理的保持机制替换了真实机制** —— 它产生的 DS 变化既不能解读为「时延无害」也不能解读为「时延有害」, 因为保持机制本身就不对。

**结论**: L0 既稀释(掩盖)低端可分辨性, 又扭曲(非物理)延迟期间行为。**文档 §3.5 自己已诚实标注 L0「保留只为量化仿真方法本身的误差」, 并把 L1 列为提升时延敏感度的关键升级** —— 这个自我认知是对的。L0 不适合作为「反映时延对驾驶影响」的控制档, 只适合作为 L1 的误差基线对照。

### 质疑 2 — CoDriving planner 是否真对感知陈旧敏感?

**判断: 现有证据不足以回答。P0 诊断回答的是另一个问题。**

关键区分(这是最容易被混淆、也最该 supervisor 盯的一点):
- **P0 诊断(§4.4)证明的命题 = 「有 RSU vs 无 RSU」改 control**: d0(有RSU) vs norsu(无RSU) 166 帧中 157 帧不同, max|Δthrottle|=0.75/|Δbrake|=1.0。这证明 **planner 确实消费融合 BEV**(不是只靠里程计/规则兜底) —— 这一点 P0 站得住, 是真结论。
- **但「planner 对陈旧度敏感」是另一个命题 = 「新鲜 RSU vs 陈旧 RSU」改 control**: 这需要比较 **d0(Δ=0) vs d500(Δ=10)** 的逐帧 control diff, 而**这个数据当前没有采**。pilot 8 档只比了最终 DS(全平), 没有逐帧 control-vs-Δ 的 diff。

⇒ **现有证据只能说「planner 用了 BEV」, 不能说「planner 对 BEV 的时序新鲜度敏感」。** 这两者之间差着一整个关键实验。完全可能: planner 消费 BEV, 但 BEV 在 r0 直道上**帧间内容几乎不变**(静止背景 + 缓慢目标), 于是「新鲜 BEV」与「陈旧 10 帧 BEV」内容近乎相同 ⇒ planner 输出近乎相同 ⇒ DS 全平。这种情况下不是 planner 不敏感, 而是**陈旧在该场景没产生可感知的内容差异**。

**廉价补强探针(强烈建议, 给 item 4 输入)**: 在难场景(r146/r160)上比 **d0 vs d500 的逐帧 control diff + BEV 内容 diff(陈旧帧 vs 当前帧的目标位置偏移)**。
- 若 d0 与 d500 control 几乎相同 ⇒ planner 对陈旧不敏感(或 BEV 内容不变), 需上 L1 或换更动态场景;
- 若 control 显著不同但 DS 仍平 ⇒ 控制差异未传导到安全后果(场景太易);
- 若 control 不同且 DS 分化 ⇒ 传导链通, 可铺全量。
这条探针比直接铺 48 格 sweep 便宜得多, 且能直接定位断点在哪一环。

### 质疑 3 — ★ τ_ego=0 是否漏掉了最主要的时延效应?

**判断: 是结构性遗漏, 成立。这是当前策略最本质的保真度短板。**

文档 §3.3 自己写得很清楚(我只是把它的逻辑后果点破):
- **τ_comm(路侧→自车传输延迟)**: 效果 = 协作特征与自车特征**时间错位** → 空间错位/鬼影/漏检。**不推迟自车出控制**。`age_collab = τ_collab_compute + τ_comm + τ_wait + τ_ego_compute + τ_act`。
- **τ_compute(自车推理延迟)**: 效果 = 基于 t 时刻数据算的计划要到 t+τ_compute 才可用 → **控制反应整体滞后**。`age_ego = τ_ego_compute + τ_act`。

**我们当前注入的 = RSU 路的 τ_comm 类延迟; τ_ego_compute 被显式设为 0(§3.8 用户拍板第一步)。**

为什么这是「漏掉主导效应」:
1. **控制理论层面**: 闭环反馈延迟(τ_ego)直接降低系统**相位裕度**, 导致超调、振荡、避障反应滞后 —— 这是闭环稳定性与碰撞的**第一性来源**。RSU 陈旧只是降低**一个输入通道的质量**(协作感知), 自车仍可用本车实时感知闭环。在多数驾驶安全场景里, **「回路反应慢了 100ms」比「协作感知旧了 100ms」对碰撞率的影响更直接、更主导**。
2. **量级层面**: 团队真测 ego 端侧(Orin)推理 e2e 混合链 FP32 219 / INT8 p75 108ms —— 这是**真实存在且可被优化的 τ_ego**, 恰恰是本项目「软硬件协同加速」要降的那个延迟。把它设为 0, 等于把**项目优化的主战场从闭环里抽走了**。我们加速降的是 ego 端侧推理, 但闭环里 ego 端侧推理零延迟 ⇒ **加速对闭环驾驶分的收益在当前仿真里恒为 0**, 无法体现「加速→更快反应→更安全」这条本该是核心卖点的链。

**nuance(不能一边倒)**: RSU 时延是 **V2X 协同特有**的维度(单车自动驾驶没有路侧协同延迟问题), 优先把它做扎实有**研究差异化定位**的合理性 —— 这正是「V2X 路侧推理 <200ms 是否提升驾驶安全」核心假设(§1)的直接对象。所以「先做 RSU」本身不是错; **错在如果把当前结果当成「时延对驾驶的影响」这个一般命题的完整回答** —— 它只回答了协同感知质量这半边, 回避了回路反应速度那半边(而后者通常更主导)。

⇒ **「本末倒置」的批评部分成立**: 就「哪个时延对驾驶更主导」而言, τ_ego 更主导却被设 0; 就「哪个时延是 V2X 论文差异化点」而言, τ_comm/RSU 是对的。**两个目标被混在一个实验里, 需要分清。**

### 质疑 4 — 「感知陈旧→驾驶退化」传导链是否结构性成立?

**判断: 在当前实验设置(RSU-only + L0 + r0 易场景)下大概率断裂。链条有 4 个串联断点, 任一断则全平。**

传导链 + 断点诊断:
```
RSU推理时延 →[Δ折算]→ RSU-BEV陈旧 →[融合]→ 融合BEV质量降 →[planner]→ waypoints差 →[控制]→ 轨迹差 →[场景]→ 碰撞/扣分
                ✅机制已验          ①断点?            ②断点?           ③断点(L0)        ④断点(易场景)
```

- **断点① 陈旧→BEV质量降**: r0 直道, 背景静止 + 目标缓慢 ⇒ 陈旧 1–10 帧的 BEV 内容差异可能极小(质疑2 同源)。**待 BEV 内容 diff 探针检验。**
- **断点② BEV质量降→planner输出差**: 过参数化 CoDriving + 可能的里程计/规则兜底 ⇒ planner 对 BEV 退化可能鲁棒。**未独立验证 planner 对陈旧的敏感度(质疑2)。**
- **断点③ planner差→轨迹差**: L0 冻结指令的非物理保持机制(质疑1)。
- **断点④ 轨迹差→碰撞**: **最致命的断点。r0 上 norsu(完全无 RSU)DS 也 = 100** —— 这意味着**在 r0, RSU 有没有都不影响安全, 那「RSU 陈旧多少」更不可能影响安全**。**逻辑前提缺失: 必须先有 norsu < 满分 的场景(证明 RSU 在该场景真有净增益), 才谈得上测「RSU 陈旧度→增益衰减」。** r0 连这个前提都不满足。

**结论**: 当前 r0 上传导链**断在断点④(场景太易)**, 且 ①②③ 均未被独立证明通畅。这与文档 §4.7 证伪条件 1+2 的命中完全一致。**难场景探针 r146/r160 的首要任务不是「找拐点」, 而是先建立断点④的前提 —— 验证 norsu < 满分(RSU 在难场景真有用)。** 若 r146/r160 的 norsu 仍 = 满分, 则需立即加难(scenario_parameter: DynamicObjectCrossing↑/pedestrian 60→120/CRAZY_LEVEL↑)或换更长更密 route, 而非铺全量 sweep。

## §4 要让仿真真能反映时延影响, 必须解决的问题清单 (★给 item 4 的输入)

按优先级与依赖排序:

### P0 — 先建立「传导链通畅」的前提 (无此则一切 sweep 无意义)
1. **难场景前提验证(廉价, 先做)**: r146/r160 跑 `norsu vs d0`, **确认 norsu < 满分**(RSU 在难场景真有净增益)。若仍满分 → 立即加难(scenario_parameter)或换 route, 不铺全量。
2. **planner 陈旧敏感度探针(廉价)**: 难场景上 `d0 vs d500` 逐帧 control diff + BEV 内容 diff(陈旧帧 vs 当前帧目标位置偏移)。定位断点在①②③哪一环(见质疑2 三分支判读)。

### P0 — ego 时延建模 (item 4 主体, 填上最主导的缺失效应)
3. **实现 τ_ego ≠ 0**: 用 LatencyScheduler 取代固定 skip_frames=4, 让 ego 推理触发由真实 τ_ego 驱动(§3.8 记账的「第二步」)。这直接让闭环反映「端侧推理慢→控制反应滞后」, 也让**本项目的加速优化对闭环驾驶分产生非零收益**(否则加速卖点无法在仿真体现)。
4. **RSU/ego 时延匹配策略(item 4 核心设计问题)**: 两条路径年龄 `age_collab` 与 `age_ego` 必须**分别注入、各走各的物理路径**(§3.3): τ_ego 走「推迟自车出控制」(控制滞后), τ_comm/RSU 走「协作特征时间错位」(融合前 ZOH, 不推迟出控制)。**禁止把两者合成一个标量延迟** —— 这是 §3.3 已论证的原理, item 4 必须落实为两个独立注入旋钮。
5. **加速档↔τ_ego 联动**: 把团队真测时延档(Orin FP32 219/FP16 136/INT8 108ms)接入 τ_ego, 这样不同精度/剪枝档在闭环里产生不同 ego 反应延迟 ⇒ 才能画出「加速→驾驶分」曲线, 服务最终目标(B1×B2×D 联合搜索的闭环验证)。

### P1 — 控制保真度
6. **L0→L1 轨迹跟踪控制器**: waypoints 锚定世界系+时间戳, PID 按 (t_now−t_anchor) 时间索引插值跟踪「最近计划」。这让延迟期间的车辆行为物理正确(沿旧轨迹推进, 对新障碍滞后 age_ego 反应), 修掉质疑1 的扭曲。L0 vs L1 的 DS 差 = 仿真保真度修正量, 本身有研究价值。

### P2 — 通信链路真实性
7. **per-link 通信模型**: τ_comm 抖动/丢包/传输量(随特征体积变化), 取代当前常数/单一 trace τ。让 RSU 路延迟有真实分布而非确定值。
8. **HIL Orin 在环(最高保真上界)**: 推理在真 Orin 跑, 回传真实端侧时延分布 + 真物理隔离, 作为锚点校准注入档。

### 横向纪律 (supervisor 持续盯)
- 闭环 sweep 入库前, **必须分清 τ_ego 档与 τ_comm 档**, 不可混入同一时延轴(否则又是「跨口径拼曲线」)。
- 每个 DS 数字标 `latency_ms_source`(injected/trace_replay/measured)+ 控制档(L0/L1)+ τ_ego 是否为 0。
- 「DS 随时延下降」的结论, 必须先排除「场景太易(断点④)」与「L0 扭曲(断点③)」两个混淆因子, 才能归因到「时延伤害驾驶」。防重蹈 AP50 2dp 假象式的归因错误。

## §4.A ★ item4 专项展开 — 为什么必须补 τ_ego + 双路径时间轴如何匹配 (team-lead 点题, 直接喂 item4 策略 md)

### A.1 为什么必须补 τ_ego (三条独立理由, 任一成立即必补)

1. **物理主导性**: τ_ego(自车感知+规划计算延迟)直接进入控制反馈回路 ⇒ 降低闭环**相位裕度** ⇒ 避障/跟车反应整体滞后 → 超调、振荡、追尾/碰撞。而 τ_RSU 只污染**一个输入通道**(协作 BEV)的时效, 自车仍可用本车实时感知闭环。**在动态安全场景, 回路慢 100ms 通常比协作感知旧 100ms 对碰撞率影响更直接。** 不补 τ_ego = 漏掉对安全更主导的那一项。
2. **项目卖点闭合**: 本项目软硬件协同加速降的**就是 τ_ego**(Orin e2e 真测 FP32 219 → INT8 p75 108ms, 降 ~111ms ≈ 2 帧)。当前 τ_ego=0 ⇒ 不同加速档(FP32/FP16/INT8/各剪枝率)在闭环里**ego 反应延迟全相同(=0)** ⇒ **「加速→更快反应→更安全」这条本该是论文核心的因果链, 在仿真里恒为空。** 补 τ_ego 是让「加速对驾驶分的收益」从恒 0 变成可测曲线的**唯一途径**。
3. **覆盖完整性**: §1 核心假设是「路侧推理 <200ms 是否提升驾驶安全」, 但真实部署里 RSU 与 ego 推理延迟**同时存在**。只注 τ_RSU = 假设 ego 是理想瞬时机, 与任何真实边缘部署都不符。要回答「时延对驾驶的影响」一般命题, 两条路径缺一不可。

### A.2 双路径信息年龄模型 (per-path information age — 时间轴匹配的数学骨架)

承 §3.3: τ_comm 与 τ_compute 作用在管线**不同位置, 不能合成一个标量**。统一量 = 逐路径信息年龄。在仿真帧 k(每帧 50ms)上, 两条路径各自的「年龄」与「施加位置」:

| 路径 | 信息年龄公式 | 物理含义 | **施加位置(关键)** |
|------|------------|---------|-------------------|
| **协作路(RSU/CAV)** | `age_collab = τ_collab_compute + τ_comm + τ_wait + τ_ego_fuse + τ_act` | 协作特征算完→传到→等到融合的总时延 | **融合前、只作用 RSU 路**: 用 Δ_RSU=ceil(age_collab_comm段/50) 后推帧 + ZOH。**不推迟自车出控制。**(✅ 已实装) |
| **自车路(ego)** | `age_ego = τ_ego_compute + τ_act` | 基于 t 时刻数据算的计划要到 t+age_ego 才生效 | **推迟自车出控制**: 帧 k 用的 plan 来自帧 k−Δ_ego 的感知, Δ_ego=ceil(τ_ego_compute/50)。**整条控制链滞后。**(❌ 当前 τ_ego=0, 待 item4) |

**两条路径的本质区别(item4 必须落实)**:
- **τ_RSU 只改「协作 BEV 内容有多旧」** → 影响融合质量 → 间接影响 planner 输出。它**不改 ego 出控制的时刻**。
- **τ_ego 改「整个 plan 何时可用」** → ego 感知/融合/规划全部往后推 Δ_ego 帧 → 控制反应整体滞后。它**直接改 ego 出控制的时刻**。
- ⇒ 二者在时间轴上是**正交的两个旋钮**, 必须分别注入。**合成一个标量延迟 = 物理错误**(会把「协作感知旧」错算成「控制反应慢」, 反之亦然)。

### A.3 时间轴匹配的具体注入设计 (item4 实现提纲)

在仿真帧 k:
```
ego 本车感知:    帧 k 实时采集 → 但 plan 受 τ_ego 推迟: 帧 k 实际执行的 plan 基于帧 (k−Δ_ego) 的 ego 感知
协作 RSU 感知:   帧 (k−Δ_ego−Δ_RSU) 的 RSU 结果(经 ZOH)与帧 (k−Δ_ego) 的 ego 感知融合
                 ↑ 注意: RSU 陈旧度是相对「ego 实际用的那一帧」叠加的, 两个延迟串联
控制输出:        帧 k 执行 帧 (k−Δ_ego) 算出的 plan(L1 沿轨迹推进; L0 冻结指令=非物理)
```

- **两个独立 config 旋钮**: `simulation.tau_ego_ms`(驱动 Δ_ego, 推迟出控制) + 现有 `latency_trace`/`latency_inject_ms`(驱动 Δ_RSU, 融合前 ZOH)。
- **LatencyScheduler 取代固定 skip_frames=4**: 当前 skip=4(200ms)是写死的 ego 节拍, 与 τ_ego 无关。item4 应让 ego 推理触发由 τ_ego 驱动 —— 推理慢则下一帧 plan 晚到, 节拍随加速档变化。
- **加速档↔τ_ego 映射表**(接团队真测, 服务最终目标): {FP32: 219ms→Δ_ego=5, FP16: 136ms→Δ_ego=3, INT8 p75: 108ms→Δ_ego=3, 各剪枝率: 待 hw 补} —— 不同档喂不同 Δ_ego, 才能扫出「加速→驾驶分」曲线。
- **L1 是 τ_ego 生效的前提**: L0 冻结指令无法正确表达「sub-Δ_ego 帧内沿旧轨迹推进、对新障碍滞后反应」; 必须 L1 轨迹跟踪才能让 age_ego 的滞后物理正确传导。⇒ **item4 的 τ_ego 与 L1 控制器应捆绑实现**, 否则 τ_ego 注入了也被 L0 扭曲。

### A.4 留给 item4 的设计开问题 (supervisor 提请决策)

1. **Δ_ego 与 Δ_RSU 串联还是并列?** A.3 按串联建模(RSU 陈旧叠加在 ego 用的那一帧上)。需确认这是否符合真实系统(RSU 数据是「ego 当前帧请求时已有的最新」还是「ego 计算那一刻的最新」)。
