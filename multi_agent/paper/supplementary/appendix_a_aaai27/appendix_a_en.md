# Supplementary Material: Measurement Protocols for Figures 1 and 2

## Appendix A: Measurement Protocols for Figures 1 and 2

In the zero-injection V2XVerse closed-loop baseline used for Figure 1(a), CARLA advances synchronously at 20 Hz, so each simulation step spans $\delta_{\mathrm{sim}}=50$ ms. At every step, the system acquires the ego state and sensor observations. It runs the complete cooperative perception and planning pipeline once every four simulation steps. During inference, observations from the ego vehicle, collaborating vehicles, and roadside units are first organized as CoDriving multi-agent inputs. The system then performs feature extraction, spatial alignment and cooperative fusion, object detection, occupancy-representation construction, and trajectory planning. The controller converts the predicted trajectory into steering, throttle, and brake commands. Between complete inference frames, the vehicle updates its control using the most recent plan and its current ego state. CARLA advances to the next simulation step only after the control command is returned. Consequently, inference runtime does not alter subsequent vehicle-state evolution in this baseline. The baseline therefore cannot directly expose how inference latency affects closed-loop driving behavior and safety.

Compared with this baseline, we insert an ego-observation latency module between raw observation acquisition and perception preprocessing. The perception, fusion, planning, and control modules remain unchanged. At each complete inference frame $k$, the module first copies the current ego input into a historical-frame buffer. It then computes the target frame delay as $\Delta_{\mathrm{perc}}=\lceil\tau_{\mathrm{perc}}/\delta_{\mathrm{sim}}\rceil$ from the nominal perception latency $\tau_{\mathrm{perc}}$. The module selects the latest cached frame $j$ satisfying $j\leq k-\Delta_{\mathrm{perc}}$ and uses it to replace the current ego input. The downstream pipeline, from perception feature extraction through control output, therefore operates on historical ego observations. Meanwhile, the simulated world continues to evolve according to its normal clock. This mechanism models the effect of stale perception information.

We evaluate this injection mechanism in Figure 1(a) using CoDriving on an NVIDIA H800 under the V2XVerse full-traffic setting. Nominal latency ranges from 0 to 700 ms in 50-ms increments, with additional high-latency stress points at 800, 900, and 1,000 ms. This sampling densely resolves the onset of degradation and covers the high-latency failure region. We first screen the candidate routes under zero latency. An eligible route must achieve a Driving Score (DS) of at least 99.9 in at least two repetitions, without collisions or timeouts. We then intersect the routes with valid records under every latency setting, yielding 35 matched routes. Each matched route is independently evaluated three times at every latency setting. The blue curve reports the Honest Driving Score (Honest DS), computed using the default CARLA Leaderboard procedure. A timed-out run or a run without a valid score contributes $\mathrm{DS}=0$ to the mean. Error bars show 95% confidence intervals computed as $1.96s/\sqrt{n}$, where $s$ and $n$ denote the sample standard deviation and number of runs. The red curve reports the collision rate among completed runs. A run is counted as a collision if any pedestrian, vehicle, or static-layout collision metric is nonzero. The purple curve reports the proportion of all runs that time out before evaluation finishes or fail to produce a valid DS. Such outcomes usually indicate a severe incident that leaves the vehicle stationary before it reaches the route endpoint.

Figure 2 divides the V2X perception pipeline into four stages: input encoding, Backbone + Neck, feature fusion, and detection. We use the same four-stage timing contract to provide consistent module attribution for Pyramid, CoDriving, and F-Cooper. For LiDAR models, input encoding includes voxelization or pillar encoding and scatter operations. For camera models, this stage corresponds to the image-processing front end. Neck, deblock, upsampling, and shrink-convolution operations are assigned to the backbone stage. The detection stage includes both the prediction head and post-processing. The prediction head performs classification, box regression, and heading prediction. Post-processing includes score-threshold filtering, top-$k$ selection, box decoding, heading correction, conversion to box corners, rotated non-maximum suppression, and range filtering.

Figure 2 and Table 1 in the main paper use different hardware, execution backends, and measurement scopes. The stage-wise profile in Figure 2 is collected on an NVIDIA GeForce RTX 4090 using the native PyTorch/CUDA execution path. Its purpose is to quantify the computational share of each stage in the complete perception pipeline. Module timing starts with inputs that are already resident on the GPU. Dataset loading, CPU preprocessing, Host-to-Device transfers, and interprocess communication are therefore outside the Figure 2 measurement boundary. CUDA events record the start and end of each module, and the device is synchronized before elapsed time is queried. The complete interval encloses the same device-side forward and post-processing path. The stage table reports arithmetic means, while the underlying records retain the median and p99. Pyramid, CoDriving, and F-Cooper each use 50 warm-up iterations followed by 200 measured iterations. For every model, a single run covers input encoding, model inference, and post-processing under the same timing boundary. The results are summarized in Table 1.
